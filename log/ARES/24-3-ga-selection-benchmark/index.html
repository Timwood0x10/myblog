Selection Operator Performance — Truncation vs Tournament vs Roulette

2026-06-28
:: tags:  #Agent  #Benchmark  #Genetic Algorithm  #Go

Selection operator performance — Truncation vs Tournament vs Roulette, measured

This article compares the three major selection operators in internal/runtime/ares_evolution/genome/selection.go using real go test -bench output — their asymptotic complexity, memory behavior, and the right situation for each. Every number below is a single -count=1 measured run, not an invented figure.

⚠️ Note: Go benchmark ns/op depends on the machine, the compiler, and load. The numbers below were measured on go1.27.1 / darwin / arm64 (Apple Silicon) with -benchtime=200ms -count=1 and are meant to convey order-of-magnitude only. Treat the earlier draft's certainty about a specific "Apple M3 Max single run" as non-reproducible.

All benchmarks live in internal/runtime/ares_evolution/genome/benchmark_test.go.

2. Measured data (go1.27.1 darwin/arm64, -count=1)

2.1 TruncationSelection

pop_10    161.2 ns/op
pop_100   5669  ns/op
pop_500   52825 ns/op
pop_1000  156384 ns/op

Cost is almost entirely the sort plus a slice copy.

2.2 SortByScore (sort baseline)

pop_10    208.7 ns/op
pop_100   6098  ns/op
pop_500   51463 ns/op
pop_1000  144377 ns/op

Truncation and SortByScore are the same order of magnitude (truncation's pop_500 is a touch under the bare sort because the benchmark also builds a result slice; within measurement noise).

2.3 TournamentSelection

pop_50  k=2   3875 ns/op   k=3  4013   k=5  4299   k=10  5514
pop_200 k=2  31903 ns/op   k=3 34263   k=5 34876   k=10 38656

Observation: going k from 2 to 10 (a 5× change) moves pop200 only from ~32µs to ~39µs (≈ +21%) — far from linear. The reason is in the code: pickUniqueIndices uses a Fisher–Yates partial shuffle whose cost is dominated by poolSize, and pool copying plus slice construction dominate. So raising k to raise selection pressure costs almost nothing computationally — but it also means tournament's dominant cost is a fixed constant (copy, slice building), not the number of comparisons.

2.4 RouletteWheelSelection

pop_10    202.1 ns/op
pop_100   2902  ns/op
pop_500   43097 ns/op
pop_1000  160606 ns/op

Each spin walks the full cumulative-weight array (O(n)); selecting n/2 individuals is O(n²). So by pop=1000, roulette (160.6µs) has tipped past truncation (156.4µs).

3. The crossover point

        t3[Truncation ~156 µs]

    end
  • Small populations: effectively a wash (microseconds); which is "fastest" is drowned in noise.
  • Around pop≈500 they cross: truncation's O(n log n) meets roulette's O(n²).
  • Tournament: the absolute time is the highest of the three (already ~32µs at pop200), driven by result construction and shuffling — but it's flat as k grows.

4. Memory allocation

Following the logic of the same benchmarks: all three copy the population and build a result slice (allocations grow linearly with population). Tournament is the heaviest per Select because of the shuffle scratch array plus the result slice. For exact B/op and allocs/op, run:

go test -bench=BenchmarkTournamentSelection -benchmem ./internal/runtime/ares_evolution/genome/

(The qualitative statement is safe: sort/truncation allocators don't grow with size — the bench copies the population slice once; roulette/tournament allocate fresh slices per select, so allocs grow linearly. Exact numbers must be measured.)

5. Complexity at a glance (from code and comments, not invented)

OperatorScopeBig-ONotes
Truncationwhole batchO(n log n)sort-dominated, stable, unevaluated last
SortByScorewhole batchO(n log n)sort.SliceStable, deterministic
Tournamentper selectO(n) shuffle + O(k) comparepool copy is the constant-dominant cost
Rouletteper spinO(n)selecting n/2 ≈ O(n²)
SUSwhole batchO(n + n·log n)single start + evenly spaced pointers, low variance
Rank / LineageRankwhole batchO(n log n)weights from post-sort linear rank

SUS deserves a special mention: versus roulette it takes one random start and then evenly spaced picks, guaranteeing a more even sampling distribution and less genetic drift — exactly what the comment states: "guarantees that an individual with above-average fitness is selected at least floor(fitness/avg_fitness) times."

6. How to choose: an engineering judgment

The code comments already point the way:

ConcernLean towardWhy
Tune selection pressureTournamentWithTournamentSize(k); measured cost barely moves as k grows
Determinism / replayTournament / RouletteWithTournamentSeed / WithRouletteSeed
Sparse improvements, lineage diversityLineageRankthreshold 0.4, strength 0.5, penalizes dominant lineages
Minimal sampling variance, anti-driftSUSevenly spaced pointers beat roulette variance
Deterministic top-NTruncationwhen you know the top band is the good band
Multi-objective trade-offsNondominatedSortingnot wired: "nsga2" silently falls back to tournament (no code writes DimensionScores)

The most important reality: in LLM-driven evolution a single scoring call takes seconds, while any selection operator's whole batch takes microseconds. The operator's algorithmic effect — diversity, convergence quality — matters far more than tens of microseconds. Don't sweat 5% of ns/op; choose the operator that is less likely to converge prematurely on your task distribution.

7. Appendix: reproducing

go test -run=^$ \
  -bench='Benchmark(Truncation|Tournament|RouletteWheel|SortByScore)Selection?$' \
  -benchtime=200ms -count=1 -benchmem \
  ./internal/runtime/ares_evolution/genome/

Baseline reproduced: go1.27.1 darwin/arm64, single -count=1 run. Add -count=3 for variance and discount the first run's GC disturbance.
