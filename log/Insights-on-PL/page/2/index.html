Rust 与 Go 的异步体系对比

2026-10-25
:: tags:  #Async  #Concurrency  #Go  #Rust

这篇我想把 Rust 和 Go 的异步体系放在一起比：不只是语法，而是执行模型、调度器、通信机制、select、取消语义、内存与资源消耗。

select 我会单独展开，因为它最能体现两种语言在并发设计上的分歧。

比较口径先说清楚：Rust 侧用 Tokio（最常用的异步运行时），Go 侧用标准库。Rust 的 select! 是 Tokio 提供的宏，不是语言语法；Go 的 select 是语言内建语句。 这个前提不搞清，后面的比较都会偏。

参考：Tokio 教程、Go 语言规范、Rust 异步编程。

一、设计理念：隐藏复杂性 vs 显式状态机

先给结论。

Go：让并发编程尽量简单，用 Goroutine + Channel + 运行时调度把门槛降下来。

Rust：把异步计算变成可组合的状态机，在编译期尽量把内存、所有权、并发安全约束清楚，再交给运行时执行。

1.1 Go：用 Goroutine 藏起调度细节

package main

import (
    "fmt"
    "time"
)

func worker(id int) {
    time.Sleep(time.Second)
    fmt.Println("worker", id, "done")
}

func main() {
    for i := 0; i < 10; i++ {
        go worker(i)
    }
    time.Sleep(2 * time.Second)
}

核心就一行：

go worker(i)

它启动一个 Goroutine。不用手动建线程，也不用管任务什么时候暂停、什么时候恢复。

Go Runtime 负责：

  • 创建和调度 Goroutine；
  • 把 Goroutine 分配给可运行的操作系统线程；
  • 处理网络 I/O 的等待与唤醒；
  • 管理 Goroutine 的栈；
  • 执行垃圾回收。
go function()

      ▼

      │
      ▼
   Go Runtime
      │
      ▼

      ▼

Goroutine 是由 Go Runtime 管理的轻量执行单元：它不是 OS 线程，但能在线程上运行，也能在运行时被调到别的线程。

注意：go 启动不意味着函数立即执行，也不意味着它一定和当前函数并行在不同核心上。

1.2 Rust：async fn 首先是个 Future

async fn worker(id: usize) {
    do_something(id).await;
}

看起来也简单，但有个根本区别：调用 async fn 不会执行函数体，它返回一个表示「未来计算」的 Future。

async fn calculate() -> i32 {
    println!("calculating");
    42
}

fn main() {
    let future = calculate();
    println!("future created");
}

我实测了一下：输出是

future created
calculating

calculating 是在后面 await 时才打印的。Future 必须被驱动（poll）才会推进。

Rust 标准库只定义了 Future trait，没有提供通用异步运行时。所以得选 Tokio、async-std 之类。Tokio 提供任务调度、异步 I/O、定时器、异步 channel、同步原语、任务取消等能力。

关键结论：Goroutine 和 Future 不是等价概念。

  • Goroutine 是「正在运行或等待运行」的执行单元；
  • Future 是一份「可被推进的计算状态」；
  • Tokio Task 是执行器管理的任务，通常承载一个 Future。

所以合理的比较对象是：

Go   : Goroutine + Go Runtime Scheduler
Rust : Future + Tokio Task + Tokio Executor

二、调度模型

2.1 Go 的 G-M-P

  • G：Goroutine，执行单元；
  • M：Machine，操作系统线程；
  • P：Processor，执行 Go 代码所需的调度资源（持有本地运行队列等）。
                 Go Runtime
                      │
          ┌───────────┴───────────┐
          │                       │
       P0 / P1 / P2 ...        Goroutine 队列
          │                       │
          ▼                       │
       M0 / M1 / M2 ... ◄─────────┘
          │
          ▼
      操作系统线程
          │
          ▼
          CPU

一个 P 同一时刻只能被一个 M 持有；M 必须先绑定 P 才能执行 Go 代码。Goroutine 可以在不同时间跑到不同的 M 上。

func worker() {
    for {
        doSomething()
    }
}

func main() {
    go worker()
    go worker()
    go worker()
    select {}
}

三个 Goroutine 不代表三个线程。8 核机器上，runtime 可能这样排：

M0: G1 → G2 → G3 → G1
M1: G4 → G5 → G6 → G4

这只是示意。实际取决于可运行队列、P 的数量、阻塞状态、系统调用和调度策略。

Goroutine 阻塞时分三种情况：

  1. 网络 I/O：runtime 用网络轮询器（netpoll），让等待的 Goroutine 休眠，不必占着一个线程干等。
  2. 系统调用：某些系统调用会真的阻塞线程，runtime 可以分离 P、让别的线程继续跑 Go 代码，等调用返回再重新调度。
  3. 纯计算：一直跑 CPU 循环就持续吃 CPU。Go 在这块做过专门改进——后面「抢占」一节细说。

2.2 Tokio 的调度

              Tokio Runtime
                    │
           ┌────────┴────────┐
           │                 │
        Worker 0           Worker 1
           │                 │
        Task Queue         Task Queue
           │                 │
           ▼                 ▼
        Future A           Future B
           │                 │
         poll()            poll()
           │                 │
      ┌────┴────┐       ┌────┴────┐
      ▼         ▼       ▼         ▼
    Ready    Pending   Ready    Pending

多线程运行时用工作窃取分配任务；单线程运行时就在一个线程上跑。

use tokio::time::{sleep, Duration};

async fn worker(id: usize) {
    println!("worker {id} started");
    sleep(Duration::from_secs(1)).await;
    println!("worker {id} finished");
}

#[tokio::main]
async fn main() {
    let a = tokio::spawn(worker(1));
    let b = tokio::spawn(worker(2));
    let _ = tokio::join!(a, b);
}

tokio::spawn 把 Future 交给运行时，不是给每个任务开一个线程。任务等定时器时返回 Pending，执行器转去跑别的任务，定时器到期再唤醒它。

2.3 抢占：这是两种模型最本质的分歧之一

Go：有异步抢占。

早期 Go 的抢占是协作式的——只在函数调用时检查栈边界，一个没有函数调用的死循环能让整个 P 卡住。Go 1.14 引入了基于信号的异步抢占，可以在几乎任意指令边界打断 Goroutine。这解决了很多「长循环拖垮调度」的问题。

但也不是毫无边界：cgo 调用、某些汇编、runtime 内部路径仍有限制。

Tokio：纯协作式。

一个任务在执行时如果不主动 .await，执行器没有办法打断它。

async fn bad_task() {
    loop {
        expensive_cpu_work();
    }
}

这段写在 async fn 里，但循环里没有任何 .await，它就会长时间占住一个 worker 线程，其他任务排队。async 不会把同步计算自动变成可暂停的东西。

Tokio 有 coop budget 之类的机制，但它作用于 Tokio 自己的资源（读 channel、拿锁等），不是对所有 CPU 指令序列的强制抢占。

遇到长时间 CPU 计算，正常做法是：

  • spawn_blocking 扔给阻塞线程池；
  • 专门的 CPU 线程池；
  • 把计算切成小块，中间主动 await 让出。

所以一个实用的判断：

Go 的调度器能「打断」你，Tokio 的调度器等「你主动让」。

把长时间同步计算塞进 async fn 时，Tokio 不会救你，Go 大体上会。

三、通信机制

3.1 Go：channel 是语言的一部分

// 无缓冲：发送与接收必须同时就绪
ch := make(chan int)

// 有缓冲：缓冲区没满就能发，没空就能收
buffered := make(chan int, 8)

chan T、<-、close、select 全是语言语法，不需要 import 任何库。

无缓冲 channel 的同步语义很直观——发送方会一直阻塞到有接收方取走。我实测过：

发送方：准备发送（会阻塞）
接收方：开始接收
发送方：已被接收方取走，解除阻塞

这就是 CSP 的核心：不要通过共享内存通信，要通过通信共享内存。

3.2 Rust：channel 是库，而且有很多种

Rust 标准库只有 std::sync::mpsc（多生产者单消费者），而且它没有 select 支持。实际项目基本都用 Tokio 的 tokio::sync：

类型语义
mpsc多生产者单消费者队列
oneshot一次性发送一个值
broadcast多生产者多消费者，每条消息广播给所有订阅者
watch单值广播，新订阅者只看最新值

这里没有「语言内建 channel」这回事，全都是库提供的数据结构。所以 Rust 的通信模型天然更分散：你要按场景挑工具，而不是只有一个 chan。

这个差异挺重要：Go 的并发原语是语法，Rust 的并发原语是库。 语法更统一也更好教；库更灵活，但也更容易选错。

四、取消语义

4.1 Go：context 协作取消

ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()

select {
case <-ctx.Done():
    return ctx.Err()
case result := <-work:
    return result
}

要点：

  • 没有「强制杀死一个 Goroutine」的 API，这是设计选择；
  • 被调用方必须主动检查 ctx.Done() 或把 ctx 传下去，取消才会生效；
  • 如果某段代码压根不看 ctx，它会照跑到结束。

4.2 Rust：drop Future 就是取消

Rust 的取消不需要协议：

let handle = tokio::spawn(worker());

// 直接丢掉 handle 或 abort
handle.abort();

abort() 的本质是让运行时丢掉这个 Task 持有的 Future。Future 是状态机，drop 它，推进就停了，占用的资源按 Drop 实现释放。

这比分发一个取消信号更「干脆」，但有两个必须理解的点：

第一，取消点只在 .await 处。

Future 不处于执行状态时才有「可被 drop」这回事。如果 Future 正在跑一段同步代码，调度器不会在指令中间把它 drop 掉——因为那本来就是同一个线程在顺序执行。

第二，取消不是「中断」，是「不再推进」。

drop 时执行的是 Drop，不是某种异步清理流程。如果你的清理逻辑需要 .await（比如发个网络请求再断开），Drop 里做不到，得用 async fn shutdown() 之类的显式协议。

Tokio 也提供 CancellationToken（需要 tokio-util），那个是协作式的，语义更接近 Go 的 context。

4.3 对比

GoRust + Tokio
主要机制context.Contextdrop Future / abort()
是否强制协作，需主动检查结构性，drop 即停止推进

五、select：等待多个事件

5.1 Go：等待多个 channel 操作

select {
case msg := <-ch1:
    fmt.Println(msg)
case msg := <-ch2:
    fmt.Println(msg)
}

两个 case 不会自动起两个 Goroutine。select 只是等待多个通信操作，选一个能执行的执行。想让两件事独立跑，得自己 go 出去。

select 的分支只能是 channel 的发送或接收，这是语言层面的限制。

5.2 Tokio：等待多个 Future

use tokio::sync::oneshot;

#[tokio::main]
async fn main() {
    let (tx1, rx1) = oneshot::channel::<String>();
    let (tx2, rx2) = oneshot::channel::<String>();

    tokio::spawn(async move {
        let _ = tx1.send("hello from rx1".to_string());
    });
    tokio::spawn(async move {
        let _ = tx2.send("hello from rx2".to_string());
    });

    tokio::select! {
        result = rx1 => {
            println!("rx1: {:?}", result);
        }
        result = rx2 => {
            println!("rx2: {:?}", result);
        }
    }
}

看起来很像，但分支不限于 channel：

tokio::select! {
    result = database_query() => {
        println!("database completed: {:?}", result);
    }
    result = http_request() => {
        println!("http completed: {:?}", result);
    }
    _ = tokio::time::sleep(std::time::Duration::from_secs(5)) => {
        println!("timeout");
    }
}

数据库查询、HTTP 请求、定时器，三个完全不同的 Future 可以并列等待。

这就是最大的抽象差异：Go 的 select 只能选 channel 操作，Tokio 的 select! 能选任何 Future。

六、Go 的 default 与 Tokio 的 else 并不等价

这块特别容易踩。

6.1 Go 的 default：没有可执行的通信就立刻执行

select {
case msg := <-ch:
    fmt.Println("received:", msg)
default:
    fmt.Println("nothing ready")
}

ch 没消息时，立刻走 default，不等待。

放进循环里就是经典的忙轮询：

for {
    select {
    case msg := <-ch:
        handle(msg)
    default:
        // 暂时没有消息
    }
}

我实测了一下：空 channel + default，50ms 里空转了 137 万次。CPU 直接被吃满。

想等消息就不要加 default。

6.2 Tokio 的 else：所有分支都被禁用时才执行

tokio::select! {
    Some(msg) = rx.recv() => {
        println!("{msg}");
    }
    else => {
        println!("all branches disabled");
    }
}

else 不是 Go default 的对应物。

用 Some(msg) = rx.recv() 这种带模式的写法时，如果 recv() 返回 None（channel 关闭），模式不匹配，这个分支就被禁用。当全部分支都被禁用，才走 else。

我实测验证了两件事：

场景 A：channel 仍开启，只是暂时没消息。

tokio::select! {
    Some(msg) = rx.recv() => println!("got {msg}"),
    _ = tokio::time::sleep(Duration::from_millis(120)) => {
        println!("超时分支触发");
    }
    else => println!("else"),
}

输出：

超时分支触发，用时 121.878667ms

等了 120ms 走超时分支。没有立即执行 else，也没有立即返回。

场景 B：channel 已关闭。

let (tx, mut rx) = mpsc::channel::<String>(4);
drop(tx);

recv() 立刻返回 None，模式不匹配 → 分支禁用 → 走 else：

all branches disabled -> else

6.3 一个语法细节

else 必须放在所有分支之后，而且前面不能有逗号漏写。我第一次写的时候把它夹在中间，编译器直接报：

error: expected identifier, found keyword `else`

所以顺序是固定的：普通分支在前，else 收尾。

6.4 对照表

场景Go defaultTokio else
当前没有消息，但通道仍开启立即执行 default继续等待，不执行 else
所有分支都被禁用取决于是否有可执行分支执行 else
能否等待非 channel 的 Future不能能
忙轮询风险加 default 后很常见没有等价语义

所以下面这两段看起来对应，行为完全不同：

select {
case msg := <-ch:
    handle(msg)
default:
}
tokio::select! {
    Some(msg) = rx.recv() => {
        handle(msg);
    }
    else => {}
}

第一段没消息就立刻往下走；第二段只要接收分支还启用，就会等。

七、公平性

7.1 Go：伪随机

两路都有消息时：

select {
case msg := <-ch1:
    handle1(msg)
case msg := <-ch2:
    handle2(msg)
}

Go 规范要求在所有就绪的通信操作里做伪随机选择。我实测 1000 次两路都就绪的 select：ch1=509、ch2=491，接近 50/50。

7.2 Tokio：默认随机检查顺序

loop {
    tokio::select! {
        Some(msg) = rx1.recv() => handle1(msg),
        Some(msg) = rx2.recv() => handle2(msg),
        else => break,
    }
}

默认情况下 select! 会随机化分支检查顺序，避免某个分支在循环里永远被优先。

但随机不等于公平调度。 它不保证两边各处理一半，也不保证某个分支在固定时间内一定被处理。

7.3 biased 模式

tokio::select! {
    biased;
    _ = shutdown.cancelled() => {
        println!("shutdown");
    }
    Some(msg) = rx.recv() => {
        handle(msg);
    }
}

加 biased; 后按源码顺序轮询分支。适合「关闭信号优先」这类场景。

代价是：如果第一个分支永远就绪，后面的分支可能长期得不到检查。公平性责任回到开发者身上。

Go 没有对应的 biased 语法。

八、未选中分支的命运

这是两种 select 最本质的区别，也是最容易被忽略的。

8.1 Go：只执行选中的通信操作

select {
case msg := <-ch1:
    handle1(msg)
case msg := <-ch2:
    handle2(msg)
}

选中 ch1 后，这次 select 就结束了。ch2 里的消息不会消失，仍留在 channel 里等下次接收。

8.2 Rust：未选中的 Future 被 drop

tokio::select! {
    result = operation_a() => {
        handle_a(result);
    }
    result = operation_b() => {
        handle_b(result);
    }
}

某个分支完成时，其他分支的 Future 会被丢弃。

我写了个带 Drop 的 Future 实测：

tokio::select! {
    _ = async { let _g = DropGuard("branch_a"); sleep(200ms).await; } => {
        println!("branch a done");
    }
    _ = async { let _g = DropGuard("branch_b"); sleep(10ms).await; } => {
        println!("branch b done");
    }
}

输出：

  [drop] branch_b
  [drop] branch_a
  branch b done

branch_b 先完成（10ms），先被 drop（已完成的 Future 也照样 drop）；branch_a 的 Future 被取消并 drop。

所以 Rust 的 select! 不只是「选结果」，还隐含「取消其他计算」。

对应到 chan 的类比：Go 里没被选中的消息留在 channel；Rust 里没被选中的 Future 被销毁。如果你的 Future 在被 drop 时需要清理（关连接、写日志），得靠 Drop 保证，不能指望它「继续跑完」。

这跟第四节说的取消语义是同一件事的两面。

九、开销

9.1 Go 的 Goroutine

有独立栈，初始很小（2KB 量级），按需增长。

我实测创建 10 万个阻塞 Goroutine：

goroutine: before=1 now=100001, heap=58.7 MB

约 60MB / 10 万 ≈ 每个 Goroutine 600 字节量级（g 结构体 + 初始栈，不含后续增长）。

9.2 Rust 的 Future

没有独立栈。Future 的大小 = 编译器生成的状态机大小，编译期确定。

println!("{}", std::mem::size_of_val(&async { 42 }));

我实测了几个：

async { 42 }            = 1 bytes
tiny()                  = 1 bytes
with_state()（1KB 局部） = 1144 bytes
Pin<Box<dyn Future>>    = 16 bytes

一个不保存任何跨 .await 状态的 Future 只有 1 字节；而带 1KB 局部变量跨 .await 的那个是 1144 字节——正好对上「状态都内联在 Future 里」。

这个大小永远是编译期确定的固定值，分配多少一目了然。代价是：当 Future 特别大时（比如深嵌套的 async 函数），用 clippy 的 large_futures lint 能发现，通常用 Box::pin 装箱解决。

9.3 对比

GoRust
栈每个 Goroutine 独立栈，动态增长无独立栈，状态内联在 Future 里
单个开销约几百字节起（含栈）由状态机大小决定，编译期可知
增长方式栈复制（会移动栈上对象）不需要，大小固定
数量上限百万级常见取决于内存与 Future 大小

这里有个值得注意的连锁反应：Go 的栈会复制、会移动，所以栈上的对象地址不稳定——runtime 会在栈增长时更新指向它的指针。这也是 Go 不需要 Pin 的原因。

而 Rust 的 Future 地址必须稳定（状态机可能自引用），所以才需要 Pin 来保证「固定住之后不再移动」。Pin 存在的前提，正是 Rust 不允许运行时帮你悄悄搬动栈上的值。

十、怎么选

不按「哪个性能好」选，按任务形态选。

用 Go 更顺手的场景：

  • 大量互相独立的网络请求 / 任务编排；
  • 团队对并发模型熟悉度参差，希望统一一处写法；
  • 需要快速迭代，不想纠结运行时选型与生命周期标注；
  • 长同步计算和异步逻辑混在一起，靠 runtime 抢占兜底。

用 Rust 更顺手的场景：

  • 需要极致的单任务开销与可预测的内存布局；
  • 并发安全需要编译期保证（Send/Sync）；
  • 要和已有 C/C++ 生态、底层内存操作紧密结合；
  • 需要精确控制取消时机与清理顺序。

几条实践中摸出来的判断：

  1. 别在 async fn 里塞长同步计算。 这在 Rust 里是硬伤，Go 里只是「不太优雅」。
  2. Go 的 context 必须传下去。 不传就等于没有取消。
  3. Rust 的取消是 drop，不是信号。 需要异步清理就设计 shutdown()，别指望 Drop。
  4. select! 会取消其他分支。 写的时候要清楚这点，尤其是分支里有副作用时。
  5. 别拿 select 的 default 和 else 互相翻译。 语义根本不同。

Rust 与 Go 的错误处理与故障恢复

2026-10-25
:: tags:  #Error Handling  #Go  #Reliability  #Rust

这篇比起比较 Result 和 error 的语法，我更想聊后者背后的问题：一门语言怎么表达失败、怎么传播失败、谁来决策，以及系统在部分组件挂掉之后还能不能继续跑。

两种语言的倾向差异很明显：

  • Rust 倾向于把失败编码进类型系统，让调用者明确面对失败的可能性。
  • Go 倾向于把错误当普通返回值，让调用者用显式分支决定怎么处理。

两种都强调显式，但类型系统、传播机制、异常策略和资源管理的实现方式差别很大。

一、错误处理和故障恢复不是一回事

这是整篇的起点。

假设一个 Agent 任务要经过：

   │
   ▼

现在 LLM 调用失败了。系统至少要回答四个问题：

  1. 怎么表示这个错误？
  2. 怎么把它传给调用者？
  3. 谁来决定接下来怎么办？
  4. 系统能不能恢复到一个有效状态？

这四个问题对应四个层次：

层次关注的问题典型机制

这行代码表达的是「加载配置可能失败，调用者要处理这种可能」。

但它没有规定：

  • 要不要重试；
  • 要不要用默认配置；
  • 要不要终止程序；
  • 要不要通知管理员；
  • 要不要回滚已经执行的操作。

语言提供的是表达和传播机制，业务系统还得自己定义处理策略。这是理解两种设计的第一把钥匙。

二、两种语言的错误哲学

2.1 Rust：失败是类型的一部分

fn divide(a: i32, b: i32) -> Result<i32, String> {
    if b == 0 {
        return Err("division by zero".to_string());
    }
    Ok(a / b)
}

Result 就是个枚举：

enum Result<T, E> {
    Ok(T),
    Err(E),
}
Result<i32, String>
       │
       ├── Ok(i32)
       │
       └── Err(String)

在安全 Rust 里，你不能把 Result<i32, String> 直接当 i32 用，必须先处理或明确提取：

match divide(10, 2) {
    Ok(value) => println!("{value}"),
    Err(error) => println!("error: {error}"),
}

这里的倾向是：函数签名会明确暴露它可能发生的、通过返回值表达的失败。

但要注意，这不等于 Rust 能保证业务流程的失败都被妥善恢复。你完全可以这么写：

let result = divide(10, 0);
println!("{result:?}");

它把返回值消费掉了，但没做任何有意义的恢复。Rust 约束的是类型和控制流，不是业务策略。

2.2 Go：错误是普通返回值

func Divide(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("division by zero")
    }
    return a / b, nil
}
value, err := Divide(10, 2)
if err != nil {
    return err
}
fmt.Println(value)

error 是个接口：

type error interface {
    Error() string
}

所以任何类型都能实现它：

type ValidationError struct {
    Field string
    Msg   string
}

func (e *ValidationError) Error() string {
    return e.Field + ": " + e.Msg
}

和 Rust 的关键区别：Rust 把成功和失败放进同一个枚举值，Go 把它们拆成两个返回值。

这不代表 Go 的错误没有类型——自定义错误类型、错误接口、错误链一样能表达丰富信息。区别只在建模方式。

2.3 真正的区别

维度RustGo
典型返回类型Result<T, E>(T, error)
失败怎么表达枚举的 Err 分支error 接口值，nil 表示无错
忽略失败会怎样编译警告（unused_must_use），可以显式忽略编译器完全不管，只能靠 linter
传播方式?return err
常用错误类型枚举、自定义结构体、trait object自定义类型、接口、错误链
错误匹配match、matches!errors.Is、errors.As、类型断言

资源清理所有权 + RAII / Dropdefer、显式 close、GC

这里必须纠正一个常见误解：「Rust 强制你处理 Result」。

不是的。Rust 给 Result 标了 #[must_use]，忽略它只是警告：

fn returns_result() -> Result<(), ()> { Ok(()) }

fn main() {
    returns_result();   // warning: unused `Result` that must be used
}

我实测过：能编译、能跑，只有一个 warning。而且加个 let _ = returns_result(); 就连 warning 都没了。

真正的差异在于默认行为的倾向：

  • Rust：忽略 → 有噪音（warning），逼你至少承认一下。
  • Go：忽略 err → 世界安静，什么都不说。

Rust 强的地方不是「自动处理错误」，而是在类型层面让失败路径无法被无意识地当成成功值使用。

三、错误传播：? 与 return err

Handler
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
数据库

数据库访问失败，我们希望底层返回错误、中间层决定是否转换、最上层决定怎么向用户反馈。

3.1 Rust 的 ?

use std::fs;
use std::io;

fn load_config() -> Result<String, io::Error> {
    let content = fs::read_to_string("config.toml")?;
    Ok(content)
}

fn initialize() -> Result<(), io::Error> {
    let config = load_config()?;
    println!("{config}");
    Ok(())
}

let config = load_config()?; 大致等价于：

let config = match load_config() {
    Ok(value) => value,
    Err(error) => return Err(error.into()),
};

（简化展开，实际走 Try trait。）

? 的语义就两条：

  • 成功 → 取出值继续；
  • 失败 → 把错误转换成当前函数能返回的类型，提前返回。

第二条很容易被忽略：? 不是无条件原样返回错误。

fn read_data() -> Result<String, AppError> {
    let content = std::fs::read_to_string("config.toml")?;
    Ok(content)
}

这里能编过，前提是 AppError: From<std::io::Error>。否则报错。

这个机制允许你在底层保留具体错误，到上层再逐步归一化成应用错误。

3.2 Go 的显式检查

func LoadConfig() (string, error) {
    content, err := os.ReadFile("config.toml")
    if err != nil {
        return "", err
    }
    return string(content), nil
}

func Initialize() error {
    config, err := LoadConfig()
    if err != nil {
        return err
    }
    fmt.Println(config)
    return nil
}

每一层都写着：

if err != nil {
    return err
}

看起来啰嗦，但好处是每个检查点都能插入局部逻辑：

config, err := LoadConfig()
if err != nil {
    metrics.ConfigLoadFailure.Inc()
    return fmt.Errorf("initialize service: %w", err)
}

%w 是关键——它保留底层错误链，让上层还能用 errors.Is / errors.As 回溯。

Rust 用 map_err 做同样的事：

let content = std::fs::read_to_string("config.toml")
    .map_err(|err| AppError::ConfigLoad(err))?;

3.3 两种传播的真正差异

Rust 的 ? 把传播压缩成语言级语法，正常路径干净。

Go 把检查留在普通控制流里，每一层都容易插东西。

没有绝对优劣。但要说一句：Rust 不是不能显式处理错误，Go 也不是不能封装传播。两种风格两边都能写，只是默认写法的手感不同。

四、错误类型设计

这块我觉得最值得细看。

假设在写一个 Agent Runtime，失败原因包括：

  • 参数不合法；
  • LLM 服务不可用；
  • 工具调用失败；
  • 任务超时；
  • 任务被取消；
  • 数据库写入失败；
  • 内部状态不一致。

4.1 Rust：用枚举描述已知类别

use std::time::Duration;

#[derive(Debug)]
enum AgentError {
    InvalidInput(String),
    LlmUnavailable,
    ToolFailed(String),
    Timeout(Duration),
    Cancelled,
    Storage(String),
}

枚举描述了系统认可的一组错误类别，调用者可以精确匹配：

fn handle_error(error: AgentError) {
    match error {
        AgentError::InvalidInput(message) => {
            eprintln!("invalid input: {message}");
        }
        AgentError::LlmUnavailable => {
            eprintln!("LLM unavailable");
        }
        AgentError::ToolFailed(message) => {
            eprintln!("tool failed: {message}");
        }
        AgentError::Timeout(duration) => {
            eprintln!("timed out after {duration:?}");
        }
        AgentError::Cancelled => {
            eprintln!("cancelled");
        }
        AgentError::Storage(message) => {
            eprintln!("storage error: {message}");
        }
    }
}

代价是耦合：每加一个类别，所有 match 都要改（除非用 _ 兜底，但那样就失去了穷尽性检查）。

缓解手段有的是：#[non_exhaustive]、Box<dyn Error>、分层错误类型。应用内部用枚举表示稳定的领域错误，通常是最优解。

4.2 Go：错误接口 + 错误链

type ErrorCode string

const (
    ErrInvalidInput   ErrorCode = "invalid_input"
    ErrLlmUnavailable ErrorCode = "llm_unavailable"
    ErrToolFailed     ErrorCode = "tool_failed"
    ErrTimeout        ErrorCode = "timeout"
)

type AgentError struct {
    Code    ErrorCode
    Message string
    Cause   error
}

func (e *AgentError) Error() string  { return e.Message }
func (e *AgentError) Unwrap() error  { return e.Cause }

三个字段各自负责一件事：

  • Code：稳定的错误类别，给程序判断用；
  • Message：给人看的描述；
  • Cause：底层原因，串成错误链。

调用者：

var agentErr *AgentError
if errors.As(err, &agentErr) {
    switch agentErr.Code {
    case ErrInvalidInput:
        // 拒绝请求
    case ErrLlmUnavailable:
        // 考虑重试或降级
    case ErrTimeout:
        // 执行超时策略
    }
}

errors.As 会沿 Unwrap() 逐层查找，所以哪怕错误被 fmt.Errorf("%w") 包了好几层，也能挖出目标类型。我实测过：

errors.As: true llm_unavailable
errors.Is(inner): true

errors.Is 同理，它走 Unwrap 链做相等比较。

Go 1.20 之后还有一个 errors.Join，用来把多个错误合成一个：

err := errors.Join(errA, errB)

它的 Unwrap() 返回 []error，errors.Is / errors.As 会遍历全部成员。我实测了一下：

a failed
b: inner b
Is(e1): true
Unwrap() []error 长度: 2

适合「多个子任务都失败了，我要一起报上去」的场景——这在并发 fan-out 里很常见。

一个容易踩的坑：errors.As 的第二个参数必须是指向「实现了 error 的类型」的指针。传值进去会直接 panic：

panic: errors: target must be a non-nil pointer

4.3 怎么选

我的判断是：

  • Rust：领域内部用清晰的枚举，跨模块或需要开放扩展的边界再上动态错误类型。
  • Go：内部模块用稳定的自定义错误类型，对外通过接口、错误码和错误链提供契约。

但别把这两条当铁律。Rust 一样可以 Box<dyn std::error::Error>，Go 一样可以定义封闭的错误类别。

真正的判断标准是：调用者需要知道多少信息？

  • 只需要知道成功与否 → 错误消息可能够了。
  • 需要决定要不要重试 → 错误类型必须携带可决策的信息。
  • 需要区分「用户输入错」和「基础设施挂」→ 这种区别必须出现在类型或分类里，不能靠解析字符串。

五、错误消息不能代替错误类型

这是生产代码里最常见的一类脆弱设计。

数据库返回：

connection refused

上层看到字符串，猜是数据库不可用。然后写成：

if strings.Contains(err.Error(), "connection refused") {
    retry()
}

Rust 里也一样会犯：

if error.to_string().contains("connection refused") {
    retry();
}

两种都不行。错误消息会随版本、库实现、操作系统、协议变化。 拿它当控制流条件，等于把稳定性押在别人的文案上。

正确做法是转换成稳定的类别：

enum RetryClass {
    Retryable,
    Permanent,
    Unknown,
}

fn classify_error(error: &AgentError) -> RetryClass {
    match error {
        AgentError::LlmUnavailable => RetryClass::Retryable,
        AgentError::InvalidInput(_) => RetryClass::Permanent,
        AgentError::ToolFailed(_) => RetryClass::Unknown,
        AgentError::Timeout(_) => RetryClass::Retryable,
        AgentError::Cancelled => RetryClass::Permanent,
        AgentError::Storage(_) => RetryClass::Unknown,
    }
}
Error
  │
  ▼
Error Classifier
  │
  ├── Retryable
  ├── Permanent
  ├── Cancelled
  ├── DeadlineExceeded
  └── Unknown

但分类只是决策输入，不是重试的充分条件。一个错误「可以重试」，还得问：

  • 当前任务还成立吗？
  • 剩余截止时间够吗？
  • 会不会重复产生副作用？
  • 下游是不是已经在过载？
  • 重试会不会放大故障？

六、panic 与 recover

前面聊的都是普通错误。两种语言都还有另一套失败机制：

Go 有 panic()，Rust 有 panic!()。看起来像，但不能等同。

6.1 Rust 的 panic

fn main() {
    let value = Some(42);
    println!("{}", value.unwrap());
}

unwrap() 遇到 None 就 panic。

panic 一般用于：

  • 不该发生的状态；
  • 违反程序假设；
  • 无法正常恢复的错误；
  • 断言失败。

区分标准其实很简单：可预期、需要向调用者报告的失败用 Result；违反程序不变量的才考虑 panic。

fn parse_port(input: &str) -> Result<u16, std::num::ParseIntError> {
    input.parse()
}

解析用户输入失败是完全正常的，不该因为用户手抖就 panic。

panic 的行为取决于策略：默认 unwind 会栈展开并跑析构；abort 直接终止进程。

即使展开，也不能保证所有资源都被恢复，更不能保证已发生的外部副作用被撤销。

6.2 Go 的 panic 与 recover

func parsePort(input string) (uint16, error) {
    value, err := strconv.ParseUint(input, 10, 16)
    if err != nil {
        return 0, err
    }
    return uint16(value), nil
}

这里用普通错误。

如果 panic("unexpected state")，就进入 panic 流程。recover() 可以在 defer 里捕获：

func runSafely() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("panic recovered: %v", r)
        }
    }()
    panic("unexpected failure")
}

但 recover 不是普通的错误传播机制。它处理的是 panic 引发的非局部控制流，而且只能在符合规则的 deferred 函数里生效。

更重要的一句：捕获 panic 不等于状态已经恢复。

出了 panic 的地方可能已经改了共享内存、发了外部请求、或者只完成了多步操作的一部分。recover 只是让控制流继续，不会回滚任何事。

场景RustGo
用户输入不合法Result::Errerror
文件不存在Result::Errerror
网络请求失败Result::Errerror
外部服务暂时不可用返回错误，上层决策返回错误，上层决策
内部不变量被破坏视情况 panic 或返回错误视情况 panic 或返回错误
插件发生意外 panic按边界和策略考虑隔离按边界和策略考虑 recover

最后一行最关键。不是所有 panic 都意味着内存坏了，但如果程序的不变量已经无法确认，那么「捕获异常继续跑」很可能把小问题放大成大问题。

对插件系统、脚本引擎、多租户任务执行器来说，故障隔离往往比盲目恢复更重要。

七、资源清理：Drop 与 defer

错误处理如果只管返回值不管资源，就是不完整的。

7.1 Rust 的 RAII

use std::fs::File;
use std::io::{self, Read};

fn read_file(path: &str) -> io::Result<String> {
    let mut file = File::open(path)?;
    let mut content = String::new();
    file.read_to_string(&mut content)?;
    Ok(content)
}

read_to_string 失败就提前返回，file 离开作用域时照样析构，文件句柄照样关闭。

这就是 RAII：资源清理绑在所有权和作用域上，而不是绑在控制流上。

但这不代表外部副作用能回滚。已经写进数据库的数据，不会因为 Rust 对象析构而消失。

7.2 Go 的 defer

func ReadFileContent(path string) ([]byte, error) {
    file, err := os.Open(path)
    if err != nil {
        return nil, err
    }
    defer file.Close()

    content, err := io.ReadAll(file)
    if err != nil {
        return nil, err
    }
    return content, nil
}

defer 会在函数返回时执行，包括所有错误返回路径。

三点注意：

  • defer 不等于事务回滚；
  • 进程被强杀时 defer 不保证执行；
  • 如果 Close() 本身可能失败且影响业务正确性，就不能无条件忽略。

Rust 有对称的问题：Drop 不能返回错误。需要报告错误的清理，得设计显式的 close() / commit()。

所以数据库事务这种必须显式收尾的东西，两边都不能交给通用清理机制：

开始事务
   │
   ▼
执行修改
   │
   ├── 失败 ──► 回滚
   │
   └── 成功 ──► 提交

提交还是回滚是业务决策，通用资源清理机制不可能替你猜。

八、异步里的错误传播

8.1 Result 与 Future 是两个层次

async fn fetch_data() -> Result<String, FetchError> {
    // 异步请求
    Ok("data".to_string())
}

这个函数返回 Future，Future 完成后的输出类型是 Result<String, FetchError>。

Future 的执行
      │
      ▼
Future 完成
      │
      ▼
Result<String, FetchError>
      │
      ├── Ok(data)
      └── Err(error)

要分清：「Future 有没有完成」是执行状态，「异步操作成不成功」是业务结果。

Result 不会让操作变异步，Future 也不会自动定义业务错误类型。

8.2 JoinHandle 的双层 Result

let handle = tokio::spawn(async {
    Err::<(), &str>("operation failed")
});
let result = handle.await;

handle.await 的类型是：

Result<Result<(), &str>, tokio::task::JoinError>

为什么两层？

外层 Result<_, JoinError>：任务本身有没有正常完成——panic 了？被取消了？

内层 Result<(), &str>：任务里的业务成功了吗？

JoinHandle.await
       │
       ▼
Result<业务结果, JoinError>
       │
       ├── Err(JoinError)
       │      └── 任务层面的失败
       │
       └── Ok(业务结果)
                 │
                 ▼
           Result<T, E>
                 │
                 ├── Ok(T)
                 └── Err(E)

这不是设计冗余。它把两种责任分开了：运行时报告任务执行状态，业务函数报告业务结果。

写 Agent Runtime 时这个区分特别有用：

  • 工具调用失败 → 业务错误；
  • 任务里 panic → 任务执行层故障；
  • 任务被主动取消 → 生命周期事件；
  • 工作线程被阻塞 → 调度和运行时问题。

这四种不该被压成同一个字符串。

8.3 Go 的 goroutine 不会把错误传回来

go func() {
    if err := doWork(); err != nil {
        log.Printf("worker failed: %v", err)
    }
}()

错误只在 goroutine 内部处理，启动它的函数收不到任何东西。

要传出去就得自己搭路：

resultCh := make(chan error, 1)
go func() {
    resultCh <- doWork()
}()
err := <-resultCh
if err != nil {
    return err
}

或者用 errgroup：

g, ctx := errgroup.WithContext(ctx)
g.Go(func() error { return doWork(ctx) })
if err := g.Wait(); err != nil {
    return err
}

两种语言在这点上是共通的：并发任务的错误必须有明确的传递路径，不会因为「是某个函数启动的」就自动回流。

区别只在接口形态：

  • Tokio：JoinHandle 返回双层 Result；
  • Go：channel、共享状态或 errgroup。

九、什么错误该重试

从这里开始，从语言机制进入系统设计。

假设一次 LLM 请求失败了。最简单的写法：

loop {
    match call_llm().await {
        Ok(result) => break result,
        Err(_) => continue,
    }
}

Go 也容易写成一样：

for {
    result, err := callLLM(ctx)
    if err == nil {
        return result, nil
    }
}

两段都是坑。服务持续不可用时就是无限重试，资源被持续烧掉。

所以「要不要重试」之外，还得问：

  1. 这个错误暂时可恢复吗？
  2. 重试会不会重复执行副作用？
  3. 最大重试几次？
  4. 有没有整体截止时间？
  5. 要不要退避？
  6. 要不要熔断？
  7. 服务过载时该不该直接拒绝新请求？

9.1 错误分类

类别例子典型处理
Validation参数不合法直接返回
Authentication凭证无效返回错误，必要时刷新凭证
RateLimited触发限流退避后重试，遵守服务端策略
Transient暂时性网络故障有界重试
Timeout操作超过期限根据操作状态决定是否重试
Cancelled主动取消停止继续执行
Permanent永久性业务失败终止当前操作
Internal内部状态异常记录诊断，必要时隔离任务

这只是个基础分类。实际要按具体协议和业务语义来定。

比如 HTTP 500 不代表重试一定有用（可能是确定性 bug）；HTTP 429 必须遵守服务端给的 Retry-After，不能自己想退避多少就多少。

9.2 重试必须有边界

生产级重试至少要这几样：

  • 最大尝试次数；
  • 指数退避；
  • 随机抖动；
  • 总体截止时间；
  • 取消检查；
  • 错误分类；
  • 幂等性保障。

指数退避：

d_n = min(d_max, d_0 × 2^n)

其中 d_0 是初始等待，n 是第几次重试，d_max 是等待上限。

实际还要加随机抖动，否则所有客户端会在同一时刻一起重试，形成「同步重试风暴」。

第一次失败：等待约 100ms
第二次失败：等待约 200ms
第三次失败：等待约 400ms
第四次失败：等待约 800ms

这些只是示例，不是推荐值。

9.3 重试不是回滚

这个原则比前面所有技巧都重要。

假设 Agent 通过工具向外部系统转账，请求发出后超时。可能是两种情况：

情况 A：请求没到达服务端  → 没转账
情况 B：服务端已完成转账  → 响应丢了

客户端看到的都是超时。

直接重试，情况 B 就变成重复转账。

所以重试之前必须确认两件事：操作是否幂等，以及能不能查到上一次操作的最终状态。

常见解法：

  • 幂等键；
  • 服务端去重；
  • 操作 ID；
  • 查询操作状态；
  • 事务；
  • 补偿机制。

这在支付、任务调度、工具调用、Agent 执行框架里都是必修课。

十、重试之外：检查点、补偿、隔离

假设一个任务分三步：

Task
 │
 ▼
Step A：读取数据
 │
 ▼
Step B：调用外部工具
 │
 ▼
Step C：保存结果

Step C 失败了。这时候不能只问「要不要整个重试」，得先看 Step A 和 Step B 做了什么、有没有副作用。

10.1 检查点恢复

保存任务执行状态：

Task State
   │
   ├── Step A: Completed
   ├── Step B: Completed
   └── Step C: Failed

恢复时从 Step C 继续，不重跑全部。

这要求系统明确持久化：

  • 已完成步骤；
  • 每步的输出；
  • 任务版本；
  • 当前状态；
  • 已执行的外部副作用；
  • 重试次数；
  • 恢复所需上下文。

10.2 补偿操作

有些操作没法回滚：

创建资源
   │
   ▼
发送通知
   │
   ▼
后续步骤失败

通知已经发出去，撤不回来。这时只能补偿：更新状态、发更正通知、或者转人工处理。

这类设计就是 Saga 模式在干的事。

10.3 隔离与熔断

某个下游工具连续失败，继续往里灌请求只会让情况更糟。这时候可以考虑：

  • 暂停对该工具的请求；
  • 限制并发；
  • 暂时拒绝任务；
  • 用降级实现；
  • 等健康检查恢复。

到这一步，讨论已经从「单个错误怎么处理」升级成「系统级故障治理」。

一句话区分：

错误传播负责告诉系统发生了什么；故障恢复负责决定系统接下来怎么做。

十二、一个完整例子

有界重试的外部请求。为了聚焦错误处理，省略 HTTP 配置、日志、指标、取消传播等生产细节。

12.1 Rust 版

use std::time::Duration;
use tokio::time::sleep;

#[derive(Debug)]
enum AppError {
    InvalidInput,
    TemporaryFailure,
    PermanentFailure,
}

async fn call_service() -> Result<String, AppError> {
    // 模拟一次外部调用
    Err(AppError::TemporaryFailure)
}

async fn execute_with_retry(max_attempts: usize) -> Result<String, AppError> {
    if max_attempts == 0 {
        return Err(AppError::InvalidInput);
    }

    for attempt in 0..max_attempts {
        match call_service().await {
            Ok(value) => return Ok(value),
            Err(AppError::TemporaryFailure) if attempt + 1 < max_attempts => {
                let delay = Duration::from_millis(100 * (1u64 << attempt.min(10)));
                sleep(delay).await;
            }
            Err(error) => return Err(error),
        }
    }

    Err(AppError::PermanentFailure)
}

几个设计点：

  1. 错误类别显式；
  2. 只对暂时性错误重试；
  3. 重试次数有上限；
  4. 退避等待本身是异步的（不阻塞线程）；
  5. 最终失败以 Err 返回。

实测跑一下：

retry result: Err(TemporaryFailure)

注意 sleep(delay).await 这一行：它让出执行权，其他任务可以继续跑。如果换成 std::thread::sleep，整个 worker 线程就被卡住了。

这只是教学示例。真实实现还要加随机抖动、总截止时间、取消令牌、重试预算和幂等控制。

12.2 Go 版

package main

import (
    "context"
    "errors"
    "fmt"
    "time"
)

var (
    ErrTemporary = errors.New("temporary failure")
    ErrPermanent = errors.New("permanent failure")
)

func callService(ctx context.Context) (string, error) {
    // 模拟一次外部调用
    return "", ErrTemporary
}

func executeWithRetry(ctx context.Context, maxAttempts int) (string, error) {
    if maxAttempts <= 0 {
        return "", errors.New("maxAttempts must be positive")
    }

    for attempt := 0; attempt < maxAttempts; attempt++ {
        value, err := callService(ctx)
        if err == nil {
            return value, nil
        }
        if !errors.Is(err, ErrTemporary) {
            return "", err
        }
        if attempt+1 == maxAttempts {
            return "", err
        }

        delay := 100 * time.Millisecond * time.Duration(1<<min(attempt, 10))
        timer := time.NewTimer(delay)
        select {
        case <-ctx.Done():
            if !timer.Stop() {
                select {
                case <-timer.C:
                default:
                }
            }
            return "", ctx.Err()
        case <-timer.C:
        }
    }

    return "", ErrPermanent
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    value, err := executeWithRetry(ctx, 3)
    if err != nil {
        fmt.Println("failed:", err)
        return
    }
    fmt.Println(value)
}

这里展示了：

  1. 用 error 返回失败；
  2. 用 errors.Is 判断类别；
  3. 用 context.Context 传播取消；
  4. 用 select 让退避等待也能被取消；
  5. 限制重试次数。

那个 timer.Stop() + 二次 select 的写法是 Go 的标准模式：如果 Stop 返回 false，说明 timer 已经触发，通道里可能还有值，要先排空再返回，否则会泄漏。

12.3 真正的差别

Rust：

match call_service().await {
    Ok(value) => return Ok(value),
    Err(error) => { /* 分类与处理 */ }
}

Go：

value, err := callService(ctx)
if err == nil {
    return value, nil
}

表面上一个用 Result 一个用 error。但两者真正的架构是一样的：

调用外部服务
      │
      ▼
获得成功或失败结果
      │
      ▼
判断错误类别
      │
      ▼
检查重试预算
      │
      ▼
等待退避时间
      │
      ▼
重新尝试或返回错误

决定系统可靠性的，不是 Result 和 error 哪个更漂亮，而是错误分类、重试预算、取消传播、幂等性和恢复策略有没有设计对。

十三、总结

七条：

  1. Rust 强调错误的类型化表达。 Result<T, E> 把成功和失败放进一个显式类型，配合 ?、match 和自定义错误类型，能建立清晰的传播链。
  2. Go 强调普通控制流里的显式检查。 (T, error) 加 if err != nil，灵活直接，也方便在每个点插入局部逻辑。
  3. Rust 的类型系统能约束形式，但保证不了业务正确。 调用者照样能 unwrap()，或者返回个错误却没有恢复策略。
  4. 两边的 panic 都不该代替日常错误返回。 可预期的失败用 Result / error；意外状态要先判断能不能安全恢复，而不是一律捕获后继续跑。
  5. 任务取消不等于外部操作回滚。 无论是 drop Future 还是 context 取消，都撤不回已经发出的请求和已提交的事务。
  6. 重试必须建立在分类、预算、幂等性之上。 不能因为出错了就盲目重跑。
  7. 故障恢复是系统设计问题，不是语言特性。 对 Agent Runtime 来说，真正重要的是让任务在失败、取消、超时和进程重启后，仍然有明确的状态和可预测的恢复行为。

一句话收尾：

Rust 和 Go 都提供了显式的错误传播机制，但生产系统的可靠性，最终取决于你怎么把错误类型、任务状态、重试策略、取消语义和恢复机制组合起来。

Rust 与 Go 的内存管理：GC、所有权与分配

2026-10-25
:: tags:  #GC  #Go  #Memory  #Rust

有个说法我觉得得先破掉：

Rust 不是「用所有权实现了一套没有 GC 的垃圾回收器」，而是从根上换了内存管理的模型。

Go 靠运行时的垃圾回收器，在执行过程中识别不可达对象并回收。Rust 靠所有权、借用、生命周期和确定性析构，在编译期约束内存的使用方式，运行时通过所有权转移、作用域结束和 Drop 来管理资源。

两者解决的是同一个大问题——怎么让程序安全地管理内存，又不要求开发者手动追踪每一块内存的释放时机——但路线完全不同。

这篇从内存管理的基本问题出发，讲到 Go GC 的工作原理、Rust 的所有权机制、循环引用、并发、性能，最后落到「一行代码到底会不会分配」这个最实际的问题上。

一、GC 到底解决什么问题

先不谈语言。C 里分配一块内存：

int *p = malloc(sizeof(int));
*p = 42;
free(p);

开发者要负责两件事：申请，以及在适当的时候释放。

什么叫适当的时候？看这段：

int *p = malloc(sizeof(int));
*p = 42;
int *q = p;
free(p);
printf("%d\n", *q);

p 和 q 指向同一块内存。释放 p 不会让 q 失效，于是 q 成了悬垂指针。

再看这段：

int *p = malloc(sizeof(int));
*p = 42;
p = NULL;

原来那块内存已经没有任何指针能访问，但我们没 free。这就是泄漏。

手动管理内存的核心风险：

问题原因后果
Use-after-free内存释放后仍在使用内存安全问题
Double-free同一块内存被释放多次内存破坏
Memory leak不再需要的内存没释放内存持续增长
Dangling pointer指针指向已失效对象非法访问
Data race多线程不安全地访问共享数据数据竞争、UB 或逻辑错误

这里要划一条边界：

GC 主要解决对象生命周期与内存回收，不自动解决并发安全问题。

Go 有 GC，多个 Goroutine 照样能同时改同一个对象造成数据竞争。Rust 的所有权系统也不只是管内存——它还通过借用规则约束引用，再配合 Send/Sync 支持线程安全。

二、Go 的路线：对象自由共享，靠可达性回收

package main

import "fmt"

type User struct {
    Name string
}

func main() {
    u := &User{Name: "Alice"}
    v := u
    fmt.Println(u.Name)
    fmt.Println(v.Name)
}

u 和 v 指向同一个 User。Go 不要求你在最后一次使用 u 之后手动释放它。

当程序不再需要这个对象，并且从 GC 根集合出发已经没有引用路径能到达它时，GC 会在后续回收过程中释放它的内存。

关键点在这：

Go 不需要知道「哪个变量是唯一所有者」，因为它用的是可达性分析，不是 Rust 那种单一所有权模型。

这让 Go 里构建共享对象、缓存、树、图、复杂对象关系都很自然。代价是运行时得干活：

  • 追踪对象之间的引用关系；
  • 判断对象是否可达；
  • 在合适时机执行回收；
  • 控制 GC 对 CPU、内存和延迟的影响。

GC 不是免费的。

三、标记-清除与写屏障

理解 Go 的 GC，从经典的 Mark-and-Sweep 开始。

       Root
         |
         v
      Object A
       /    \
      v      v
  Object B  Object C

  Object D
  Object E

假设从根集合能到 A、B、C，到不了 D、E。GC 通过可达性分析识别出哪些对象还活着。

Mark：标记存活对象

Root
 │
 ▼
Object A  [marked]
 ├── Object B  [marked]
 └── Object C  [marked]

D、E 不可达，没被标记。

Sweep：回收未标记对象

Object A  保留
Object B  保留
Object C  保留
Object D  可回收
Object E  可回收

这是最基本的模型。但 Go 的实际实现远比「停下来、遍历、清除」复杂：它用并发标记-清除，让应用在 GC 标记的同时继续跑。

并发就带来一个问题。

为什么需要写屏障

假设 GC 正在标记，同时程序修改了对象之间的引用：

原来是：  A ──► B
改成：    A ──► C

如果 GC 只在开始时观察一次关系，就会出错——可能把 C 当作不可达回收掉，而 A 还指着它。

写屏障就是干这个的：程序修改特定指针关系时，额外执行一些操作，让 GC 能正确维护可达性信息。

程序运行
   │
   ├── 创建和修改对象
   │
   ├── GC 触发
   │
   ├── 并发标记
   │      └── 结合写屏障维护对象关系
   │
   ├── 标记终止阶段
   │
   └── 清除不可达对象

实际实现还有别的阶段和优化，这是核心思路不是完整状态机。

Go 用的是混合写屏障（hybrid write barrier），具体实现在不同版本持续演进。参考 The Go GC Guide 和 Go 源码里的 GC 文档。

一句话总结这条路：Go 把内存管理成本放到运行时，换来程序不需要手动决定大多数对象何时释放。

四、GC 什么时候工作

这是个经常被误解的点：Go 的 GC 不是等内存耗尽才动。

它有自己的触发策略，会综合考虑堆内存增长、配置参数（GOGC、GOMEMLIMIT）、分配压力等因素。

func processRequest() {
    data := make([]byte, 1024*1024)
    _ = data
}

每次调用申请约 1 MiB 的底层存储（实际取决于编译器优化和逃逸分析）。频繁调用就会持续产生分配，其中一部分对象很快不可达。

但这里有个重要区别——三件事并不等价：

  1. 对象是否已经可以被回收；
  2. 对应的堆空间是否已经可以重新用于分配；
  3. 堆内存是否已经归还给操作系统。

所以观察 Go 程序内存时，不能只看某一刻的进程 RSS 就断定 GC 是否正常。

另外，Go 也不是所有数据都在堆上：

func add(a, b int) int {
    return a + b
}

这种函数通常不需要为返回值创建堆对象。GC 只管需要回收的堆对象，不是每个变量都被它追踪。

五、Rust 的路线：靠所有权，不靠追踪

struct User {
    name: String,
}

fn main() {
    let user = User {
        name: String::from("Alice"),
    };
    println!("{}", user.name);
}

user 离开作用域就被析构：

创建 user
    │
    ▼
使用 user
    │
    ▼
离开作用域
    │
    ▼
调用 Drop
    │
    ▼
释放 User 持有的资源

这里没有后台 GC 线程定期扫描对象是否可达。Rust 用所有权规则在编译时约束：

  • 哪个值拥有资源；
  • 什么时候所有权转移；
  • 哪些地方可以借用；
  • 借用能持续多久；
  • 哪些资源要在生命周期结束时清理。

Rust 把许多传统上需要运行时追踪的问题，转化成了编译期的静态约束。

但这不代表 Rust 不需要运行时内存管理。它仍然可以：

  • 在堆上分配内存；
  • 用 Box<T>、Vec<T>、String；
  • 用引用计数；
  • 用自定义分配器；
  • 通过 unsafe 实现底层数据结构。

Rust 没有默认的追踪式 GC，但它既不是不分配内存，也不是没有运行时成本。

六、所有权、借用、生命周期怎么配合

所有权解决「谁负责释放」

fn main() {
    let a = String::from("hello");
    let b = a;
    println!("{b}");
}

let b = a; 之后，String 的所有权从 a 转到 b，a 不能再用。

a ──► String
       │
       │ move
       ▼
b ──► String

为什么要这么设计？假设 Rust 允许两个变量都当所有者，那程序结束时两边都可能去释放同一块缓冲区。

注意关键点不是「Rust 只能有一个指针」——Rust 允许多个引用指向同一个值。关键是：对于普通拥有型值，所有权转移不会自动产生第二个独立的所有者。 真需要共享所有权，有 Rc/Arc。

借用与生命周期解决「引用能用多久」

fn main() {
    let r;
    {
        let value = String::from("hello");
        r = &value;
    }
    println!("{r}");
}

value 在内部作用域结束时销毁，r 还想在外面用它。编译器直接拒绝。

外部作用域
┌──────────────────────────┐
│ r                        │
│                          │
│  内部作用域              │
│  ┌──────────────────┐    │
│  │ value            │    │
│  └──────────────────┘    │
│        ▲                 │
│        │                 │
│        r 试图继续引用它   │
└──────────────────────────┘

生命周期标注不是「手动控制内存释放的命令」，而是描述引用约束的一种方式：

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

'a 不表示「编译器要分配一段名为 'a 的内存」，它表达的是：返回的引用不能比输入引用满足的共同生命周期约束更长。

生命周期本身通常不会成为运行时对象，也不会产生一个追踪引用的 GC。它主要参与编译器的静态分析。

两个容易搞混的点：

  • 生命周期不等于对象的实际存活时间，它是编译器检查引用有效性的约束；
  • 反过来，标注也不会让一个已经被销毁的对象复活。

三者组合起来

struct Buffer {
    data: Vec<u8>,
}

fn process() {
    let buffer = Buffer {
        data: vec![1, 2, 3],
    };
    let view = &buffer.data;
    println!("{view:?}");
}
机制负责什么
所有权谁负责管理资源
借用与生命周期引用能在什么范围内有效
Drop资源生命周期结束时怎么清理

不过要说清楚：Rust 的生命周期系统不是通用的内存回收算法。 它不会在运行时扫描堆、找不可达对象。它的作用是约束引用关系，让很多资源的清理时机能由所有权和作用域确定下来。

七、Arc 是不是一种小型 GC

Rust 没有默认的追踪式 GC，但提供了引用计数类型：

use std::sync::Arc;

fn main() {
    let a = Arc::new(String::from("hello"));
    let b = Arc::clone(&a);
    println!("{a}");
    println!("{b}");
}
a ──┐
    ├──► Arc 管理的对象
b ──┘

Arc 维护引用计数，计数归零时析构内部对象并释放分配。所以它确实提供了某种自动管理共享对象生命周期的机制。

但和 Go 的 GC 有根本区别。

区别一：Arc 依赖显式引用计数

每次 clone 增加强引用计数，每个 Arc 析构时减少。最后一个强引用消失，对象才被析构。

区别二：Arc 不追踪任意对象图的可达性

假设两个对象互相引用：

A ──► B
▲     │
└─────┘

如果两条边都是强 Arc，即使外部已经没有引用，内部计数还是非零，两个对象都释放不掉。这就是引用循环。

Go 的追踪式 GC 通常能回收这种对象图——只要整体从根集合不可达就行。

但这里也有个细节：如果 Go 对象仍然能从某个根到达，即使业务上已经不要了，GC 也不会自动知道。

GC 判断的是可达性，不是业务意义上的「还需不需要」。

Rust 怎么破环？

用 Weak<T>，它不增加强引用计数：

use std::sync::{Arc, Weak};

struct Node {
    parent: Weak<Node>,
}

（简化片段，完整树结构还得有子节点集合，并在创建时建立正确的引用关系。）

if let Some(node) = weak.upgrade() {
    // 对象仍然存活
}

对象已释放时 upgrade() 返回 None。

所以：

  • Arc<T> 适合共享所有权；
  • Weak<T> 适合「不应维持对象存活」的关联；
  • Rc<T> 是单线程版；
  • Rc<T> 也有对应的 Weak。

但引用计数不等于追踪式 GC：

判断依据
引用计数强引用数量
追踪式 GC从根集合出发的可达性

八、Drop 与 Finalizer

struct Resource {
    id: u64,
}

impl Drop for Resource {
    fn drop(&mut self) {
        println!("dropping {}", self.id);
    }
}

fn main() {
    let resource = Resource { id: 1 };
    println!("using resource");
}

resource 离开作用域就被析构。对普通的、没被遗忘的拥有型值，资源释放和所有权、作用域绑得很紧。

但也不保证总执行：

std::mem::forget(resource);

forget 消耗这个值，但不跑析构。所以 Rust 的安全抽象不能假定所有 Drop 一定执行。

Go 这边：

type Resource struct {
    ID int
}

如果一个对象只是普通堆对象，GC 不会因为它不可达就调用一个类 Rust Drop 的方法。Go 有 runtime.SetFinalizer，但终结器不是确定性析构机制，不适合承担必须及时执行的资源释放或业务逻辑。

文件、数据库连接这类，通常还是靠显式 Close()、defer 或专门的资源管理接口。

维度RustGo
普通资源释放通常由所有权和析构决定显式关闭 + GC 共同管理
Drop / FinalizerDrop 通常在值被析构时运行Finalizer 不保证及时执行
是否依赖后台追踪默认不依赖堆对象依赖 GC 回收

业务事务回滚需要显式实现同样需要显式实现

Rust 的确定性析构也有边界：进程被强杀、系统崩溃、用 abort 时，不能依赖普通析构完成清理。而且 Drop 不能撤销已经发生的外部副作用。

RAII 特别适合管文件句柄、锁、内存分配，但不能理解成自动回滚系统。

九、Rust 是不是一定比 Go 快

不能这么下结论。

Rust 没有默认追踪式 GC，确实不用承担同样的追踪回收工作。在分配量很大、对象生命周期短、延迟要求严格的程序里，避免追踪式 GC 有利于控制尾延迟。

但 Rust 也不是零成本。

Rust 仍然会分配堆内存

let data = Vec::<u8>::with_capacity(1024);

这里可能发生堆分配。分配器本身有成本，Vec 扩容要重新分配和复制，String 也可能重分配，Arc 要维护引用计数。锁、channel、异步任务、动态分发同样有开销。

没有 GC，不代表没有内存管理成本。

Go 也不是每个对象都在堆上

func sum(a, b int) int {
    return a + b
}

这里一般不需要创建堆对象。编译器会分析变量用法决定放哪。

所以：

Rust = 栈分配
Go   = 堆分配

这个说法是错的。

Go 的 GC 换来的是工程便利

type Cache struct {
    data map[string][]byte
}

缓存可以被多个组件持有。开发者要考虑并发安全、淘汰策略、内存占用，但一般不用手动算每个缓存条目的引用计数。

Rust 也能构建同样的缓存，但要先想清楚：谁拥有缓存、怎么借用、要不要 Arc、要不要 Mutex/RwLock、条目什么时候移除。

这些机制提供了明确的所有权和同步关系，但设计工作量更多。

比较两种语言要看完整系统，不能只盯着 GC。

十、延迟、内存占用，以及生命周期系统的边界

尾延迟

解析请求
   │
   ▼
创建任务对象
   │
   ▼
执行调度
   │
   ▼
调用工具
   │
   ▼

整个过程产生临时对象。Go 可能在分配积累到一定程度后触发 GC。

Rust 不会因为普通堆对象不可达就启动追踪式扫描，但仍受这些因素影响：

  • 分配器竞争；
  • 堆分配与释放成本；
  • 引用计数的原子操作；
  • 锁竞争；
  • 内存碎片；
  • 数据结构的局部性；
  • 异步任务和队列的开销。

所以不能这么推：

Rust 没有 GC
    ↓
Rust 的尾延迟必然更低

更准确的结论：Rust 避免了追踪式 GC 这一类运行时成本，但最终延迟还取决于分配行为、数据结构、调度、同步、I/O 和系统负载。

同样，Go 的 GC 也不是单纯的「性能损失」——它降低了内存管理的编程负担，很多业务场景下这是非常合理的工程选择。

为什么没有 GC 也会占很多内存

use std::collections::HashMap;
let mut cache: HashMap<String, Vec<u8>> = HashMap::new();

如果只往里插不删除，内存就会一直涨。Rust 没有 GC，但这个问题照样存在。

原因很简单：这些对象仍然被 cache 持有。从所有权角度看，它们仍是有效资源。Rust 不会擅自推断「这个缓存条目业务上已经没价值了，删了吧」。

你得自己定策略：什么时候淘汰、最大容量多少、要不要 TTL、按访问频率还是按时间、允不允许后台清理。

Go 一模一样：

var globalCache = make(map[string][]byte)

只要缓存还存着这些数据，GC 就认为对象可达。

GC 能回收不可达对象，但判断不了一个仍然可达的对象是否已经失去业务价值。

这也是为什么内存泄漏不是 GC 语言独有的问题。GC 语言照样会遇到：缓存无限增长、Goroutine 泄漏、订阅者没退出、channel 里积压、全局变量意外保留对象、闭包长期捕获不再需要的数据。

Rust 也会出现逻辑层面的泄漏，尤其是用引用计数、全局状态或故意泄漏资源时。

生命周期系统的边界

Rust 的所有权和生命周期能在安全 Rust 里静态排除很多内存错误，但不保证：

  • 不会发生逻辑内存泄漏；
  • 不会资源使用过度；
  • 不会死锁；
  • 不会算法错误；
  • 不会业务上的资源泄漏；
  • 不会因为 unsafe 出现内存安全问题。
use std::sync::Arc;
let value = Arc::new(42);
let cloned = Arc::clone(&value);

如果把 Arc 存进一个长期存活的全局结构，相关对象就一直活着。这是所有权关系的正常结果，不是编译器有问题。

unsafe 更要小心：用裸指针、手动管理初始化状态、实现自定义容器时，可能绕过部分静态保证。自己写一个类 Vec 的结构，得处理内存布局、分配释放、初始化状态、元素析构、指针有效性、别名规则、Send/Sync 的实现条件。这些不变量写错了，外围 API 再漂亮也可能有 UB。

所以 Rust 的优势是让安全抽象能建立在严格的静态约束之上，而不是让程序从此不需要内存管理设计。

十一、并发内存管理

Agent Runtime 有很多并发任务，每个任务都要维护状态、记录事件、调用工具、保存检查点、更新统计。这些会产生大量临时对象。

Go 的优势是对象能自然地在 Goroutine 之间传递和共享，GC 管堆内存，但数据竞争和同步还得自己处理：

var counter int
go func() { counter++ }()
go func() { counter++ }()

这里存在数据竞争，GC 不会解决它。

Rust 用类型系统约束线程间共享：

use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

let counter = Arc::new(AtomicUsize::new(0));
let a = Arc::clone(&counter);
let b = Arc::clone(&counter);

let t1 = std::thread::spawn(move || {
    a.fetch_add(1, Ordering::Relaxed);
});
let t2 = std::thread::spawn(move || {
    b.fetch_add(1, Ordering::Relaxed);
});
t1.join().unwrap();
t2.join().unwrap();
  • Arc 管共享所有权；
  • AtomicUsize 提供原子计数；
  • Ordering::Relaxed 保证这个计数操作本身是原子的，但不提供其他内存访问之间的同步顺序；
  • join 等两个线程结束。

这些原子操作不需要 GC 也能工作。Go 也有 sync/atomic、sync.Mutex、channel。

所以主要区别不是「Go 有 GC 所以不安全」：

  • Go 用 GC 管对象内存，通过同步原语和运行时检测工具帮助管理并发访问；
  • Rust 用所有权、借用、Send/Sync 与同步原语共同约束内存和线程安全。

两个体系都需要正确设计任务状态、共享数据和同步关系。

十二、Box、Rc、Arc 怎么选

想真正理解 Rust 为什么不用 GC，得先理解这几个类型的分工。

类型核心用途所有权模式特点
T普通值直接拥有通常按值存储
Box<T>堆分配单一所有者管理一块堆分配
Rc<T>单线程共享引用计数共享所有权，不保证线程安全
Arc<T>多线程共享原子引用计数能否跨线程仍取决于 T
Weak<T>非拥有式关联弱引用不增加强引用计数
&T只读借用不拥有受生命周期和借用规则约束
&mut T可变借用不拥有受独占可变借用规则约束

特别强调：Arc<T> 不意味着内部的 T 可以被任意多个线程同时修改。

use std::sync::{Arc, Mutex};
let value = Arc::new(Mutex::new(0));

Arc 解决共享所有权，Mutex 解决互斥访问——两个不同问题。只有 T 本身满足相应的 Send/Sync 条件，Arc<T> 才能满足跨线程使用要求。

Rust 的内存管理从来不是单靠生命周期标注，而是多种机制共同作用。

十三、内存生命周期 ≠ 业务对象生命周期

这个区别我觉得比前面所有技术细节都重要。

一个任务被创建，业务生命周期是：

Created
   │
   ▼
Ready
   │
   ▼
Running
   │
   ▼
Completed

业务状态可能要持久化，但内存里的结构体可能早就释放了：

数据库中的 Task 记录：仍然存在
内存中的 Task 对象：已经释放

这完全合理。

反过来也一样：任务在数据库里已经 Completed，但某个监控组件还持有内存对象——因为它正在读最终统计信息。也合理。

所以要区分四种生命周期：

生命周期代表什么
内存生命周期对象何时创建、持有、释放
任务生命周期任务何时创建、执行、完成、失败或取消
进程生命周期运行时何时启动和退出
持久化生命周期数据何时写入、保留、归档或删除

GC 只处理第一种，Rust 的所有权和析构也只处理第一种。

它们都不能单独保证任务执行正确、检查点一致或故障恢复成功。这对分布式系统尤其重要：内存对象被释放不等于业务任务被取消，业务任务完成也不意味着所有内存对象立即消失。

十四、一行代码怎么变成内存分配

从这里开始进入第二块：分配本身。

package main

type User struct {
    ID   int64
    Name string
}

func NewUser(id int64, name string) *User {
    u := User{
        ID:   id,
        Name: name,
    }
    return &u
}

NewUser 返回一个指向局部变量 u 的指针。C 里这行是错的——函数返回后栈帧就失效了。Go 却允许。

因为 Go 编译器会分析 u 的用法。如果它需要在函数返回后继续存在，编译器就把它放到堆上。

源代码
  │
  ▼
编译器分析
  │
  ├── 对象布局
  ├── 逃逸分析
  ├── 栈与堆分配决策
  └── 代码生成
          │
          ▼
运行时内存管理
  │
  ├── 栈空间
  ├── 堆分配器
  └── GC

这是概念图，不是精确执行顺序。

编译器还会做内联、死代码消除、寄存器分配。内联尤其重要：一个函数单独看可能有堆分配，被内联后分配可能被消除，或者变量留在调用者的栈上。

所以不能只看源码里的 &、new、make 就判断一定在堆上。

Rust 里写了 Box::new 也不绝对——编译器可能在不影响可观察行为的前提下消除某些分配。

十五、Go 逃逸分析到底分析什么

func f() *int {
    x := 42
    return &x
}

x 在哪？

很多人会直接回答「因为返回了 &x，所以 x 一定在堆上」。这作为直觉可以，但不够严谨。

更准确的说法：返回的指针可能在函数返回后继续被使用，所以编译器必须保证它指向的对象在需要时仍然有效。 在常见编译结果里，x 会被放到堆上。

编译器并不是逐个查找所有 & 然后机械决定，它分析指针和引用之间的流动关系，结合上下文和其他优化作决定。

我实测了几种写法，go build -gcflags="-m=2" 的输出很能说明问题。

返回指针 → 逃逸

./main.go:10:2: x escapes to heap in f:
./main.go:10:2: moved to heap: x

只在内部用 → 没有逃逸记录

func sum() int {
    x := 42
    return x + 1
}

编译器可能直接算出结果，连 x 都不保留。

取地址但只在内部用 → 也不逃逸

func readValue() int {
    x := 42
    p := &x
    return *p
}

输出里根本没有 x 的逃逸记录。虽然写了 &x，但 p 只在当前函数用，编译器有机会把 x 留在栈上，甚至把指针和内存访问一起消掉。

所以要分清四件事：

  1. 源码里是否声明了变量；
  2. 编译器是否保留这个变量；
  3. 这个变量是否需要具体的内存位置；
  4. 如果需要，是否分配在堆上。

这四件事并不等价。

十六、new、make、取地址为什么不等同于堆分配

这是分析 Go 分配时最实用的一部分，我全部实测了。

new 不保证堆分配

func newLocal() {
    p := new(int)
    *p = 10
    println(*p)
}

实测输出：

./main.go:46:10: new(int) does not escape

new(int) 得到的是指向零值 int 的指针。但编译器能证明它只在本函数用，就有机会放栈上，甚至消除分配。

new 表示「创建并返回指针」，不表示「强制堆分配」。

make 也不一定

func makeValues() []int {
    values := make([]int, 3)
    values[0] = 10
    return values
}

因为切片被返回，底层数组要在函数外继续存在：

./main.go:53:16: make([]int, 3) escapes to heap in makeValues:

但如果切片不外传，比如只取第一个元素返回：

func f() int {
    values := make([]int, 3)
    values[0] = 10
    return values[0]
}

实测里这条是 does not escape——底层数组可以留在栈上。

切片本身只是个描述符：

slice
 ├── data pointer
 ├── length
 └── capacity

接口值也不一定导致分配

func printValue(v any) {
    println(v.(int))
}

调用 printValue(42) 时，实测：

./main.go:59:17: v does not escape

接口值需要保存动态类型信息和数据，但具体表示和是否需要额外分配，取决于值的类型、大小、用法和编译器优化。

所以「传入接口就会分配」也是过于绝对的结论。

一个有意思的现象

func cacheExample() {
    m := make(map[string][]byte)
    m["k"] = make([]byte, 128)
    _ = m
}

实测：

./main.go:65:11: make(map[string][]byte) does not escape
./main.go:66:15: make([]byte, 128) escapes to heap

map 本身没逃逸（因为整个函数里它就没出去），但塞进去的 128 字节切片逃逸了——map 的底层存储必须能在增长时重新分配，所以数据会被放到堆上。

这类细节只能实测，光看源码猜不出来。

十七、怎么亲自观察逃逸分析

这一步别省。逃逸分析不能只靠理论推断。

go build -gcflags="-m=2" .

输出编译器优化诊断，包括内联和逃逸信息。你可能会看到：

u escapes to heap
moved to heap: u

两点注意：

  1. 诊断内容会随 Go 版本、优化和调用上下文变化；
  2. 有诊断不代表最终机器码里确实有一次堆分配。

还可以用基准测试看实际分配统计：

go test -bench=. -benchmem

输出格式类似：

BenchmarkExample-8    1000000    120 ns/op    32 B/op    1 allocs/op

（这是格式示例，不是某个真实程序的结果。）

  • ns/op：每次操作耗时；
  • B/op：每次操作平均分配字节数；
  • allocs/op：每次操作平均分配次数。

对 Agent Runtime 这种服务，这些指标能帮你定位高频路径上的分配压力。

十八、Rust 是不是「默认栈分配」

很多人把 Rust 总结成「默认栈分配，Go 默认堆分配」。这个说法不准确。

Rust 没有一条简单规则规定所有普通变量都在栈上，也没有一条规则规定所有拥有型对象都在堆上。更准确的理解是：

  • 局部值通常由编译器根据使用方式安排存储；
  • Box<T> 等类型通过分配器管理堆内存；
  • Vec<T> 和 String 通常在堆上管理动态数据；
  • 编译器可能优化掉不必要的存储和分配；
  • 对象在哪，不能仅凭类型名字判断。
struct User {
    id: u64,
}

fn main() {
    let user = User { id: 42 };
    println!("{}", user.id);
}

user 是普通值，不需要像 Box<User> 那样通过堆分配器管理主体存储。常见情况下作为局部值存储；优化后编译器甚至可能把字段直接放寄存器里。

所以即使 Rust 没有默认追踪式 GC，也不能认为所有值都一定拥有可观察的栈内存位置。

十九、Box 与 Vec

Box：把值放堆上，但不引入 GC

fn main() {
    let user = Box::new(42);
    println!("{user}");
}
栈上的 Box<i32>
       │
       ▼
堆上的 i32

要区分两个对象：

  1. Box 这个拥有型指针值；
  2. Box 管理的堆分配里的 T。

Box 的指针值本身通常很小，被管理的 T 在堆上。这只是概念模型，编译器仍可能优化掉不影响可观察行为的操作。

Box 最常见的用途是构造递归类型：

enum List {
    Cons(i32, Box<List>),
    Nil,
}

不用间接存储，递归类型的大小无法有限确定。Box<List> 提供了一个已知大小的间接引用，让整个 List 有有限大小。这和 GC 无关，只是让数据结构能在堆上组织。

Box 与 Go 指针的区别

p := &User{ID: 42}
let p = Box::new(User { id: 42 });

看起来都是拿到指向数据的指针，语义不同：

  • Go 的 *User 是普通指针，不表达独占所有权；
  • Rust 的 Box<User> 表达对所管理值的所有权。

所以 Rust 能在类型系统里追踪所有权转移：

let a = Box::new(42);
let b = a;
// a 不再拥有该 Box

b 析构时负责释放资源。Go 的普通指针不会在类型系统里提供同样的独占语义——当然 Go 可以通过 API 约定和封装建立所有权规则，只是这些规则不由 *T 本身表达。

Vec：栈上的管理对象 + 堆上的元素缓冲区

let mut values = Vec::with_capacity(4);
values.push(10);
values.push(20);
values.push(30);
Vec<i32>
 ├── pointer ──────────────┐
 ├── length = 3            │
 └── capacity = 4          │
                           ▼
                       堆分配
                       ┌─────────┐
                       │   10    │
                       ├─────────┤
                       │   20    │
                       ├─────────┤
                       │   30    │
                       ├─────────┤
                       │ 未初始化 │
                       └─────────┘

图里「未初始化」只是为了说明 len 和 capacity 的差别：剩余容量不代表那里已经构造了可用的 T。

Vec 的堆内存不由 GC 决定何时释放，而是由 Vec 的所有权和析构逻辑管理。

扩容时：

let mut values = Vec::with_capacity(4);
for i in 0..1000 {
    values.push(i);
}

容量不足就重新分配，可能移动元素数据。这意味着：

  • Vec 自己的管理信息可以留在原位；
  • 但元素缓冲区可能换地址。

这正好接上 Pin 那一篇：固定外层对象的地址，不等于固定它拥有的所有堆分配。

Go 切片 vs Rust Vec

Go slice        Rust Vec
 ├── data         ├── pointer
 ├── len          ├── len
 └── cap          └── capacity

结构相似，所有权语义不同：

  • Go 切片是对底层数组的描述，多个切片可以共享同一个数组；
  • Rust Vec<T> 拥有底层缓冲区。

Rust 的 &[T]、&mut [T] 才更接近 Go 的切片视图，但它们受借用规则约束。这直接影响数据共享、缓冲区复用和零拷贝设计。

二十、对象布局：Rust 自动重排，Go 要手动重排

这块的实测结果我觉得最有意思。

struct Example {
    a: u8,
    b: u64,
    c: u8,
}

直觉是 1 + 8 + 1 = 10 字节。实际不是。

Rust 的情况（实测）

repr(Rust): size = 16, align = 8
repr(C)   : size = 24, align = 8

repr(Rust) 的字段偏移：b = 0, a = 8, c = 9

默认 repr(Rust) 下编译器重排了字段：把 u64 放前面，两个 u8 紧凑排在后面，总大小 16。

加上 #[repr(C)] 后必须保持声明顺序，于是 a 占 1 字节 + 7 字节填充 + b 8 字节 + c 1 字节 + 7 字节尾部填充 = 24。

Go 的情况（实测）

type Example struct {
    A byte
    B uint64
    C byte
}
size=24 align=8
  A offset=0  B offset=8  C offset=16

Go 不重排，严格按声明序，结果和 Rust 的 repr(C) 一样是 24。

手动把字段从大到小排：

type Packed struct {
    B uint64
    A byte
    C byte
}
size=16 align=8
  B offset=0  A offset=8  C offset=9

16 —— 和 Rust 的默认布局完全一致。

这个对照挺能说明问题：

Rust 的 repr(Rust) 自动做了 Go 需要手动做的事；而 Rust 的 repr(C) 才等价于 Go 的默认行为。

所以「Go 结构体布局更省内存」或「Rust 布局更紧凑」都是错的——取决于你有没有加 repr(C)、有没有手动排字段。

怎么观察

Rust：

use std::mem::{align_of, size_of};

fn main() {
    println!("size = {}", size_of::<Example>());
    println!("align = {}", align_of::<Example>());
}

Go：

fmt.Println("size:", unsafe.Sizeof(Example{}))
fmt.Println("align:", unsafe.Alignof(Example{}))
fmt.Println("A offset:", unsafe.Offsetof(Example{}.A))
fmt.Println("B offset:", unsafe.Offsetof(Example{}.B))
fmt.Println("C offset:", unsafe.Offsetof(Example{}.C))

注意：size_of::<T>() 只告诉你总大小，不告诉你每个字段的偏移。默认 Rust 布局下字段顺序不被语言保证，不能靠推断。

Go 这边 unsafe.Offsetof 是能用的，因为 Go 保证字段按声明序排列。

布局优化的前提

调整字段顺序确实能减少填充，但不能因为「少占几个字节」就断定程序会更快。还得看：

  • 缓存局部性；
  • 数据访问模式；
  • 分配数量；
  • 结构体是否被复制；
  • 并发访问模式；
  • ABI 和序列化兼容性。

先测量，再调整。

二十一、分配器

Rust 侧

let value = Box::new(42);
let values = Vec::<u64>::with_capacity(1000);

两者都可能向堆分配器请求内存：

Box / Vec
    │
    ▼
Rust 标准库的分配接口
    │
    ▼
当前配置的全局分配器
    │
    ▼
底层分配实现
    │
    ▼
操作系统提供的虚拟内存

注意实际分配可能被优化掉，或被分配器内部缓存复用。这张图描述的是典型的资源管理路径，不是每次 Box::new 都触发一次系统调用。

分配器要处理：按大小和对齐分配、释放、管理不同大小的块、适当时候向 OS 要更多内存、适当时候归还、处理碎片和内部元数据。

操作系统通常不会为每个小对象单独执行系统调用——分配器管理较大的区域，再从中划分小块。

Rust 允许自定义全局分配器，但自定义不意味着更快。不同分配器在小对象速度、多线程竞争、碎片、峰值内存、大块分配、归还策略上表现不同，而且换全局分配器会影响整个程序和所有依赖库。

先确认分配真是瓶颈，再在真实负载下比较。

Go 侧

Go 运行时也有自己的堆分配器，为高效处理大量小对象，它管理不同大小类别的内存块，并尽量复用已取得的内存。

Go 程序
   │
   ▼
Go runtime allocator
   │
   ├── 小对象分配路径
   ├── 较大对象分配路径
   ├── 堆空间管理
   └── 与 GC 协同

具体路径取决于对象大小、对齐、运行时实现和版本。但肯定不是「每次 new 就调一次操作系统」。

为什么 Go 特别关注分配速率

假设服务每秒 10 万请求，每个请求平均分配 20 个小对象：

100,000 requests/sec × 20 allocations/request
= 2,000,000 allocations/sec

（假设数字，用来说明量级。）

即使每个对象很小，持续产生也可能增加：分配器工作量、GC 要处理的对象数、扫描工作、CPU 使用率、内存占用。

所以 Go 性能优化里常关注 allocs/op、B/op、alloc_space、alloc_objects。

但也不能因为分配次数多就断定代码有问题。某些分配是合理的，硬优化可能让代码难维护。测真实负载，再决定要不要减。

二十二、分配成本到底差在哪

假设两边都要创建任务对象：

type Task struct {
    ID    string
    State int
}
struct Task {
    id: String,
    state: i32,
}

如果两边都要把任务放堆上，那就都得承担某种形式的内存分配成本。区别主要在：

  1. 对象怎么分配；
  2. 生命周期怎么管理；
  3. 何时释放；
  4. 是否需要运行时追踪；
  5. 是否存在引用计数；
  6. 对象之间怎么共享；
  7. 分配器怎么复用内存；
  8. 编译器怎么优化。
Go：                        Rust：
分配对象                     分配对象
   │                            │
   ▼                            ▼
运行时管理                   某个值拥有资源
   │                            │
   ▼                            ▼
对象变得不可达              所有权转移或继续使用
   │                            │
   ▼                            ▼
GC 后续回收                 资源生命周期结束
                                │
                                ▼
                            析构与释放

这不意味着 Rust 每次释放都没成本，也不意味着 Go 的 GC 一定在某个固定时间点回收对象。两者都要管理分配器和内存空间。

主要差别是默认的生命周期管理模型不同。

二十三、对 Agent Runtime 来说该减少什么

三个层次。

第一层：减少不必要的对象分配

READY
  │
  ▼
LEASED
  │
  ▼
RUNNING
  │
  ▼
COMPLETED

如果每次状态变化都构造大量临时对象，分配成本会累积。

Go 用基准测试、逃逸分析、CPU/内存剖析找热点；Rust 用分配剖析、基准测试、数据结构分析找热点。

但别为了省几个小对象就把代码改成复杂的手动内存池。

第二层：控制对象生命周期

事件流和任务上下文可能比单次执行活得更久。某个事件缓存了很久，相关对象也就长期占内存。

  • Go：长期引用会阻止 GC 回收；
  • Rust：长期持有 Arc 或放全局结构里，资源同样持续存活。

要控制：缓存大小、事件保留量、任务历史、临时上下文的释放、长期订阅、不再使用的共享引用。

这一层是业务生命周期管理，不只是语言层面的内存管理。

第三层：降低大规模并发下的分配与同步成本

多个任务同时更新共享状态时：

Go 可能需要互斥锁、channel、对象复用、有界队列、GC 指标监控。

Rust 可能需要所有权转移、借用、Arc、锁、有界 channel、缓冲区复用。

两边都能构建高效系统。真正的差别要通过具体负载衡量。

优化重点逃逸分析、减少分配、控制 GC 工作量数据结构设计、减少分配、优化所有权与共享
内存安全GC 不解决并发与业务资源问题安全 Rust 提供较强静态约束，unsafe 仍需自查

最后一个认识我想强调：

Go 不是把内存管理交给 GC 之后就完事，Rust 也不是没有 GC 就自动拿到最优性能。

Go 要关注分配速率、逃逸、GC 工作量和长期引用。Rust 要关注所有权结构、堆分配、引用计数、数据布局和资源生命周期。

真正值得问的问题不是「这段代码会不会分配内存」，而是：

为什么它会分配？分配在哪里？谁负责释放？对象为什么还活着？这部分成本能不能通过编译器优化或数据结构设计消掉？

这才是分析系统内存性能的核心能力。
