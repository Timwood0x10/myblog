深入理解 Go / Rust / C++ 泛型

2026-10-25
:: tags:  #CPP  #Go  #Rust  #generic

从语言设计 → 类型系统 → 编译器实现 → 机器码 → 内存布局 → 性能与工程实践这几个层次，系统地比较 Go、Rust 和 C++ 的泛型

先给出一个最重要的结论：

Go 的泛型采用 GC Shape Stenciling（基于 GC 形状的代码生成）与 Dictionary（字典）相结合的实现方式；Rust 的泛型主要采用 Monomorphization（单态化）；C++ 的模板则采用模板实例化机制，在编译期根据模板参数生成特化的类型或函数。

三者都能实现编译期类型检查，但它们在代码生成、类型信息传递、抽象能力和编译成本方面有显著差异。

需要注意，C++ 模板和 Rust 泛型在语言设计上也有很大区别，不能简单地认为它们只是两种不同的单态化实现。

下面开始拆解。

一、先理解：泛型究竟解决什么问题？

1. 没有泛型时，我们会遇到什么问题？

假设你正在开发一个系统，需要实现一个通用的 Max 函数。

先不考虑泛型，我们只能为不同类型编写不同的函数。

func MaxInt(a, b int) int {
    if a > b {
        return a
    }
    return b
}
func MaxFloat64(a, b float64) float64 {
    if a > b {
        return a
    }
    return b
}
func MaxString(a, b string) string {
    if a > b {
        return a
    }
    return b
}

这三个函数的业务逻辑几乎完全相同，区别只在于参数类型和比较操作。

假如我们还要支持 int32、int64、uint64、float32 等类型，就得不断重复代码。

我们希望写一次逻辑，让多个类型复用。

这就是泛型的基本目的。

2. Go 泛型怎么写？

Go 1.18 开始正式支持类型参数。

package main
import "fmt"
func Max[T ~int | ~int32 | ~int64 | ~float32 | ~float64](
    a, b T,
) T {
    if a > b {
        return a
    }
    return b
}
func main() {
    fmt.Println(Max(10, 20))
    fmt.Println(Max(1.5, 2.5))
}

这里最重要的是：

[T ~int | ~int32 | ~int64 | ~float32 | ~float64]

它声明了一个类型参数 T，并通过类型约束限定 T 可以代表哪些类型。

其中：

  • T：类型参数。
  • ~int：允许底层类型为 int 的类型。
  • |：表示类型集合的并集。
  • ~int | ~float64：表示底层类型为 int 或 float64 的类型集合。

例如：

type UserID int
func main() {
    fmt.Println(Max(UserID(10), UserID(20)))
}

UserID 是一个独立定义的类型，但其底层类型是 int，因此满足 ~int 的约束。

注意：如果只写 int，就不能因此认为所有底层类型为 int 的自定义类型也会被允许。

还有一个容易忽略的细节：

type UserID int
type OrderID int

虽然 UserID 和 OrderID 的底层类型相同，但它们是不同的定义类型，不能直接混合传入要求同一个 T 的函数。

例如：

Max(UserID(1), OrderID(2))

无法通过类型检查，因为编译器不能为这个调用推导出同时满足两个参数的同一个 T。

这说明 Go 泛型并不是简单地把类型都抹掉。

在编译期，Go 仍然会检查具体类型、类型约束以及运算是否合法。

这里有一个重要区别。

泛型的语言语义，不等于泛型的底层实现。

例如，Go 规定了泛型函数应该如何进行类型检查、类型推导和调用，但并不意味着每个具体类型都必须拥有独立的一份机器码。

同样，Rust 的泛型在语言层面有自己的类型系统，而单态化是 Rust 编译器生成可执行代码的重要机制。

C++ 模板则是一套更广泛的编译期机制，除了类型参数，还支持非类型模板参数、模板模板参数、偏特化等能力。

因此，接下来必须分开研究两个问题：

  1. 编译器如何确定一个泛型程序是否合法？
  2. 编译器最终如何把它变成机器码？

第二个问题才是特别关心的底层实现。

三、Go 泛型的底层实现：GC Shape + Dictionary

这是整个问题最值得深入的部分。

Go 泛型的实现并不是简单的「每种类型生成一份代码」，也不是简单的「所有类型共用一份代码」。

它采用的是一种折中方案：

GC Shape Stenciling + Dictionary。

官方设计文档对此有明确说明。

为了理解它，我们先从最简单的泛型函数开始。

3.1 从一个 Go 泛型函数开始

func Identity[T any](x T) T {
    return x
}

我们这样调用：

a := Identity[int](10)
b := Identity[string]("hello")
c := Identity[*User](&User{})

从语言层面来看，我们使用了三个实例：

Identity[int]
Identity[string]
Identity[*User]

但问题来了。

假设 Go 编译器对每种具体类型都生成一份独立机器码，那么它就会产生类似下面的三个函数：

func IdentityInt(x int) int {
    return x
}
func IdentityString(x string) string {
    return x
}
func IdentityUserPtr(x *User) *User {
    return x
}

这叫作针对具体类型生成独立实现。

这种方式可以让每个版本都使用最合适的机器类型，但如果类型组合很多，生成的代码也会变多。

Go 选择了一种不同的策略。

它会根据类型的 GC Shape 对实例进行归类，让形状相同的实例共享同一份生成的代码。

但要分清两件事：

  • 代码共享的判据就是 GC Shape：形状相同 → 落到同一份生成代码（stencil）。
  • 共享的代码不一定能直接处理所有具体类型：代码里若存在需要具体类型的操作（类型的大小、字段偏移、方法地址、%T 等），就要靠 Dictionary 在运行时补充信息。

这需要进一步解释。

3.2 什么是 GC Shape？

GC 是 Garbage Collection，也就是垃圾回收。

Go 是带有垃圾回收器的语言，因此编译器必须知道对象和栈帧中的哪些位置包含指针。

举个简单的例子。

假设有三个类型：

type A struct {
    X int64
    Y int64
}
type B struct {
    X *int64
    Y *int64
}
type C struct {
    X int64
    Y *int64
}

在常见的 64 位平台上，可以把它们的内存结构粗略理解为：

A:
+--------+--------+
| int64  | int64  |
+--------+--------+
  非指针    非指针
B:
+--------+--------+
| *int64 | *int64 |
+--------+--------+
    指针     指针
C:
+--------+--------+
| int64  | *int64 |
+--------+--------+
  非指针    指针

假设每个字段都是 8 字节，并忽略额外的对齐等细节。

这三个类型的大小都可能是 16 字节。

但是它们的指针布局不同：

  • 对于 A：第 1 个机器字不是指针，第 2 个机器字不是指针。
  • 对于 B：第 1 个机器字是指针，第 2 个机器字是指针。
  • 对于 C：第 1 个机器字不是指针，第 2 个机器字是指针。

垃圾回收器需要区分这些布局。

如果把 A 的数据误认为两个指针，就可能错误地解释内存。

如果把 B 的指针误认为普通整数，又可能导致垃圾回收器无法正确追踪对象。

所以，GC Shape 不是简单的「占用多少字节」。

它主要与以下信息相关：

  • 类型的大小。
  • 所需的内存对齐。
  • 内存中哪些位置包含指针。

官方设计文档对 GC Shape 的定义也强调了这些因素。

一个重要的纠正

不能认为：

A 和 B 都是 16 字节 所以 A 和 B 一定可以共享泛型代码。

这是错误的。

它们的指针布局不同。

更重要的是，即使两个类型的 GC Shape 相同，泛型代码中的操作也可能存在差异。

这就是 Dictionary 出场的原因。

3.3 Go 为什么不直接按照 GC Shape 合并所有类型？

假设有下面这个泛型函数：

func PrintValue[T any](v T) {
    fmt.Println(v)
}

当 T 是 int 时：

PrintValue[int](123)

当 T 是 string 时：

PrintValue[string]("hello")

这两种类型不仅表示方式不同，打印方式也不同。 编译器需要知道具体类型，才能正确执行相关操作。

又例如：

func NewValue[T any]() T {
    var v T
    return v
}

如果 T 是一个结构体，那么编译器必须知道它的具体布局，才能正确处理零值和返回值。

再比如：

func IsZero[T comparable](v T) bool {
    var zero T
    return v == zero
}

对于不同类型，比较操作可能有不同的实现方式。

因此，仅仅知道一个类型的大小和指针布局是不够的。

Go 的设计思路是：

  1. 对适当相同 GC Shape 的实例共享一部分生成代码。
  2. 对代码执行过程中需要区分具体类型的操作，通过 Dictionary 提供必要的信息。

这就是两个机制必须一起工作的原因。

四、Go 的 Dictionary 到底是什么？

这是 Go 泛型底层实现最容易让人误解的部分。

先说结论：

Dictionary 不是泛型对象本身，也不是一个装着所有类型值的容器。它是编译器生成的一组类型相关元数据及操作所需的信息。

官方文档指出，Go 1.18 的实现通过字典传递类型参数相关的信息，以便生成的泛型函数实例能够正确处理具体类型。

我们用一个例子来理解。

4.1 一个需要比较具体类型的泛型函数

func Max[T ~int | ~int64](a, b T) T {
    if a > b {
        return a
    }
    return b
}

调用：

x := Max[int](10, 20)
y := Max[int64](100, 200)

在源码层面，我们看到的是：

Max[T]

但是编译器生成的机器码必须能够完成具体的比较。

例如，在 amd64 平台上：

  • int 通常是 64 位整数。
  • int64 是 64 位有符号整数。

在这个例子里，两者的 GC Shape 相同（8 字节、无指针），因此会落到同一份 stencil。

但要注意：判据始终是 GC Shape，而不是「大小相同」。大小相同而指针布局不同的类型（例如 int64 与 *int64）不会合并。

而且，这个例子还有一个值得注意的细节：

Max 中的 > 是内建操作，不是用户通过接口传入的任意方法。

不能据此推断 Go 会把所有泛型运算都变成 Dictionary 中的函数调用。

Dictionary 需要提供哪些信息，取决于具体泛型函数使用了什么类型相关操作。

4.2 Dictionary 在概念上包含什么？

为了便于理解，我们可以把它抽象成：

type DictionaryConcept struct {
    TypeInfo       []TypeMetadata
    DerivedTypes   []TypeMetadata
    SubDictionaries []DictionaryConcept
    Helpers        []OperationMetadata
}

这只是帮助理解的伪代码，并不是 Go 运行时中的真实结构体定义。

真实字典由编译器根据泛型函数的需求生成。

它可能包含：

  • 类型参数对应的类型信息。
  • 泛型函数中使用的派生类型信息。
  • 调用其他泛型函数时需要的子字典。
  • 某些类型相关操作需要的辅助信息。

官方实现文档详细讨论了这些内容。

为什么需要类型信息？

例如：

func Describe[T any](v T) {
    fmt.Printf("%T\n", v)
}

这里的 %T 要求程序获得具体的类型信息。

编译器必须确保这个操作能够正确执行。

在泛型代码中，类型参数 T 并不是运行时可以随意读取的普通变量。

它是编译期的类型参数。

如果某个操作需要具体类型信息，编译器就必须安排适当的机制来提供这些信息。

为什么需要子字典？

考虑：

func Outer[T any](x T) {
    Inner[T](x)
}
func Inner[T any](x T) {
    fmt.Println(x)
}

Outer 并不知道 T 最终是什么具体类型。

例如：

Outerint

或者：

Outerstring

当 Outer 调用 Inner[T] 时，Inner 所需的类型信息需要从 Outer 的泛型实例化上下文中传递下去。

这就是子字典等机制存在的原因之一。

当然，具体代码生成还可能进行优化，不能认为所有泛型函数调用都会机械地多出一次独立字典分配。

4.3 Dictionary 一定意味着运行时反射吗？

不一定。

这里需要区分三个概念：

概念含义
类型参数源码层面的泛型参数，例如 T
Dictionary编译器生成的、与具体类型相关的元数据及操作信息
Reflection程序通过反射 API 检查或操作类型和值

它们不是同一个东西。

Go 泛型并不是通过反射来完成所有类型操作的。

对于很多操作，编译器可以在编译期直接确定具体类型和指令。

对于另一些操作，生成的代码需要借助 Dictionary 或运行时辅助机制。

因此，更准确的说法是：

Go 泛型可能在运行时携带类型相关的信息，但这不意味着泛型调用本身等价于反射。

五、Go 的泛型函数最终是怎样执行的？

现在我们把前面的概念串起来。

假设你有：

func First[T any](items []T) T {
    return items[0]
}

然后：

ints := []int{10, 20, 30}
x := First[int](ints)

从源码角度来看，执行过程可以抽象为：

                    编译期
                       │
                       ▼
            解析泛型函数 First[T]
                       │
                       ▼
             检查 T 是否满足约束
                       │
                       ▼
            根据实际类型实例化 First[int]
                       │
                       ▼
         分析所需的 GC Shape 和类型信息
                       │
                       ▼
          生成或复用相应的代码实现
                       │
                       ▼
             准备需要的 Dictionary
                       │
                       ▼
                    链接
                       │
                       ▼
                    运行期
                       │
                       ▼
              调用生成的机器码

这是一张概念流程图，不代表 Go 编译器内部只有这些步骤，也不意味着每次调用都会动态创建一个 Dictionary。

Dictionary 通常是编译器生成的静态数据，不是每次调用都在堆上分配一个字典。

这一点非常重要。

如果每次调用泛型函数都要在堆上分配字典，开销会非常不合理。

实际实现中，字典通常在编译期生成，并由调用代码引用。

六、Rust 泛型的底层实现：Monomorphization

接下来研究 Rust。

如果说 Go 选择了代码共享与类型信息传递之间的折中，那么 Rust 的核心思路就更直接：

在编译期确定泛型的具体类型，并为使用到的具体类型组合生成相应的实现。

Rust 官方文档将这一过程称为 Monomorphization，即单态化。

6.1 Rust 泛型示例

fn identity<T>(x: T) -> T {
    x
}
fn main() {
    let a = identity::<i32>(10);
    let b = identity::<f64>(3.14);
    let c = identity::<String>("hello".to_string());
}

源码只定义了一次：

fn identity<T>(x: T) -> T {
    x
}

但编译器需要为这些具体类型生成可执行代码。

概念上，可以把结果理解成：

fn identity_i32(x: i32) -> i32 {
    x
}
fn identity_f64(x: f64) -> f64 {
    x
}
fn identity_string(x: String) -> String {
    x
}

这些代码只是为了帮助理解单态化的伪代码，不是 Rust 编译器真正生成的源文件。

实际生成的是编译器内部表示和机器码。

这意味着什么？

对于：

let a = identity::<i32>(10);

编译器知道：

T = i32

因此可以把类型参数替换为 i32，再继续优化。

对于：

let b = identity::<f64>(3.14);

编译器则处理另一个具体类型。

到生成机器码时，泛型抽象已经被具体类型实例化了。

一般情况下，运行时不需要再通过一个 Dictionary 判断 T 到底是什么。

这就是 Rust 泛型通常被称为零成本抽象的重要原因。

不过，必须强调：

零成本泛型不意味着零编译成本，也不意味着最终二进制没有额外开销。

单态化可能导致：

  • 编译时间增加。
  • 机器码体积变大。
  • 更多实例化函数需要进行优化。
  • 编译缓存和链接工作增加。

Rust 官方文档也明确说明，单态化会生成针对具体类型的实现。

6.2 Rust 的泛型约束去了哪里？

假设我们写：

fn max_value<T: PartialOrd>(a: T, b: T) -> T {
    if a >= b {
        a
    } else {
        b
    }
}

这里的：

T: PartialOrd

表示 T 必须实现 PartialOrd Trait。

那么，编译器怎么知道 a >= b 是合法的？

因为 PartialOrd 为类型提供了相关的比较能力。

当编译器检查：

max_value::<i32>(10, 20)

时，它会验证 i32 满足相应的 Trait 约束。

随后，在单态化过程中，编译器根据具体类型生成相应实现。

从概念上看：

fn max_i32(a: i32, b: i32) -> i32 {
    if a >= b {
        a
    } else {
        b
    }
}

由于 i32 的比较方式已经确定，编译器通常能够将相关操作直接编译为具体指令。

这与 Go 的 Dictionary 机制形成了一个鲜明对比。

Go 的泛型实现可能在生成代码中传递 Dictionary，以便代码共享时仍能正确处理类型差异。

Rust 则主要依赖具体类型实例化，让编译器有机会直接生成针对具体类型的代码。

当然，Rust 的 Trait 系统还有动态分派、关联类型、泛型关联类型等机制，不能把整个 Trait 系统都简单等同于单态化。

七、Rust 中的泛型与动态分派不是一回事

这部分很关键。

很多人会认为：

Rust 的 Trait 就相当于 Go 的 Interface。

这句话只在某些场景下成立。

Rust Trait 可以用于静态分派，也可以通过 Trait Object 实现动态分派。

这两种机制的底层行为并不一样。

7.1 静态分派：泛型参数

例如：

trait Worker {
    fn work(&self);
}
struct Planner;
impl Worker for Planner {
    fn work(&self) {
        println!("planning");
    }
}
fn execute<T: Worker>(worker: &T) {
    worker.work();
}

调用：

let planner = Planner;
execute(&planner);

这里的 T 是具体类型 Planner。

编译器可以生成相应的具体实现。

概念上相当于：

fn execute_planner(worker: &Planner) {
    worker.work();
}

由于类型已经确定，编译器通常可以直接调用 Planner::work，甚至进一步内联函数。

这种方式一般没有通过虚函数表进行动态分派的必要。

7.2 动态分派：Trait Object

再看：

fn execute(worker: &dyn Worker) {
    worker.work();
}

这里使用的是：

&dyn Worker

它不是普通的泛型类型参数。

这是 Trait Object。

概念上，Trait Object 的引用通常包含：

+------------------+
| 数据指针         |
+------------------+
| vtable 指针      |
+------------------+

数据指针指向具体对象。

vtable 保存与该 Trait Object 相关的类型具体实现所需的函数入口等信息。

调用：

worker.work();

时，程序通过动态分派机制确定要调用哪个实现。

需要注意，Trait Object 的实际表示和调用细节属于 Rust 编译器与 ABI 实现层面的内容，上图是帮助理解的概念模型。

两种机制对比

特性T: Worker&dyn Worker
分派方式通常静态分派动态分派
编译器是否知道具体类型在具体实例化时知道调用点不一定知道
是否通常需要 vtable 调用不需要需要
是否可能内联通常更容易一般更困难，但优化器有时能消除间接调用
是否容易产生大量实例化代码可能通常可以共享动态调用路径

所以，Rust 泛型并不是只能走静态分派。

它同时提供了静态分派和动态分派两套机制。

泛型约束决定哪些类型可以参与调用；分派策略决定调用具体实现的方式。

这是两个不同的维度。

八、C++ 模板的底层实现：模板实例化

现在来看 C++。

C++ 的模板与 Go、Rust 的泛型有一个共同点：

它们都可以让程序员编写通用算法和数据结构。

但 C++ 模板的设计范围更广。

它不仅允许类型参数，还支持非类型模板参数、模板模板参数，以及复杂的模板元编程。

C++ 模板的核心机制之一是模板实例化：编译器使用具体模板实参生成相应的特化实体。

8.1 C++ 模板示例

template<typename T>
T identity(T x) {
    return x;
}
int main() {
    int a = identity<int>(10);
    double b = identity<double>(3.14);
}

概念上，编译器会生成类似：

int identity_int(int x) {
    return x;
}
double identity_double(double x) {
    return x;
}

的具体实现。

同样，这只是概念上的展开。

真实的 C++ 编译器会先进行模板实参推导、语义检查、模板实例化和优化，再生成目标代码。

如果你使用 GCC 或 Clang，后续通常还会经过 LLVM 或其他后端处理。

8.2 C++ 模板与 Rust 泛型的相似点

二者都经常生成针对具体类型的机器码。

因此：

identity<int>(10)

和：

identity::<i32>(10)

在底层思路上存在相似之处。

但不要因此认为二者的类型系统相同。

8.3 一个关键差异：类型检查发生在什么时候

这是两种「单态化」最容易混淆的地方：

  • Rust：泛型函数体在定义处就用 trait bound 做类型检查。编译器要求函数体对任意满足约束的 T 都成立，写错在定义时就报错，不必等到某个具体实例。
  • C++：模板体在定义处只做与模板参数无关的检查（两阶段查找的第一阶段），涉及 T 的语义检查要等到实例化时才进行。同一个模板可能对 int 合法、对 std::string 报错。

由此带来两个直接后果：

  • C++ 的模板错误往往在实例化点展开一长串调用栈；Rust 的约束错误集中在定义处，提示「T 不满足 bound」。
  • Rust 的泛型体被保证「对全部满足约束的类型都成立」，C++ 模板体只保证「对实际出现的实例成立」。

这是语法相似、编译期行为不同的典型例子，也是不能把两者简单等同的原因。

C++ 模板允许许多在 Rust 中需要不同机制才能表达的编译期操作。

例如，C++ 支持非类型模板参数：

template<typename T, std::size_t N>
struct Array {
    T data[N];
};

然后：

Array<int, 10> a;
Array<int, 20> b;

这里的 N 不是一个类型，而是一个编译期数值参数。

Array<int, 10> 与 Array<int, 20> 是不同的模板特化类型。

Rust 也支持常量泛型：

struct Array<T, const N: usize> {
    data: [T; N],
}

因此，这项能力并不是 C++ 独有的。

但 C++ 模板还具有独特的偏特化、SFINAE、Concepts 和模板元编程生态，这些特性共同构成了一个非常强大、也非常复杂的编译期系统。

九、C++ 模板为什么经常被说成「编译期编程」？

因为模板不只是用来生成不同类型的容器。

它还可以参与复杂的编译期计算和代码选择。

例如：

template<int N>
struct Factorial {
    static constexpr int value = N * Factorial<N - 1>::value;
};
template<>
struct Factorial<0> {
    static constexpr int value = 1;
};
int main() {
    constexpr int result = Factorial<5>::value;
}

这里的：

Factorial<5>

会通过模板实例化递归地形成一系列类型。

概念上相当于：

Factorial<5>
    │
    ▼
5 * Factorial<4>::value
    │
    ▼
5 * 4 * Factorial<3>::value
    │
    ▼
5 * 4 * 3 * 2 * 1
    │
    ▼
120

这段代码使用模板递归表达了编译期计算。

不过，在现代 C++ 中，类似的数值计算通常更适合使用 constexpr 或 consteval，不一定要使用模板递归。

这只是为了说明 C++ 模板的表达能力。

Rust 和 Go 也支持不同形式的编译期检查与计算，但不能直接把它们的泛型系统视为与 C++ 模板元编程完全等价的机制。

十、C++ 模板为什么可能导致二进制膨胀？

假设有：

template<typename T>
T process(T x) {
    return x + x;
}

然后：

process<int>(1);
process<double>(1.0);
process<long>(2L);
process<float>(2.0f);

编译器通常需要为这些不同的类型实例化生成相应实现。

概念上：

process<int>
process<double>
process<long>
process<float>

于是，编译器需要处理多个具体版本。

如果模板被大量使用，并且参数组合非常多，就可能导致：

  • 编译时间增加。
  • 目标文件变大。
  • 链接时间增加。
  • 机器码体积增大。

不过，这并不意味着最终二进制必然包含四份完全独立、大小相同的函数。

编译器可能内联函数，链接器可能合并某些重复实例，优化器也可能删除不可达代码。

C++ 模板实例化和链接层面的去重是不同阶段的事情。

十一、三者最核心的差异：到底生成几份机器码？

现在把 Go、Rust 和 C++ 放到同一个例子里。

假设我们定义一个泛型函数：

Process<T>(value T) -> T

并使用以下类型：

int32
int64
float64
*User
*Order

我们想知道编译器最终生成几份机器码。

答案是：不能只根据源码中使用了几个类型参数来确定。

因为三者的策略不同。

11.1 Rust：以具体实例化为核心

Rust 通常会为实际使用的具体类型实例生成独立实现。

概念上：

Process<i32>
Process<i64>
Process<f64>
Process<*User>
Process<*Order>

通常对应不同的单态化实例。

但具体的代码生成和最终二进制布局仍然可能受到优化、内联、链接去重等因素影响。

11.2 C++：以模板实例化为核心

C++ 编译器通常根据不同的模板实参生成相应的模板特化实体。

概念上也是：

Process<int32>
Process<int64>
Process<double>
Process<User*>
Process<Order*>

但同样不能直接推导出最终二进制一定包含五份完全独立的机器码。

11.3 Go：按 GC Shape 共享部分代码

Go 则不同。

判据就是 GC Shape。

例如，所有指针类型在机器层面都是一个机器字、且该字要被 GC 当作指针扫描，因此它们属于同一个 GC Shape：

Process[*User] Process[*Order]

这两个实例会共享同一份生成的代码，具体类型的差异由 Dictionary 在需要时补充（例如字段偏移按 *User 还是 *Order 解读）。

但要注意区分「共享代码」与「所有类型都能合并」：

  • int 与 *User：在 amd64 上都是 8 字节，但一个是普通整数、一个要被 GC 扫描，GC Shape 不同，因此不会合并。
  • int64 与 float64：GC Shape 相同（8 字节、无指针），因此会共享同一份 stencil；但整数加法与浮点加法是不同的指令，这个差异只能靠 Dictionary 里的 helper 在运行时分发。

所以更准确的说法是：GC Shape 决定「共享哪一份代码」，Dictionary 负责「让这份共享代码能针对具体类型做正确的事」。两者缺一不可。

Go 的官方设计文档明确将这种实现方式描述为 GC Shape Stenciling 与 Dictionary 的结合。

十二、把三者放到内存布局层面比较

这部分对理解底层系统尤其重要。

假设我们定义一个通用容器。

12.1 Go

type Box[T any] struct {
    Value T
}

然后：

a := Box[int64]{Value: 10}
b := Box[*User]{Value: &User{}}

Box[int64] 和 Box[*User] 的字段类型不同。

它们的实际内存布局必须能够正确表示各自的字段。

对于 Box[int64]：

+----------------+
| int64          |
+----------------+

对于 Box[*User]：

+----------------+
| *User          |
+----------------+

在常见的 64 位平台上，它们都可能占用 8 字节。

但二者的语义与 GC 指针布局不同。

泛型类型实例化不会让 Go 忽略这些差异。

12.2 Rust

struct Boxed<T> {
    value: T,
}

然后：

let a = Boxed::<i64> { value: 10 };
let b = Boxed::<&User> {
    value: &user,
};

Boxed<i64> 和 Boxed<&User> 同样是不同的具体类型。

编译器根据具体类型确定布局。

此外，Rust 的泛型类型还会受到 repr(Rust)、repr(C)、对齐规则、字段重排等因素影响。

不能把 Rust 泛型布局简单理解成「将 T 原样替换进去，其他所有规则都不变」。

12.3 C++

template<typename T>
struct Boxed {
    T value;
};

然后：

Boxed<long long> a{10};
Boxed<User*> b{nullptr};

同样，两个模板特化具有各自的具体类型和布局。

关键结论

三者都必须保证具体实例化类型的内存表示符合各自的语言规则。

Go 的 GC Shape 主要用于编译器内部的代码生成与共享决策，不是说不同 Shape 或不同类型的容器在语言层面会变成同一个类型。

这点必须牢牢记住。

十三、Go 的 Dictionary 与 Rust 的 vtable 有什么区别？

这是一个很容易混淆的问题。

先看两种不同的概念。

Go Dictionary

Go 泛型的 Dictionary 是编译器为泛型代码生成的一组类型相关信息。

它服务于泛型实例化，帮助生成的代码正确处理具体类型。

它不是 Go Interface 的另一个名字。

Rust vtable

Rust 的 vtable 主要与 Trait Object 的动态分派相关。

当程序使用：

&dyn Worker

时，调用方可以通过 vtable 找到具体实现的函数入口。

为什么它们不能直接等同？

因为它们服务的目的不同。

对比Go DictionaryRust vtable
主要用途支持泛型代码的类型相关操作支持 Trait Object 动态分派
是否等价于泛型类型参数否否
是否必然用于每次方法调用否动态分派调用通常需要使用
是否包含类型相关信息是与具体 Trait Object 实现有关
是否意味着动态分派不意味着是动态分派机制的一部分

换句话说：

Go 泛型可能通过 Dictionary 补充类型信息，而 Rust 的普通泛型通常通过单态化获得具体类型。

但当 Rust 使用 dyn Trait 时，它就进入了动态分派的世界。

Go Dictionary、Rust 泛型参数和 Rust vtable 是三个不同的概念。

十四、为什么 Go 不完全采用 Rust 的单态化方案？

这是一个非常值得思考的设计问题。

Go 团队为什么不直接给每种类型生成一份完整的机器码？

一种重要的考虑是代码生成规模。

假设你有一个复杂的 Agent Runtime。

内部有：

type Task[T any] struct {
    Input  T
    Output T
}

func Execute[T any](task Task[T]) {
    // 复杂调度逻辑
}

如果系统里存在大量不同的 T，完全按类型生成代码可能增加编译器需要处理的实例数量。

Go 选择通过 GC Shape 共享部分代码，避免纯粹按照所有具体类型生成一份独立代码。

但这也不是没有代价。

为了让共享代码正确工作，编译器必须通过 Dictionary 等机制提供它需要的类型相关信息。

于是，Go 的设计在两个方向之间进行折中：

完全单态化
    │
    ├── 优点：具体类型已知，容易生成专门代码
    └── 代价：可能产生更多实例化代码
GC Shape + Dictionary
    │
    ├── 优点：某些实例能够共享生成代码
    └── 代价：部分类型相关操作需要额外机制

这里也要强调，不能把 Go 泛型的性能简单概括成「比 Rust 慢」。

对于一个简单的泛型函数，Go 可能生成非常高效的机器码。

对于另一个复杂函数，Rust 的单态化也可能因为内联、优化或实例数量增加而产生不同的成本。

真正的差异取决于具体代码、编译器优化以及调用场景。

十五、为什么 Go 不直接采用 C++ 模板那样的机制？

这涉及语言设计哲学。

Go 的泛型是在语言已经发展多年后才加入的。

Go 需要尽量兼容既有语言设计，并维持相对简单的编译模型。

C++ 模板则经历了很长时间的发展，形成了相当复杂的编译期抽象体系。

例如 C++ 可以使用：

  • 模板偏特化。
  • 非类型模板参数。
  • 模板模板参数。
  • SFINAE。
  • Concepts。
  • 模板元编程。

Go 则更强调通过类型参数与约束表达通用算法。

例如：

func Map[T any, U any](
    input []T,
    transform func(T) U,
) []U {
    result := make([]U, len(input))
    for i, item := range input {
        result[i] = transform(item)
    }
    return result
}

这里，Go 使用显式类型参数和函数参数表达转换逻辑。

而 C++ 可以通过模板参数、类型推导和其他编译期机制组合出更加复杂的抽象。

这并不是说哪种语言绝对更好。

而是三者对泛型的定位不同：

  • Go： 让通用数据结构与算法更容易表达，同时维持语言和工具链的相对简单。
  • Rust： 结合强类型系统、Trait 约束和所有权模型，以单态化为基础实现高效的静态抽象。
  • C++： 提供非常强大的模板实例化与编译期编程能力，同时承担相应的语言和编译器复杂度。

十六、一个更有意义的例子：实现通用的 Agent Scheduler

现在把理论放回实际开发场景。

假设正在实现一个 Scheduler，需要从一组候选任务中选择一个任务。

我们定义一个通用的选择函数：

SelectBest<T>(items) -> T

不同语言会怎么处理？

16.1 Go

package main
type Scored interface {
    ~int | ~int64 | ~float64
}
func Max[T Scored](items []T) T {
    best := items[0]
    for _, item := range items[1:] {
        if item > best {
            best = item
        }
    }
    return best
}

这个例子演示了通用数值比较。

如果你把它用于真实的 Scheduler，可能会将 T 替换成任务评分、优先级或其他可比较的值。

Go 编译器会检查类型约束，并根据具体实例化生成相应实现。

但如果任务评分依赖复杂的业务逻辑，例如动态策略、插件或者模型评估，那么仅仅使用泛型未必是最佳抽象。

16.2 Rust

fn max<T: PartialOrd + Copy>(items: &[T]) -> Option<T> {
    items.iter().copied().max_by(|a, b| {
        a.partial_cmp(b).unwrap()
    })
}

这里为了让代码更短，使用了 Copy，但需要注意：

PartialOrd 并不保证所有值都能产生有序比较结果。

例如浮点数的 NaN 就会让 partial_cmp 返回 None。

所以，在生产代码里直接 unwrap() 需要谨慎处理。

这个例子还说明，Rust 的 Trait Bound 可以组合多个约束。

编译器会验证类型是否满足约束，并根据具体类型生成实现。

16.3 C++

#include <algorithm>
#include <optional>
#include <span>
template<typename T>
std::optional<T> max_value(std::span<const T> items) {
    if (items.empty()) {
        return std::nullopt;
    }
    return *std::max_element(items.begin(), items.end());
}

这个函数使用了模板参数 T，并通过标准库算法找到最大值。

它没有显式写出 T 的完整约束，但调用能否成立仍然取决于 std::max_element 对相关操作的要求，以及具体类型是否支持相应的比较。

在 C++20 中，可以通过 Concepts 更明确地表达约束。

例如：

#include <concepts>
template<std::totally_ordered T>
T max_value(T a, T b) {
    return a < b ? b : a;
}

这里的 std::totally_ordered 表达了更强的有序性要求。

不过，Concepts 检查的是类型和表达式是否满足规定的约束，并不自动证明用户自定义的比较操作在数学意义上真的满足全序关系。

十七、如果我们深入到汇编层面，会发生什么？

前面一直在讲编译器策略，现在看更接近机器码的一层。

考虑：

func Add[T ~int64](a, b T) T {
    return a + b
}

调用：

x := Add[int64](10, 20)

在 amd64 平台上，编译器最终可能将核心计算转换成类似：

ADDQ ...

这样的整数加法指令。

这里的汇编只是示意，不能当作 Go 编译器对这段代码的精确反汇编结果。

如果换成 Rust：

fn add<T>(a: T, b: T) -> T
where
    T: std::ops::Add<Output = T>,
{
    a + b
}

调用：

let x = add::<i64>(10, 20);

Rust 编译器可以针对 i64 生成具体实现。

经过优化之后，核心运算也可能变成一条或少量整数加法指令。

C++：

template<typename T>
T add(T a, T b) {
    return a + b;
}

调用：

auto x = add<long long>(10, 20);

也可以产生类似的机器码。

因此，在这个简单的加法例子中，三种语言最终可能生成几乎一样的核心计算指令。

这就引出了一个非常重要的结论：

不同的泛型实现策略，并不必然意味着简单运算的最终机器码存在显著差异。

真正的差异通常要在更复杂的场景中观察，例如：

  • 大量不同类型的实例化。
  • 泛型容器与接口的组合。
  • 动态分派。
  • 需要运行时类型信息的操作。
  • 复杂泛型函数的内联与优化。
  • 编译时间与最终二进制体积。

十八、泛型与接口：Go 的另一条路线

如果你已经熟悉 Go，那么还必须理解一个问题：

Go 泛型与 Go Interface 是两套不同的机制，但它们可以组合使用。

例如：

type Worker interface {
    Work()
}

我们可以定义：

func Execute[T Worker](worker T) {
    worker.Work()
}

这里使用的是泛型类型参数。

与之不同：

func ExecuteInterface(worker Worker) {
    worker.Work()
}

这里使用的是接口类型。

两者的区别不只是语法。

泛型版本

func Execute[T Worker](worker T)

编译器需要确定 T 的具体类型，并检查它满足 Worker 约束。

其代码生成可能使用具体类型实例化、GC Shape 共享以及 Dictionary 等机制。

接口版本

func ExecuteInterface(worker Worker)

接口值在 Go 的常见实现中携带动态类型相关的信息和数据表示。

通过接口调用方法时，运行时可以根据动态类型找到对应的方法实现。

接口值的具体内部表示属于 Go 实现细节；常见的非空接口实现包含类型相关信息和数据指针，但不应该把某种内部结构直接当作所有 Go 版本的语言规范。

两者怎么选择？

假设你在 ARES 中定义一个任务执行接口：

type Agent interface {
    Execute(ctx context.Context, task Task) error
}

不同 Agent 可能具有完全不同的实现：

Planner
Executor
Verifier
Retriever

这些类型的行为不同，且可能在运行时由配置、插件或注册表决定具体使用哪个实现。

这时，接口往往很自然。

但如果你在编写一个通用的内存容器：

type RingBuffer[T any] struct {
    data []T
}

泛型通常更适合，因为你希望在编译期确定元素类型，并获得类型安全的容器操作。

因此，不能简单地说：

泛型比接口快，所以应该尽可能使用泛型。

更合理的思路是：

  • 数据结构的元素类型需要参数化：考虑泛型。
  • 需要在运行时替换不同实现：考虑接口。
  • 需要统一 API，同时又希望类型安全：可以组合使用两者。

十九、Go 泛型的性能开销到底在哪里？

现在我们从工程角度总结。

不要简单地把 Go 泛型理解为「运行时慢」，也不要把 Rust 泛型理解为「绝对零开销」。

需要具体分析。

19.1 Go 泛型可能产生的成本

第一类：类型相关操作

如果泛型函数需要具体类型信息，编译器可能通过 Dictionary 或运行时辅助机制支持这些操作。

但普通的整数运算并不意味着必然发生一次字典函数调用。

第二类：代码共享的优化边界

当多个类型共享一份泛型代码时，编译器不能总是像针对单一具体类型那样自由地进行所有专门化优化。

具体影响取决于共享方式和代码内容。

第三类：接口转换

如果泛型代码把值转换为接口类型，或者调用接口方法，就可能涉及接口表示、装箱或动态分派等额外工作。

不过，这属于具体操作的成本，不能一概归因于泛型本身。

19.2 Rust 泛型可能产生的成本

第一类：单态化产生的代码量

不同类型组合可能生成不同实例。

第二类：编译时间

更多实例意味着编译器可能需要处理更多函数和类型。

第三类：动态分派

如果使用 dyn Trait，调用路径可能包含 vtable 间接调用。

但如果使用静态泛型参数，通常不需要这条动态分派路径。

19.3 C++ 模板可能产生的成本

第一类：模板实例化

大量模板参数组合可能导致编译时间和代码量增加。

第二类：复杂的编译期计算

模板元编程、复杂约束和递归实例化可能增加编译器负担。

第三类：实例化与链接

跨翻译单元使用模板时，编译器可能生成重复实例化，随后由链接机制处理符合条件的重复实体。

二十一、实际建议：Go 和 Rust 应该怎么选？

结合我之前在开发 ARES、CodeScope 这类系统软件项目的情况，我建议不要单纯从泛型的理论性能来选择语言，而应该看任务的特点。

1. 如果是 Go Agent Runtime

例如：

  • Task、Checkpoint、Event 等通用数据结构。
  • 泛型队列、集合、缓存。
  • 通用的数据转换函数。
  • 类型安全的工具库。
  • 需要与 Go 的接口体系自然结合的基础设施。

Go 泛型已经足够实用。

例如：

type Queue[T any] struct {
    items []T
}

你不必为了避免 Dictionary 而放弃泛型。

对于大多数普通业务逻辑和基础数据结构，首先考虑代码清晰度、类型安全和可维护性。

如果性能敏感，再通过 benchmark、CPU profile 和内存 profile 确认瓶颈。

2. 如果是 Rust 底层分析器

例如：

  • LLVM IR 分析。
  • 复杂的数据流分析。
  • 类型化的内存图。
  • 所有权与借用关系建模。
  • 高性能遍历和转换。
  • 需要严格控制内存布局与生命周期的数据结构。

Rust 的泛型、Trait 和所有权系统可以形成很强的组合。

例如：

trait Analyzer {
    type Input;
    type Output;
    fn analyze(
        &self,
        input: Self::Input,
    ) -> Self::Output;
}

这里使用了关联类型。

不同的分析器可以定义不同的输入和输出类型。

对于具体分析器，使用泛型参数通常可以获得静态分派。

如果你需要在运行时存储不同类型的分析器，也可以使用 Trait Object，或者通过枚举等方式实现统一管理。

3. 如果是 C++ 编译器与模板基础设施

例如：

  • LLVM 周边工具。
  • 编译器库。
  • 高度通用的算法库。
  • 复杂的编译期类型计算。
  • 需要充分利用 C++ 模板生态的场景。

C++ 模板具有很强的表达能力。

但如果只是实现一个普通的泛型容器或简单算法，没有必要为了模板元编程而增加额外复杂度。

二十二、最后总结

我们把整个问题浓缩成几个关键结论。

第一，泛型是一种语言抽象，底层实现是另一回事

三种语言都能表达类型参数化的函数和数据结构，但它们并不使用完全相同的代码生成机制。

第二，Go 泛型不是简单的字典调用

Go 的核心实现是 GC Shape Stenciling 与 Dictionary 相结合。

有些实例可以共享代码，某些类型相关操作则需要额外信息。

不能把每一次泛型调用都理解为运行时反射或字典函数调用。

第三，Rust 泛型主要依赖单态化

编译器为使用到的具体类型实例化生成相应实现。

这样通常能够产生高效的静态调用路径，但也可能增加编译时间和二进制体积。

第四，C++ 模板不仅是泛型

C++ 模板的实例化机制与 Rust 单态化存在相似之处，但 C++ 还具有非类型模板参数、偏特化、Concepts 和复杂的模板元编程能力。

第五，不能简单地按语言给泛型性能排名

对简单的整数运算，三者可能生成非常接近的机器码。

真正的区别通常体现在代码生成规模、运行时类型信息、分派机制、优化机会和编译成本上。

1、Monomorphization（泛型实例化）—— 代码量的放大器

专有名词

名词含义
monomorphization每个泛型 + 具体类型组合 → 生成一份独立的机器码
type instantiationHashMap<String, i32> 和 HashMap<String, f64> 是两份代码
LLVM codegen每个实例化函数都走 LLVM 后端（IR → 机器码），release 下还要跑优化 pass
CGU（Codegen Unit）rustc 把实例化结果切成若干代码生成单元，这是 LLVM 并行度的来源（release 默认 16 个）
combinatorial explosion嵌套泛型：Vec<HashSet<Box<dyn Iterator<Item = T>>>> → 每层都展开

通俗解释

fn sum<T: Add<Output = T>>(a: T, b: T) -> T 被 10 种类型调用 → 10 份机器码，每份都走完整的 LLVM 后端。

Vec<String>、Vec<i32>、Vec<MyStruct>、HashMap<String, i32>、HashMap<&str, &str>……每个都是独立函数体。一个中型项目做到数万个实例化项很常见（可用 cargo llvm-lines、-Zprint-mono-items 实测，见第 4 节）。

关键点：单态化本身不是最慢的那一步。它在前端只是收集实例、生成 MIR；真正昂贵的是它把这些代码量乘以 N 之后灌进 LLVM 后端。所以更准确的说法是"单态化 + LLVM 后端"是一个复合主因，单态化是放大器。

为什么 Go 不这样？

Go 1.18+ 的泛型实现是 GC shape stenciling + dictionaries：按类型对 GC 的"形状"分组，所有指针类型共享同一份实例（都按 uintptr 处理），方法调用、字段偏移通过隐藏的 dictionary 参数间接寻址。

所以 Go 既不是完全单态化（Sum[int] 和 Sum[int64] 仍然是两份代码），也不是"一份代码服务所有类型"，更不是"装箱进 any"。它在代码体积 ↔ 运行时分发开销之间取了折中。Rust 选了"零运行时开销"，代价就落在编译期。

2、LLVM 优化管线（尤其 --release）

专有名词

名词含义
LLVM IR（Intermediate Representation）编译器中端表示，Rust → LLVM IR → 目标机器码
SROA（Scalar Replacement of Aggregates）把 struct 拆成标量，便于寄存器分配
IPO（Inter-Procedural Optimization）跨函数优化（含内联）；跨 crate 内联需要 LTO 才成立
LTO（Link Time Optimization）链接时跨 crate 优化，lto = true（fat）最慢
thin LTO折中方案（lto = "thin"），比 fat 快，比不开启效果好
local ThinLTO每个 CGU 内部的 ThinLTO，这是 release 默认就有的，不等于跨 crate LTO
PGO（Profile-Guided Optimization）可选，用 profile 数据引导内联/分支布局

通俗解释

cargo build（debug）：opt-level = 0，LLVM 基本不优化。单个函数的优化通常在毫秒级或更低。

cargo build --release：opt-level = 3、codegen-units = 16、lto = false（默认不开跨 crate LTO）、incremental = false。此时每个 CGU 内部有 local ThinLTO，由 LLVM 并行处理——耗时大头基本都在 LLVM_module_codegen + LLVM_passes 这两个 phase。

所以量级是：数万个实例化函数 × 每个毫秒级后端开销 → 几十秒到几分钟的纯后端时间，再叠加几百个依赖 crate 的同类开销。

类比：Go 没有 release/debug 之分，优化策略固定（内联预算小、无自动向量化），所以全量构建通常是秒级到几十秒。

3、依赖 DAG（有向无环图）

专有名词

名词含义
crate DAG每个 .crate 是一个节点，依赖关系是有向边
cargo包管理器，解析 Cargo.toml → 构建 DAG
串行依赖A 依赖 B，B 编译完 A 才能开始（关键路径）
并行编译cargo 可并行编译无依赖关系的 crate；默认 -j 就等于可用核心数
feature unification多个 crate 依赖同一库的不同 feature → 合并后可能多出变体
build.rs构建脚本（FFI、代码生成），阻塞所在 crate 的编译

通俗解释

一个典型 Rust 项目（tokio + serde + anyhow + tracing）：

  • 依赖树展开后 200-500 个 crate
  • 每个 crate 必须完整编译（类型检查 + MIR 优化 + codegen + 产出 .rlib/.rmeta），哪怕它只有一个函数被用到
  • 关键路径（最长链）上的 crate 只能串行，这条链通常决定了整体下限
  • 一个 build.rs 跑 CMake / bindgen → 额外 10-60 秒，且期间无法并行

类比：Go 以 package 为编译单元，依赖几百个 package 也很常见，但单元粒度更细、没有 codegen 阶段的重活，包级并行度更充分。

4、复杂类型检查（Trait + Lifetime + GAT）

专有名词

名词含义
trait resolution每个泛型调用点，编译器要确定用哪个 impl（可能有多个 candidate）
coherence一致性检查（impl 不能重叠），这也是新 solver 最先落地的部分
lifetime unification多个 'a 约束要求交（intersection），证明兼容
GAT（Generic Associated Type）type Item<'a> where Self: 'a; → 额外一层约束求解
HRTB（Higher-Ranked Trait Bound）for<'a> fn(&'a T)，属于 rank-1 高阶限定，不是"二阶逻辑"
inference variable未标注的 lifetime 是 ?a，要等所有约束收集完再统一求解
trait solver旧 solver 是"递归 + 缓存"；新 solver（-Znext-solver）是基于 canonicalization 的类型化约束求解，不是并行；目前仍是 nightly，首要目标是正确性与可维护性，性能在逐步追平

通俗解释

Go 的类型检查：struct 字段 + interface 隐式匹配 → 基本是线性扫描。 Rust 的类型检查：每个调用点要解一组约束（比如 T: Iterator<Item = u32> + Send + 'a），要证明 3 个约束成立且 lifetime 兼容 → 搜索空间大。实际有缓存，但大项目里缓存命中率不一定高。

越复杂的泛型组合（tokio 的 Future + Send + 'static、serde 的 Deserialize<'de>），前端耗时越明显；diesel、nalgebra 这类重度泛型库是典型受害者。

5、宏展开（次要因素）

专有名词

名词含义
macro_rules!声明式宏，编译器进程内展开，开销很小
proc macro（#[derive] / #[attr]）编译成动态库，rustc 通过 proc_macro 桥接 dlopen 到同一进程内调用——不是子进程，也没有管道 IPC
TokenStream编译器内部 token 流与 proc_macro API 之间的句柄式抽象，跨界时需要转换
derive macro#[derive(Serialize)] → 展开成几十行 impl → 再进入类型检查 + 单态化

通俗解释

macro_rules! 很快（token 层面的替换）。 proc macro 的开销来自三块：动态库加载、token 树的来回转换、以及展开出来的代码还要再走一遍类型检查和单态化。

一个 #[derive(Serialize, Deserialize, Clone, Debug)] = 4 次宏调用 × 200 个 struct = 800 次宏调用。次数不少，但单次开销在微秒到毫秒级，相比后端仍是小头。

真正被宏拖慢的典型是 serde + 大量 DTO 的组合，或者编译期生成大数组/大 match 的宏。

6、链接（Linking）

名词含义
thin LTO / fat LTO跨 crate 去重 + 内联，链接时再跑一遍优化
symbol deduplication泛型实例默认以 linkonce_odr 产出，由链接器负责合并；-Zshare-generics 可让 rustc 在 codegen 阶段就复用
可复现构建--remap-path-prefix、-Ztrim-paths（nightly），消除构建路径带来的 hash 差异

通俗解释

几百个 .rlib（Rust 库产物）→ 链接器（ld / lld / mold）合并所有 linkonce_odr 符号并重排。 fat LTO：链接器先拿到所有 crate 的 LLVM IR → 重新跑一遍优化 → 再链接。最慢，但产物通常最小最快。 换用 mold / lld 加速的是链接这一步本身（比 GNU ld 快数倍），但 LTO 的大头仍然在 LLVM 里，换链接器救不了。

opt-level = 1 或 2比 3 明显更快，多数场景运行性能损失可接受
换 mold / lld只加速链接步骤本身（数倍），LTO 时收益被稀释
sccache跨项目编译缓存，CI 与多 worktree 场景收益明显；它和 cargo 增量是两件事
workspace 拆分 + 控制在合理粒度提升并行度与增量命中率；但拆太碎会反而增加每 crate 固定开销，且跨 crate 内联要依赖 LTO
减少依赖 / 关掉默认 feature直接减少 DAG 节点与关键路径长度
少用巨型泛型、#[inline] 收敛、debug = "line-tables-only"减少后端代码量与调试信息体积
-Znext-solver（nightly）新 trait solver，部分场景更快，但别指望固定倍数，且未稳定

5. 直接回答

"Rust 编译慢是因为类型推断 + 宏展开 + 编译依赖吗？"

部分对，但更准确的分层是：

  1. 后端（LLVM codegen + 优化），而单态化把送进后端的代码量放大 N 倍 —— 这两者要合起来看，不能拆开排第一第二
  2. 依赖 DAG：几百个 crate 各自完整编译，关键路径串行，固定开销累加
  3. 前端类型检查：trait resolution + lifetime 约束求解，泛型越重越明显
  4. 宏展开：proc macro 有加载与转换开销，但属小头
  5. 链接：只开 LTO 时才是显著项

"类型推断"这个说法不准确——Rust 不是"推断慢"，而是实例化之后每个函数体都要完整编译 + 优化。Go 用 GC shape stenciling 让多数类型共享同一份实例，Rust 用完全单态化换零运行时开销，代价自然落在编译期。

6. 总结

Rust 编译慢不是单一原因：完全单态化把代码量放大 N 倍，再叠加 LLVM 后端的完整优化管线，这是最大的一块；其次是 200-500 个 crate 的构建 DAG——每个都要完整编译，关键路径还只能串行；再者是 trait + lifetime 的约束求解，比 Go 的 interface 匹配贵得多；proc macro 和链接（开 LTO 时）属于次要项。Go 快在结构上：GC shape stenciling 让泛型实例数量有限、优化策略固定且轻量、以 package 为编译单元且并行充分。想真正定位瓶颈，别靠记忆排序，用 cargo build --timings、-Zself-profile、cargo llvm-lines 实测。

Rust 生命周期到底在「确保」什么

2026-10-25
:: tags:  #Borrow Checker  #Lifetime  #Rust

先纠正我的理解

我原来的理解是「确保所有变量指向的内存是有效的」——方向对，但不够精确。

准确的说法是： 编译器确保每一个「借用」（reference/borrow），在其所有使用点上，被指向的「对象」（referent）还活着。

不是「所有变量」，而是所有引用。拥有（owned）变量天然在作用域内有效（drop 顺序保证），不需要 lifetime 额外管。

1. 生命周期到底在管什么？

一句话

Lifetime = 引用的「有效时间窗口」。编译器的工作是：证明每个 &T 的使用区间 ⊆ T 的存活区间。

专有名词

名词含义
referent（被引用对象）&T 指向的那个 T
borrow（借用）从 referent 借出一个 &T 或 &mut T
liveness（活性）变量在某个程序点上「之后还会被使用」的性质；NLL 用点集描述，不是简单时间区间
NLL（Non-Lexical Lifetimes）实际 liveness 不跟花括号走，到「最后一次使用」就结束（Rust 2018+ 默认）
region编译器内部的 lifetime 抽象，由一组 live point 组成，最终由约束求解出最小解
borrow checker编译器组件，做 liveness 分析 + 冲突检测（工作在 MIR 上）
aliasing + mutability核心规则：不能同时存在 &mut T 和 &T（或另一个 &mut T）

通俗解释

想象一个场景：

fn main() {
    let r;
    {
        let s = String::from("hello");   // s 活着（栈上）
        r = &s;                          // r 借了 s（r 的有效窗口 ⊆ s 的有效窗口）
    }                                    // s 在这里结束
    println!("{}", r);                   // ❌ `s` does not live long enough
}

报错是 error[E0597]: 's' does not live long enough。

反过来，只要 s 在外层声明，就完全合法：

let s = String::from("hello");
let r = &s;
println!("{}", r);          // ✅ s 活得比 r 久

编译器在编译期就证明：r 的某个使用点上 s 已经没了 → dangling reference → 编译不过。

不是"所有变量都有效"，而是"引用指向的东西在引用用的时候还活着"。

2. 堆 vs 栈：lifetime 管的是"谁"？

关键洞察

Lifetime 不关心 referent 在栈上还是堆上。它只关心时间关系：referent 比 reference 活得久。

// 栈上的 referent
let x = 42;                  // 栈
let r = &x;                  // r 指向栈
println!("{r}");             // ✅ x 活得比 r 久

// 堆上的 referent（Box 是栈上的所有权句柄，指向堆）
let b = Box::new(String::from("hi"));
let r = &*b;                 // r 指向堆
println!("{r}");             // ✅ b 活得比 r 久

两种情况 lifetime 检查逻辑完全一样：referent 的存活区间 vs reference 的使用区间。

所以精确答案是：

"编译器确保所有被借用的内存（不管堆栈）在引用使用期间仍然有效。"

拥有变量（owned）不需要额外检查——它们天然在作用域内有效（drop 在作用域末执行）。 需要 lifetime 检查的是引用（borrow）：你借了一个东西，编译器要证明"你用完之前，它没被释放"。

3. 编译器具体在做什么？（Borrow Checker 算法）

步骤（NLL 实现）

1. parse + 宏展开 → AST → HIR
   └── HIR 只做名字解析与高层检查，不是 borrowck 的工作对象

2. 类型检查（typeck）→ THIR → 构建 MIR
   └── borrowck 在 MIR（Mid-level IR，控制流图形式）上进行
   └── 每个变量的赋值点 + 使用点 + drop 点
       （drop 被建模成显式的 Drop terminator，这是 NLL 能"非词法"的基础）

3. 对每个 borrow（&T / &mut T），计算 liveness 区间
   └── 从借出点到最后一次使用点（不是花括号结束！）
   └── NLL 实际算的是"点集"，再用 region 约束求最小解

4. 检查冲突：
   a. dangling：borrow 的 liveness 超出了 referent 的 liveness → ❌
   b. aliasing：同一个 referent 同时有 &mut 和 & → ❌
   c. move：被借用的值被移走 → ❌
      （Send/Sync 那类跨线程约束属于 auto trait 检查，不在 borrowck 里）

5. 如果全通过 → 生成代码（不需要任何运行时检查）

通俗解释

编译器做的是静态分析（不是运行时检查）：

  • 扫一遍代码，标出每个变量的"出生"（赋值）和"死亡"（最后使用 / drop）
  • 对每个 &T，检查"我用的时候 T 还活着吗？"
  • 检查"两个 &mut 有没有重叠？& 和 &mut 有没有重叠？"
  • 全部在编译期完成，零运行时开销（没有 guard、没有 check）

和 GC 语言的对比

Rust borrow checkerGo / Java GC
检查时机编译期（静态）运行期（动态）+ 编译期逃逸分析
手段liveness 约束 + 类型系统（region inference）引用计数 / 三色标记
开销零运行时（代码里不插入任何检查）GC 停顿（STW）/ 写屏障
能证明什么"这个引用永远不会悬空""这块内存暂时还有人可达"
unsafe 逃生有（unsafe {} 可解引用裸指针，但仍须自行遵守别名规则）无（GC 兜底）

4. 几个容易搞混的点

1、 "作用域" ≠ "生命周期"

fn f() {
    let x = String::from("hello");
    {
        let y = &x;   // y 的借用从这开始
        println!("{}", y);
    } // y 本身在这 drop，但借用其实更早就结束了
    // x 还活着
}

NLL 下，y 的借用区间到最后一次使用 y 的那行结束，而不是到花括号 }。 这就是为什么 Rust 里很多"看起来该报错"的代码不报错——NLL 比"词法作用域"更精确。

再往后是 Polonius（基于 Datalog 重写的借用分析），能处理 NLL 目前仍会误报的场景（例如条件分支里提前 return 后的借用），尚未默认启用。

2、 drop(x) 不是"手动结束 lifetime"的开关

这里有个容易踩的坑：

// a. Copy 类型：drop 的是副本，x 依然有效
let x = 42;
let r = &x;
drop(x);                     // i32: Copy → 丢弃的是副本
                             // warning: calls to `std::mem::drop` with a value
                             // that implements `Copy` does nothing
println!("{r}");             // ✅ 正常输出 42，不会悬空

// b. 非 Copy 类型：move 与借用冲突，编译期就报错
let x = String::from("hello");
let r = &x;
drop(x);                     // ❌ error[E0505]: cannot move out of `x` because it is borrowed
println!("{r}");

drop(x) 的签名是 fn drop<T>(_x: T)，按值接收，所以它是一次 move（Copy 类型则是复制）。

报错点在 drop(x) 那一行，原因是"被借用的值不能 move"，不是 println! 处出现运行时悬空。

在安全 Rust 里造不出悬空引用——这正是 lifetime 的价值。想制造真正悬空，只能进 unsafe（例如 Box::into_raw 后手工释放再解引用）。

3、 生命周期 ≠ 内存位置

&'a T 里的 'a 不告诉你 T 在栈还是堆。它只说"T 至少活到 'a 结束"。 具体在栈还是堆，由 let（栈）/ Box（堆）/ static（静态区）决定。 lifetime 是时间维度，不是空间维度。

4、 所有权转移后，原变量"死"了

fn f() {
    let s = String::from("hello");
    let t = s;       // 所有权转移（move）
    // s 不能再用了（已被 move）
    let r = &s;      // ❌ error[E0382]: borrow of moved value: `s`
}

这不是 lifetime 问题，是所有权问题：s 被 move 了，不再是"有效变量"。 但效果类似：&s 在 s 被 move 后无效。注意报错码不同（E0382 vs E0597/E0505），能反过来提示你问题出在哪一层。

5、 'static 与 const 不是一回事

let s: &'static str = "literal";   // 字符串字面量本身就在静态区
const N: i32 = 42;
let r: &'static i32 = &N;          // ✅ 靠 const promotion 提升为 'static

'static 表示"这个引用可以活到程序结束"，是对引用存活时长的上界约束。 const 是编译期常量（会被内联替换），本身不是引用；&CONST 能变成 'static 是因为常量无地址敏感性（const promotion）。

5. 那"编译器能不能总是推断"？

能推断（elision）的场景

Rust 的 lifetime elision 是三条明确规定，不是"智能推断"：

  1. 每个输入引用位置各自获得独立的 lifetime 参数（fn f(&T, &U) → fn f<'a, 'b>(&'a T, &'b U)）
  2. 只有一个输入引用 → 输出 lifetime 取它
  3. 有 &self / &mut self → 输出 lifetime 取 self（规则 3 优先于规则 2）

本质：这些规则让"引用指向谁、活多久"唯一确定，无歧义。

不能推断（必须手写 'a）的场景

  • 两个以上输入引用 + 有输出引用（规则 2 不适用，规则 3 也不适用）→ 返回绑定到 a 还是 b？
  • struct / enum 含引用字段：类型定义里无法省略，必须声明 lifetime 参数（struct Foo<'a> { s: &'a str }），因为这个参数是类型本身的一部分，会参与后续所有约束求解
  • 需要表达"一个比另一个长"（'a: 'b）
  • impl 块、dyn Trait + 'a、trait 方法签名等需要显式约束的位置

本质：存在多个合法答案，而语言规范不允许编译器替你挑一个——挑错就会放过一个真实的悬空引用。

通俗类比

生命周期推断就像数学里的唯一解：

  • 一个方程一个未知数 → 唯一解，不用你标注（elision）
  • 一个方程两个未知数 → 多解，你必须给约束（手写 'a）
  • 编译器不做假设（"我猜返回绑定到第一个参数"），因为猜错就是悬空引用

6. 精确回答

"编译器是不是要确保所有变量（堆栈都行）在作用域内指向的内存是有效的？"

不完全是。 精确说法是：

  1. 拥有变量（let x = T）：有效性由所有权 + drop 顺序（逆声明序）保证，不需要 lifetime 参与。
  2. 引用 / 借用（let r = &x）：由 NLL 借用检查保证 r 的每个使用点上 x 还活着（不管 x 在栈还是堆）。这才是 lifetime 管的。
  3. 裸指针 / unsafe：编译器不检查。你自己保证。
  4. 'static：表示引用可活到程序结束，编译器直接接受，不需要额外证明。

所以：lifetime 管的是"引用的有效性"，不是"所有变量的有效性"。所有变量的有效性是所有权系统（ownership + drop）管的，lifetime 是所有权系统在"引用"这一子集上的额外约束。

7. 一张图总结

Rust 内存安全 = 所有权（Ownership） + 借用（Borrowing）

├── 所有权（owned）
│   ├── 每个值有且只有一个 owner
│   ├── drop 在作用域末（或 move 后原 owner 失效）
│   └── 不需要 lifetime 参与（"我的东西我管"）
├── 借用（borrowed，&T / &mut T）
│   ├── 需要 lifetime 证明：referent 比 reference 活得久
│   ├── 需要 aliasing 检查：&mut 独占，& 共享
│   └── 编译器在 MIR 上做 liveness 分析（NLL）
└── unsafe
    ├── 裸指针、FFI、内部可变性（UnsafeCell）
    └── 编译器不检查，你自己保证

Lifetime 只出现在"借用"层。
"拥有"层由 drop 顺序保证。
"unsafe"层由程序员保证。

8. 30 秒口述版

"Rust 的 lifetime 不是'确保所有变量有效'，而是专门管引用（borrow）：借用检查器在 MIR 上做 NLL 分析，证明每个 &T 的使用区间不超出 T 的存活区间，同时保证 &mut 独占、& 共享。拥有变量不需要 lifetime——drop 顺序保证它们在作用域内有效。裸指针（unsafe）编译器不管，你自己保证。堆还是栈不影响 lifetime 语义——lifetime 是时间维度（活多久），不是空间维度（在哪）。编译器能推断（elision）的场景由三条固定规则给出：每个输入引用独立、只有一个输入则输出继承、有 &self 则输出继承 self；规则不足以唯一确定时必须手写，因为语言不允许编译器替你猜。所有检查都在编译期完成，零运行时开销。"

Rust 的 Send 与 Sync 到底在保证什么

2026-10-25
:: tags:  #Concurrency  #Rust  #Send  #Sync

Rust 的 Send 和 Sync 是 Rust 并发编程中最重要的两个 Trait。尤其是在研究 Rust 底层系统、内存安全分析器时，理解它们能帮助你进一步理解 Rust 如何在编译期阻止数据竞争，以及 Arc、Mutex、线程之间的数据传递究竟是怎么回事。

先记住最核心的区别：

  • Send：一个值能不能安全地转移到另一个线程。
  • Sync：一个值能不能安全地被多个线程通过共享引用访问。

Rust 官方定义是：

  • T: Send：类型 T 的值可以安全地在线程之间转移。
  • T: Sync：类型 T 可以安全地在线程之间共享引用。严格来说，T: Sync 当且仅当 &T: Send。

下面从语言语义、内存模型、源码示例和底层实现逐层拆解。

一、先用一张表理解 Send 和 Sync

对比SendSync
核心问题值能否转移到另一个线程？共享引用能否被多个线程安全使用？
关注对象所有权和值的转移共享引用与并发访问
Rust 定义T: SendT: Sync 当且仅当 &T: Send
典型用途thread::spawn 传递闭包与数据多线程共享 Arc<T> 等数据
不满足时意味着什么不能安全地将该值转移到其他线程不能安全地让多个线程共享对该值的引用
是否自动实现通常是通常是

最简单的记忆方法：

  • Send = 移交所有权。
  • Sync = 安全共享引用。

不过，这只是帮助理解的直觉。Send 不代表值只能被一个线程使用，Sync 也不意味着类型内部完全没有可变状态。

二、Send：值能否跨线程转移？

2.1 从所有权开始理解

看一个简单的例子：

use std::thread;

fn main() {
    let value = String::from("hello");
    let handle = thread::spawn(move || {
        println!("{value}");
    });
    handle.join().unwrap();
}

这里有三个重要步骤。

第一步：创建 String

let value = String::from("hello");

在常见的 64 位 Rust 实现中，String 可以概念性地理解为：

String
┌─────────────────┐
│ ptr             │ ──────┐
│ len             │       │
│ capacity        │       ▼
└─────────────────┘   ┌─────────────┐
                      │ hello       │
                      │ UTF-8 bytes │
                      └─────────────┘

这只是帮助理解的示意布局，不应当把具体字段顺序或布局当成 Rust 的稳定 ABI 保证。

第二步：使用 move

thread::spawn(move || {
    println!("{value}");
});

move 使闭包取得它捕获的 value 的所有权。原线程不能再直接使用已经移交的 value。

第三步：新线程使用这个值

新线程拿到了 String，并可以读取其中的数据。

为什么这是安全的？

因为 String 实现了 Send，编译器允许它的所有权跨线程转移。

在这里，Rust 的所有权系统和 Send Trait 配合起来，保证了线程之间的值传递满足相应的安全约束。

2.2 Send 不等于复制

这里非常容易产生误解。

let value = String::from("hello");

String 并不是因为实现了 Send 才能够被复制。事实上，String 通常不实现 Copy。

这几个概念要区分开：

机制含义
Copy某些值可以按位复制，复制后原变量仍然可用
Clone类型提供显式的克隆操作
Send值可以安全地跨线程转移
Sync类型可以安全地通过共享引用跨线程访问

例如：

let value = String::from("hello");
let another = value;
// println!("{value}"); // 编译错误：borrow of moved value
println!("{another}");

这是所有权转移。

而 Send 决定这种值能否在满足其他线程约束的情况下被安全地传递到另一个线程。

三、Sync：为什么共享引用需要单独的安全保证？

现在考虑另一种情况。

我们不想把数据所有权交给新线程，而是希望多个线程同时读取同一个对象。

例如：

use std::sync::Arc;
use std::thread;

fn main() {
    let value = Arc::new(String::from("hello"));
    let a = Arc::clone(&value);
    let b = Arc::clone(&value);

    let t1 = thread::spawn(move || {
        println!("{a}");
    });
    let t2 = thread::spawn(move || {
        println!("{b}");
    });

    t1.join().unwrap();
    t2.join().unwrap();
}

这里的情况与之前不同。

我们创建了两个 Arc 智能指针，它们指向同一个底层分配的对象。

                    堆上的 String
                  ┌────────────────┐
                  │ "hello"        │
                  └────────────────┘
                          ▲
                          │
                  Arc 管理的共享分配
                          ▲
                  ┌───────┴───────┐
                  │               │
              Arc clone 1     Arc clone 2
                  │               │
               线程 1           线程 2

这时就出现了一个关键问题：

如果两个线程同时访问同一个对象，Rust 怎么知道这种访问是安全的？

答案是：需要满足相关的线程安全约束。

对于 Arc<T>，它可以安全地共享所有权，但这不意味着任意 T 都能被安全地并发访问。

要通过 Arc<T> 在不同线程之间共享数据，通常需要 T: Send + Sync。

如果只需要在不同线程之间转移一个值，而不需要共享引用，那么所需要的约束可能不同。

例如，Mutex<T> 正是为此设计的：它可以通过锁来安全地保护一个不满足 Sync 的 T，前提是 T: Send。

这说明：

  • Send 关注值的跨线程转移。
  • Sync 关注共享引用的跨线程安全性。
  • 智能指针和同步原语会组合这些约束，形成不同的线程安全能力。

四、Send 和 Sync 的数学关系

这是理解它们最重要的部分。

Rust 官方给出了一个非常精确的定义：

T: Sync  ⟺  &T: Send

换句话说：

如果类型 T 的共享引用 &T 可以安全地转移到另一个线程，那么 T 就是 Sync。

为什么？

假设：

let value: T = /* ... */;
let reference: &T = &value;

现在我们把 reference 传递给另一个线程。

线程 A                           线程 B
    T
    │
    ▼
   &T  ────────────────────────► &T

我们没有转移 T 的所有权，只是转移了一个指向它的共享引用。

如果 &T 能够安全地跨线程转移，就说明这种共享访问满足 Rust 的安全要求。

因此：

T: Sync  ⟺  &T: Send

这个关系不是一种经验规则，而是 Rust 对 Sync 的正式定义。

4.1 那么 &T: Send 需要什么条件？

&T: Send  ⟺  T: Sync

因此，下面两个结论是等价的：

T 实现 Sync
        ⇕
&T 实现 Send

这也是为什么 Send 和 Sync 必须一起理解。

4.2 &mut T 又是什么情况？

对于可变引用：

&mut T: Send  ⟺  T: Send

也就是说，只要 T 是 Send，它的独占可变引用就可以在线程之间转移。

但注意，转移 &mut T 的前提是引用的生命周期与所有权关系仍然合法。这不是说可以随意把一个普通的借用引用塞进一个 'static 的线程闭包，Rust 还需要检查生命周期。

官方文档对这些引用类型与 Send、Sync 的关系有明确说明。

五、为什么 Rc<T> 不是 Send，也不是 Sync？

这是一个理解底层实现的绝佳例子。

Rust 有两种常见的引用计数智能指针：

  • Rc<T>
  • Arc<T>

它们都可以让多个所有权句柄指向同一份堆数据，但它们的线程安全属性不同。

5.1 Rc 的基本原理

可以把 Rc<T> 的内部结构简化理解为：

Rc<T>
   │
   ▼
┌───────────────────────┐
│ strong_count: usize   │
│ weak_count: usize     │
│ value: T              │
└───────────────────────┘

这是概念模型，不是对标准库内部布局的承诺。

当你执行 Rc::clone(&a) 时引用计数会增加；当 Rc 被销毁时，引用计数会减少。如果最后一个强引用被销毁，底层值就可以被释放。

问题在于：普通 Rc 使用非原子引用计数。

如果两个线程同时修改引用计数，就可能发生数据竞争。例如：

初始 strong_count = 2
线程 A                       线程 B
读取 strong_count = 2        读取 strong_count = 2
计算 2 + 1                   计算 2 + 1
写入 3                       写入 3
最终可能错误地得到 3，而不是 4

这是一个简化的竞态示意。

实际情况下，两个线程必须先能够合法地访问同一个 Rc 内部状态，才会出现这样的竞争；Rust 正是通过 Rc 不实现 Send 和 Sync 来阻止普通安全代码构造这种跨线程共享。

因此，Rust 不允许把普通 Rc<T> 当作线程安全的共享所有权指针。

官方文档也明确指出，Rc 不实现 Send，原因之一就是它的引用计数没有使用原子操作。

六、Arc 为什么可以跨线程共享？

Arc<T> 是 Atomic Reference Counted 的缩写。

与 Rc<T> 不同，Arc<T> 使用原子操作管理共享引用计数。

use std::sync::Arc;

fn main() {
    let a = Arc::new(100);
    let b = Arc::clone(&a);
    println!("{a}");
    println!("{b}");
}

概念上：

Rc<T>：
引用计数更新
      │
      ▼
普通内存读写
      │
      ▼
不能安全地并发更新

Arc<T>：
引用计数更新
      │
      ▼
原子操作
      │
      ▼
能够安全地并发更新引用计数

不过，Arc 解决的是共享所有权与引用计数的线程安全问题，不会自动让内部的任意数据变成线程安全的。

例如：

use std::cell::RefCell;
use std::sync::Arc;

fn main() {
    let value = Arc::new(RefCell::new(10));
    // 不能直接将这个 Arc<RefCell<i32>>
    // 作为普通的 Send + Sync 共享状态传给多个线程。
}

为什么？

因为 RefCell<T> 的动态借用检查不是线程安全的同步机制。Arc 的原子引用计数无法保护 RefCell 内部的借用状态。

因此：

Arc<T>
   │
   ├── 共享所有权安全
   │
   └── 不代表 T 内部的访问自动安全

这是一个特别重要的原则。

七、Mutex 为什么能够保护一个不是 Sync 的类型？

现在我们来解决一个看似矛盾的问题。

我们知道：

  • RefCell<T> 不是 Sync。
  • Arc<T> 不能让任意类型自动变成 Sync。

但下面的类型却可以用于多线程共享：

Arc<Mutex<RefCell<T>>>

只要 T 满足适当的条件，例如 T: Send。

这是为什么？

因为 Mutex 提供了独占访问。

这个组合在工程上其实是冗余的（Mutex 已经提供了互斥，内层的 RefCell 没有意义）。这里只是用它演示类型系统的推导路径。

先看一个更简单的例子：

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = Vec::new();

    for _ in 0..4 {
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            let mut value = counter.lock().unwrap();
            *value += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("{}", *counter.lock().unwrap());
}

输出：

4

这个例子使用了三个机制：

  1. Arc：多个线程共享同一个锁对象的所有权。
  2. Mutex：保证同一时刻只有一个线程通过锁访问受保护的值。
  3. Send 和 Sync：确保相关类型可以在线程之间安全地传递和共享。

Mutex<T> 的关键特性是：

  • 如果 T: Send，那么 Mutex<T> 可以实现 Send。
  • 如果 T: Send，那么 Mutex<T> 可以实现 Sync。

注意这里需要的是 T: Send，而不是必须要求 T: Sync。

为什么？

因为 Mutex 通过独占访问保护内部数据。它不要求多个线程能够直接同时访问 &T。

Rust 标准库的文档明确解释了 Mutex<T> 的这些约束。

7.1 Mutex 的底层逻辑

可以把访问过程理解为：

线程 A                         线程 B
   │                              │
   ▼                              ▼
lock()                         lock()
   │                              │
   ▼                              ▼
获得锁                         等待锁
   │                              │
   ▼                              │
访问 T                           │
   │                              │
   ▼                              │
释放锁                            │
                                  ▼
                               获得锁
                                  │
                                  ▼
                                访问 T

Mutex 并没有把 T 变成一种天然可以同时读写的类型。它只是建立了一种同步规则，让不同线程通过受保护的访问路径操作 T。

这也是 Rust 并发模型的一个核心思想：

线程安全不仅依赖数据类型本身，还可以通过正确的同步原语来建立。

八、Send 和 Sync 为什么会自动实现？

你可能注意到，Rust 程序里经常不需要手动为结构体实现 Send 和 Sync。

例如：

struct User {
    id: u64,
    name: String,
}

这个结构体通常自动实现 Send 和 Sync。

为什么？因为它的字段 u64、String 都满足对应的线程安全条件。

Rust 将这种机制称为 Auto Traits。Send 和 Sync 都是 Auto Traits。

编译器会根据类型的组成部分判断它们是否适合自动实现这些 Trait。可以把规则概念化为：

struct User {
    id: u64,
    name: String,
}

编译器检查：

u64:    Send + Sync
String: Send + Sync

因此，通常可以推导出：

User: Send + Sync

再看另一个例子：

use std::rc::Rc;

struct User {
    data: Rc<String>,
}

由于 Rc<String> 不满足 Send 和 Sync 的要求，这个 User 通常也不会自动实现它们。

这就是 Auto Trait 的重要特点：

一个结构体是否能够跨线程传递和共享，往往取决于它内部所有字段的线程安全属性。

九、哪些常见类型实现 Send 和 Sync？

下面这张表非常实用。

类型SendSync说明

Vec<T>当 T: Send 时当 T: Sync 时取决于元素类型
Box<T>当 T: Send 时当 T: Sync 时取决于内部类型
Rc<T>否否非原子引用计数

这张表中的条件比单纯的「是」或「否」更重要。

例如：

Vec<Rc<String>>

因为 Rc<String> 不实现 Send，所以这个 Vec 也不会自动实现 Send。

但：

Vec<String>

通常可以安全地跨线程转移。

十、一个容易混淆的细节：为什么 &mut T 也可能是 Sync？

这个问题非常值得单独讲。

你可能会认为：

&mut T 可以修改数据，所以如果它是 Sync，多个线程岂不是能同时修改同一个对象？

这里忽略了 Rust 对引用的约束。

首先，&mut T 代表独占可变引用。在安全 Rust 中，同一时间不能随意创建多个指向同一个对象的独占可变引用。

其次，Sync 的含义是：可以安全地在线程之间共享对这个类型的引用。

当我们有：

&&mut T

时，外层引用是共享引用。通过这个共享引用，不能直接取得内层 &mut T 的独占访问权，它不会允许你随意修改 T。

因此，在满足 T: Sync 的条件下，&mut T 可以实现 Sync。

更准确的关系是：

&T: Send      ⟺  T: Sync
&mut T: Send  ⟺  T: Send
&T: Sync      ⟺  T: Sync
&mut T: Sync  ⟺  T: Sync

这正是 Rust 引用模型与 Send、Sync 相互配合的结果。

十一、为什么原始指针默认不是 Send 和 Sync？

例如：

let ptr: *const i32;

你可能会想：指针只不过是一个内存地址，为什么不能直接跨线程传递？

因为指针本身不能证明它指向的对象是否满足线程安全要求。

例如：

struct RawData {
    ptr: *mut i32,
}

这个结构体包含一个可变原始指针。编译器无法仅凭这个字段判断：

  • 指针是否有效。
  • 指针指向的数据是否还活着。
  • 是否存在其他别名。
  • 其他线程是否正在修改同一块内存。
  • 是否存在数据竞争。

因此，Rust 的原始指针默认不实现 Send 和 Sync。这样可以防止包含原始指针的结构体被自动判定为线程安全。

这并不是说原始指针永远不能用于多线程，而是说：如果要让包含原始指针的类型跨线程安全使用，开发者必须通过适当的抽象和安全保证来证明其行为。

Rust 官方的 Nomicon 对此有详细说明。

十二、Send 和 Sync 是怎么在编译期起作用的？

现在我们看一个典型的编译错误。

use std::rc::Rc;
use std::thread;

fn main() {
    let value = Rc::new(100);
    thread::spawn(move || {
        println!("{value}");
    });
}

这段代码不能通过编译，报错是：

error[E0277]: `Rc<i32>` cannot be sent between threads safely

原因不是 move 写错了，也不是 Rc 不能被移动——你完全可以在同一个线程内移动一个 Rc 的所有权。

问题在于：thread::spawn 要求闭包满足相应的 Send 约束，而这个闭包捕获了不满足 Send 的 Rc<i32>。

概念上，thread::spawn 的签名可以简化理解为：

fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,
{
    // ...
}

这不是完整源码，只是为了展示关键约束。

这里 F: Send 意味着闭包本身必须可以安全地传递到新线程；而闭包是否实现 Send，通常取决于它捕获的值。

因为 Rc<i32> 不实现 Send，所以这个闭包不能满足约束，编译器就在编译期拒绝了这段代码。

如果改成：

use std::sync::Arc;
use std::thread;

fn main() {
    let value = Arc::new(100);
    let handle = thread::spawn(move || {
        println!("{value}");
    });
    handle.join().unwrap();
}

就可以正常编译。Arc<i32> 满足相关线程安全约束，因此闭包能够传递到新线程。

这就是 Send 的实际价值：它不是运行时检查，而是编译期的线程安全约束。

十三、Send 和 Sync 是 unsafe Trait，意味着什么？

Send 和 Sync 都是 unsafe auto trait。

这意味着：

  1. 它们是编译器可以自动推导的 Trait。
  2. 开发者在特殊情况下可以手动实现它们。
  3. 手动实现时，必须确保类型确实满足相应的线程安全保证。

例如：

struct MyType {
    // 某些底层数据
}

理论上，你可以为自定义类型手动实现 Send：

unsafe impl Send for MyType {}

但如果你的类型内部存在不安全的共享可变状态，而你错误地声称它是 Send 或 Sync，就可能让安全 Rust 程序产生未定义行为。

因此，不能把它们当作普通的标记随便添加。

对于普通业务代码，通常不需要手动实现这两个 Trait。让编译器根据字段自动推导，往往是更安全的方式。

只有在封装底层资源、原始指针或特殊并发结构时，才需要认真考虑手动实现的必要性。

十四、放到 Rust 系统开发中，应该怎么理解？

结合底层系统和分析器项目，可以这样理解。

假设你需要构建一个多线程的代码分析任务系统，每个任务包含：

struct AnalysisTask {
    id: u64,
    source: String,
}

这个类型通常可以实现 Send + Sync。因此，你可以：

  • 把一个任务转移给工作线程。
  • 将不可变的任务数据共享给多个分析线程。
  • 在满足其他所有权与生命周期条件的情况下，使用 Arc<AnalysisTask> 共享任务。

如果任务状态需要并发修改，可以使用：

use std::sync::{Arc, Mutex};

struct TaskState {
    status: String,
}

let state = Arc::new(Mutex::new(TaskState {
    status: "ready".to_string(),
}));

这时：

  • Arc 负责共享所有权。
  • Mutex 负责同步对任务状态的访问。
  • Send 和 Sync 负责在类型层面约束跨线程使用是否合法。

不过，如果任务对象本身包含非线程安全的资源，例如某些线程绑定的句柄，那么它可能无法直接满足 Send。

这时应当考虑让资源留在所属线程，由其他线程发送消息请求它执行操作，而不是强行把资源跨线程移动。

这种设计在编译器服务、运行时、事件循环和 Agent Scheduler 中都很常见。

十五、最后用三个问题彻底记住它们

以后遇到 Rust 并发问题，可以依次问自己三个问题。

问题一：这个值能不能被移动到另一个线程？

看 T: Send。如果不满足，检查它是否包含 Rc、非线程安全的内部可变状态、原始指针或其他不能自动跨线程转移的成员。

问题二：这个对象能不能被多个线程通过共享引用访问？

看 T: Sync。如果不满足，检查它是否存在没有适当同步保护的内部可变状态。

问题三：我究竟需要转移所有权，还是共享同一个对象？

  • 只需要把值交给另一个线程：重点关注 Send。
  • 需要多个线程共享同一份数据：通常需要 Sync，并根据共享方式使用 Arc、Mutex 或 RwLock。
  • 需要多个线程修改共享状态：必须使用适当的同步机制，不能仅凭 Arc 就认为线程安全。

最后浓缩成一句话：

Send 保证值可以安全地跨线程转移；Sync 保证共享引用可以安全地跨线程传递。Rust 再通过所有权、借用、自动 Trait 推导和同步原语，把大量线程安全问题提前到编译期检查。

一、Safe Rust 与 Unsafe Rust 的边界

先纠正一个常见误解：

unsafe 不代表这段代码不安全，而是代表编译器无法替你证明某些操作满足安全条件，需要程序员承担证明责任。

安全 Rust：

fn main() {
    let x = 42;
    let r = &x;
    println!("{r}");
}

编译器能验证引用的使用满足安全规则。

需要 unsafe：

fn main() {
    let x = 42;
    let ptr = &x as *const i32;
    unsafe {
        println!("{}", *ptr);
    }
}

通过原始指针读取数据需要 unsafe。但这并不意味着它一定不安全——只要指针有效、对齐正确、指向有效的 i32、且访问满足别名与生命周期要求，这次读取就是合法的。

反过来，代码里出现 unsafe 也不代表程序员已经证明了它的正确性。

1.1 unsafe 究竟允许做什么

操作为什么需要 unsafe
解引用原始指针编译器无法保证指针有效
调用 unsafe fn调用者必须满足函数的安全契约
访问 static mut编译器无法保证全局访问的线程安全
实现 unsafe trait实现者必须保证满足该 trait 的安全契约
使用底层内存操作必须保证内存状态、初始化状态与类型不变量正确

unsafe 并不关闭 Rust 的所有检查。下面这段没有任何需要 unsafe 的操作，类型检查、借用检查照常执行：

unsafe {
    let x: i32 = 10;
    let y = x + 20;
}

更准确地说，Rust 的安全模型要求：即使一个库内部使用了 unsafe，它暴露给调用者的安全 API 也不应该允许安全 Rust 代码触发未定义行为（UB）。这就是底层库必须重视安全抽象的原因。

二、谁负责证明安全

理解 unsafe，最好从调用关系切入：

unsafe fn read_value(ptr: *const i32) -> i32 {
    *ptr
}

传入的 ptr 一定有效吗？不一定。调用者可能传入空指针、已释放的地址、未对齐的地址、未初始化的内存，或指向其他类型对象的地址。

因此这个函数有一个隐含的安全契约：调用者必须保证指针满足解引用所需的全部条件。

把契约写出来：

/// # Safety
///
/// `ptr` 必须指向一个有效、正确对齐且已初始化的 i32，
/// 并且读取操作必须满足 Rust 的内存安全规则。
unsafe fn read_value(ptr: *const i32) -> i32 {
    unsafe { *ptr }
}

这里要区分两个层次：

  1. unsafe fn：调用者承担满足安全契约的责任。
  2. 函数内部的 unsafe 块：实现者确保其中的操作符合要求。

Rust 2024 Edition 起，unsafe fn 内部的 unsafe 操作需要显式写成 unsafe {} 块（unsafe_op_in_unsafe_fn 在该 edition 默认开启警告），以便把安全边界画清楚。

一句话概括：unsafe 把部分安全责任从编译器转移给程序员，但不会取消这些操作必须满足的安全要求。

2.1 对外安全，对内 unsafe

/// 读取一个有效的 i32。
///
/// # Safety
///
/// 调用者必须保证 ptr 指向有效、正确对齐且已初始化的 i32。
pub unsafe fn read_raw(ptr: *const i32) -> i32 {
    unsafe { *ptr }
}

/// 读取一个普通引用指向的 i32。
pub fn read_ref(value: &i32) -> i32 {
    *value
}

第二个函数不需要 unsafe，因为 &i32 本身携带了更强的有效性保证。

安全抽象的基本思想：

  • 尽可能用安全类型表达约束；
  • 把必须使用的 unsafe 限制在较小的内部区域；
  • 在安全 API 的入口检查必要条件；
  • 不把无法验证的假设留给普通调用者。

三、原始指针

特征引用 &T / &mut T原始指针 *const T / *mut T
默认可以为空否是
编译器验证有效性有较强保证不保证
携带生命周期信息是不携带
解引用是否需要 unsafe通常不需要需要
常见用途普通 Rust 代码FFI、底层内存操作、互操作
let value = 100;
let reference: &i32 = &value;
let raw_ptr: *const i32 = &value;

两者都能指向 value，但契约不同：引用表示「这是一个满足 Rust 引用规则的借用」；原始指针只提供地址层面的信息——「这里可能有一个地址，但你不能仅凭类型认定它有效」。

原始指针没有生命周期，不代表它可以安全地长期保存：

let ptr: *const i32;
{
    let value = 42;
    ptr = &value;
}
// value 已离开作用域，ptr 不能再被安全解引用

原始指针允许绕过部分静态生命周期检查，但不会改变底层内存的真实生命周期。

四、协变、逆变、不变

Variance 只需抓住一个问题：当一个类型包含另一个类型时，内部类型的关系能不能传递到外部类型？

4.1 先理解子类型关系

let long: &'static str = "hello";

fn print_str<'a>(value: &'a str) {
    println!("{value}");
}

'static 表示引用指向的数据至少存活到程序结束。因为字符串字面量拥有 'static，它也可以当作较短生命周期的引用来用：

'static <: 'a

'long <: 'short 的含义是：较长的生命周期满足较短生命周期所要求的存活范围。这不是把变量的生命周期真的缩短了，而是说它可以在需要较短生命周期的上下文中使用。

4.2 协变 Covariance

若 T1 <: T2 能推出 F<T1> <: F<T2>，则 F 对 T 协变——内部类型可以往更宽松的方向变，外部类型跟着变。

最常见的例子是共享引用：&'a T 对 'a 协变。

fn print_str<'a>(s: &'a str) {
    println!("{s}");
}

fn main() {
    let value: &'static str = "hello";
    print_str(value);
}

拥有型容器通常也对 T 协变：Box<T>、Vec<T>。例如 Vec<&'static str> 在类型约束满足时可以转成 Vec<&'a str>——转换后只是放弃了对更长生命周期的保证，并没有凭空制造出更长的生命周期。

4.3 不变 Invariance

即使 T1 <: T2，也推不出 F<T1> <: F<T2>。最重要的例子是 &mut T，它对 T 不变。

为什么？因为 &mut T 既能读也能写。假如允许：

&mut &'static str  ->  &mut &'a str

而 'static <: 'a 看起来合理，但会出问题：

fn assign<T>(slot: &mut T, value: T) {
    *slot = value;
}

fn main() {
    let mut hello: &'static str = "hello";
    {
        let world = String::from("world");
        assign(&mut hello, world.as_str());
        // 若允许把短生命周期引用写进承诺保存 'static 的位置，
        // 就会在 world 释放后留下悬垂引用
    }
    println!("{hello}");
}

这段代码会因生命周期约束而编译失败。它展示的是「为什么不能允许这种转换」，不是可编译的漏洞示例。

核心原因：可变引用既是读通道也是写通道，允许内部生命周期随意变化会破坏写入的安全性。

4.4 逆变 Contravariance

若 T1 <: T2，对逆变的 F 有 F<T2> <: F<T1>。

Rust 中最典型的是函数参数：

fn accept_any_str(_: &str) {}
fn accept_static_str(_: &'static str) {}

如果调用方需要一个能接收任意 'static 字符串的函数，accept_any_str 也能满足——它接受的范围更宽。反过来不行：只能接收 'static 的函数，无法替代需要接收任意有效字符串的函数。

所以函数参数位置是逆变的，返回值位置是协变的：

fn(T) -> U
T：逆变
U：协变

4.5 型变速查表

类型对生命周期的型变对 T 的型变
&'a T协变协变

Box<T>—协变

注意：生命周期型变与类型参数型变是两个维度。&'a mut T 对 'a 协变，但对 T 不变。

五、型变对 unsafe 与 FFI 的意义

unsafe 代码经常绕过编译器平时用来保护生命周期的约束，所以必须自己守住型变规则。

struct MyPointer<T> {
    ptr: *mut T,
}

*mut T 对 T 不变，所以 MyPointer<T> 通常也因为该字段而对 T 不变。

这意味着：

MyPointer<&'static str>  ->  MyPointer<&'a str>

不能仅凭内部生命周期的子类型关系推导出来。因为原始指针可能被用于写入——错误地允许转换，就可能把短生命周期引用写进仍被认为保存着长生命周期引用的位置。这与 &mut T 不变是同一个安全考量。

但要分清：型变规则不会验证原始指针是否有效，也不会让 unsafe 操作变安全，它只是限制哪些类型转换成立。设计底层封装时，下面这些条件必须同时成立：

  • 类型参数的型变；
  • 生命周期约束；
  • 指针有效性；
  • 对齐要求；
  • 内存初始化；
  • 别名与可变性；
  • 所有权与释放时机。

六、FFI 基础

FFI 是 Foreign Function Interface。

// math.c
int add(int a, int b) {
    return a + b;
}
unsafe extern "C" {
    fn add(a: i32, b: i32) -> i32;
}

fn main() {
    let result = unsafe { add(10, 20) };
    println!("{result}");
}

两个关键点：

extern "C" 指定 C ABI。ABI 不只是函数名，还包括参数如何传递、返回值如何返回、调用约定等。

unsafe 因为 Rust 编译器无法验证外部实现是否符合声明：实际参数类型是否一致、签名是否准确、外部函数是否访问非法内存、是否满足线程安全约束。

这里 i32 与 C 的 int 在常见平台相符，但不能泛化到所有 C 类型。真实项目应按目标平台使用 std::ffi::c_int 等准确类型。

6.1 repr(C)

普通 Rust 结构体不保证 C 布局：

struct Point {
    x: f64,
    y: f64,
}

如果要直接传给 C，需要：

#[repr(C)]
struct Point {
    x: f64,
    y: f64,
}

但 #[repr(C)] 只解决布局兼容，它不意味着：

  • 任意 Rust 类型都能安全传给 C；
  • 所有字段自动具有 C 兼容性；
  • 任意指针都有效；
  • 所有权与释放责任会自动协调。

6.2 字符串是经典陷阱

Rust 的 String 与 C 的 char * 不是同一种东西：Rust 字符串不以 NUL 结尾，C 字符串依赖 \0 确定结束位置。所以不能随便把 String 的内部指针当成合法 C 字符串。

use std::ffi::CString;

fn main() {
    let text = CString::new("hello").unwrap();
    let ptr = text.as_ptr();
    // 在 text 仍然存活时，可以把 ptr 交给符合约定的 C API
    // 但不能在 text 被释放后继续使用 ptr
}

关键不在转换语法，而在指针有效期必须覆盖外部代码使用它的整个期间。如果 C 函数会保存指针供稍后使用，仅仅在调用期间保持 CString 存活就不够。此外 C API 还可能要求调用者提供缓冲区、长度或释放函数——这些都是 FFI 安全契约的一部分。

七、跨语言最危险的失配

最常见的错误不是函数声明本身，而是双方对所有权、生命周期和线程安全的理解不一致。

int *get_data(void);
unsafe extern "C" {
    fn get_data() -> *mut i32;
}

仅凭签名，无法知道：

  1. 返回的指针是否可能为空？
  2. 数据由谁分配？
  3. 数据由谁释放？
  4. 内存有效多久？
  5. 其他线程能否同时修改？
  6. 是否有特殊的对齐或布局要求？

这正是成熟 FFI 库要在原始指针外面再包一层安全接口的原因：把约定用类型系统表达出来，而不是把裸指针直接暴露给所有调用者。

型变不是纯理论，它是类型系统维护生命周期安全的一部分；FFI 则是类型系统无法完全控制外部代码时，安全契约变得格外重要的场景。Rust 能检查引用是否满足生命周期约束，但不能只凭一个 C 函数声明就证明 C 实现在返回后不会继续使用已失效的指针。

九、设计原则：把 unsafe 限制在边界内

核心原则一句话：对外提供尽可能安全、符合 Rust 习惯的 API；对内集中处理指针、内存布局、生命周期与外部调用。

一个好设计通常分三层：

┌──────────────────────────────────────────┐
│              Safe API                    │
│                                          │
│  fn analyze(input: &[u8]) -> Result<...> │
│  fn close(&mut self) -> Result<()>       │
├──────────────────────────────────────────┤
│        Safety / Ownership Layer          │
│                                          │
│  参数验证、所有权管理、生命周期管理      │
│  错误转换、资源释放、线程安全约束        │
├──────────────────────────────────────────┤
│           Unsafe / FFI Layer             │
│                                          │
│  原始指针、extern "C"、repr(C)           │
│  C ABI、内存布局、外部资源管理           │
└──────────────────────────────────────────┘

不要在整个项目里到处散落：

unsafe {
    external_function(ptr, len);
}

而是建立一个独立的底层模块集中外部调用，再由安全接口向上层提供功能。三个好处：

  1. 缩小审计范围：需要重点审查的 unsafe 代码更集中。
  2. 隔离外部约定：C 的所有权和生命周期规则不必渗透整个 Rust 项目。
  3. 提高可测试性：上层业务逻辑可以在不依赖真实 C 库的情况下测试。

十、设计 unsafe API 前先回答五个问题

问题需要确定什么
1. 为什么需要 unsafe？是否真的需要原始指针、外部调用或手动内存操作？
2. 谁负责保证安全？调用者负责，还是封装内部负责？
3. 安全条件是什么？指针有效、对齐、初始化、生命周期、别名等约束
4. 哪些条件能自动验证？能否用安全类型、长度检查、状态检查消除部分风险？
5. 如何验证实现正确？单元测试、边界测试、Miri、Sanitizer 如何组合？

其中最关键的是第二个。

10.1 两种完全不同的设计

方案 A：由调用者保证安全

/// # Safety
///
/// `ptr` 必须指向一个有效、正确对齐且已初始化的 i32，
/// 并且读取期间必须满足 Rust 的内存安全规则。
pub unsafe fn read_raw(ptr: *const i32) -> i32 {
    // SAFETY: 函数调用者必须满足上面声明的安全契约。
    unsafe { *ptr }
}

这个接口把部分安全责任交给调用者，适用于底层库确实需要开放原始指针操作的场景。但文档里的契约必须完整——仅仅说「指针有效」不够，还要覆盖读取期间的有效性、初始化、对齐和别名规则。

方案 B：由封装层保证安全

pub fn read_ref(value: &i32) -> i32 {
    *value
}

调用者不需要自行证明指针有效性，因为安全引用已经携带更强的约束。

结论：能用安全类型表达约束，就不要把不必要的安全责任交给调用者。 但这不意味着所有原始指针都要藏起来——如果调用者确实需要控制指针生命周期、与外部 API 交互或自行管理资源，提供明确的 unsafe 接口是合理的。

十一、安全不变量

安全不变量（Safety Invariant）：为保证代码不产生 UB，某些条件必须在对象的整个相关生命周期内始终成立。

包装 C 资源时，例如：

pub struct Engine {
    handle: NonNull<CEngine>,
}

我们希望它满足：

  1. handle 非空。
  2. handle 指向有效的 C 引擎对象。
  3. 该对象只有一个负责释放它的所有者。
  4. 对象释放后不允许再访问。
  5. 所有 C API 调用遵循该库的线程安全约束。
  6. 如果 C API 要求先销毁子对象，析构必须遵循正确顺序。

这些不变量决定了实现形态：

impl Engine {
    pub fn new() -> Result<Self, EngineError> {
        // 1. 调用 C API 创建对象
        // 2. 检查返回值和错误状态
        // 3. 检查句柄是否为空
        // 4. 成功后构造 Engine
        todo!()
    }

    pub fn execute(&mut self, input: &[u8]) -> Result<(), EngineError> {
        // 1. 验证输入是否符合 C API 约定
        // 2. 调用内部 FFI 包装
        // 3. 把错误状态转换成 Rust 错误
        todo!()
    }
}

impl Drop for Engine {
    fn drop(&mut self) {
        // 按 C API 约定释放资源
    }
}

两点必须记住：

  • NonNull<T> 只表达非空，不会保证地址有效、内存未释放或对象类型正确。
  • Drop 不能修复错误的所有权设计。如果外部代码提前释放了句柄，Drop 再次释放就是双重释放。资源所有权必须在 API 设计阶段定清楚，而不是在析构函数里补救。

负责 C ABI 声明、绑定生成、C 类型与 Rust FFI 类型映射、原始指针与句柄、外部库链接。

use std::ffi::c_int;

#[repr(C)]
pub struct CEngine {
    _private: [u8; 0],
}

unsafe extern "C" {
    pub fn engine_create(out: *mut *mut CEngine) -> c_int;
    pub fn engine_destroy(engine: *mut CEngine);
    pub fn engine_run(
        engine: *mut CEngine,
        data: *const u8,
        len: usize,
    ) -> c_int;
}

[u8; 0] 是表达「不透明类型」的惯用法。真实项目必须以 C 头文件和实际实现为准：C 的 size_t 应映射为 usize 或合适的 FFI 类型，返回值、指针可空性和错误码都必须与 ABI 一致。

另外，#[repr(C)] 不会让 Rust 结构体自动变成 C++ 对象。复杂的 C++ 类通常应该通过一个 C ABI 桥接层暴露不透明句柄，而不是直接跨 ABI 传递类实例。

分析流程、图构建、业务规则、结果处理、算法实现。这样底层 C++ 引擎变化时，业务层不需要了解指针、析构顺序和 ABI。

返回的指针可能指向引擎内部的缓冲区，不能直接转成拥有所有权的 Vec<u8>：Vec<u8> 的析构会释放它自己拥有的内存，而这块内存可能由引擎管理。误当成 Rust 分配的内存就会非法释放。

先确定契约：

  • 指针是否可能为空？
  • 长度由谁提供？
  • 指针何时失效？
  • 下次调用 API 是否会覆盖缓冲区？
  • 销毁引擎后指针是否仍然有效？
  • 是否允许其他线程同时修改？

零拷贝不是默认更好的设计。先保证契约正确，再谈性能。

十四、什么时候该 unsafe impl Send / Sync

pub struct Engine {
    handle: NonNull<ffi::CEngine>,
}

它能否跨线程移动、能否被多线程共享，取决于 C 引擎本身的线程安全契约，而不是「Rust 代码能不能编译通过」。

14.1 不要为了方便就实现

// 仅为说明语法
unsafe impl Send for Engine {}

实现 Send 是在承诺：把 Engine 的所有权转移到另一个线程不会破坏安全保证。实现 Sync 是在承诺：多线程通过共享引用访问它不会造成数据竞争。

如果 C 引擎内部有未同步的全局状态，或要求所有操作都发生在创建它的线程，随意实现这两个 trait 就会破坏安全性。

几个容易忽略的点：

  • C API 文档说「线程安全」，不一定意味着每个句柄都能被并发访问；
  • 支持多线程创建多个对象，不等于允许多线程同时操作同一个对象；
  • 加一个 Mutex 也解决不了线程亲和性、回调重入或外部资源的全局约束。

如果引擎只支持单线程，最好的方案通常是保留这个限制；确实需要跨线程时，把资源放进专用工作线程，通过消息传递调用它。只有在完整理解外部库并发契约、并证明封装维持了这些约束之后，才应该手动实现 Send / Sync。

十五、如何写安全注释

每个关键的 unsafe 操作都应有对应的安全说明。这样写没有信息量：

// SAFETY: Safe to call.

有用的注释要回答：

  • self.handle 为什么仍然有效？
  • input.as_ptr() 指向的内存能否覆盖整个调用期间？
  • input.len() 是否与实际缓冲区长度一致？
  • C 函数是否会保存该指针？
  • C 函数是否可能并发修改这块内存？
// SAFETY:
// - self.handle 由 Engine 持有，且在本次调用期间保持有效。
// - input 是有效的 Rust slice，指针和长度来自同一个 slice。
// - C API 只在本次调用期间读取 input，不保存该指针。
// - Engine 的访问方式满足底层 C API 的线程安全要求。
let result = unsafe {
    ffi::engine_run(
        self.handle.as_ptr(),
        input.as_ptr(),
        input.len(),
    )
};

这些说明依赖真实的 C API 契约。如果 C 函数会保存输入指针，第三条就不成立，设计也必须改变。

十六、如何测试 unsafe / FFI 模块

普通单元测试不够：很多内存安全错误不会立即崩溃，甚至只在特定优化或时序下暴露。

测试类型重点
正常路径合法输入、创建、调用、释放
边界测试空输入、零长度、超大长度、异常返回值
生命周期测试重复释放、缓冲区失效、析构顺序、回调晚到
并发测试多线程调用、竞争访问、线程退出与资源释放

工具层面：

  1. Miri：检测部分 Rust UB，包括无效指针访问、未初始化内存访问、别名规则违规。但不能证明整个程序正确，也替代不了真实 C/C++ 库的集成测试。
  2. Sanitizer（ASan 等）：检查越界访问、释放后使用。覆盖范围受编译方式、运行环境和错误类型影响。
  3. FFI 集成测试：真实调用 C/C++ 库，验证 ABI 声明、资源创建销毁是否匹配、字符串与缓冲区是否按契约传递、回调是否可能在对象释放后发生、错误路径是否正确处理。
  4. Fuzzing：适合解析器、二进制接口、跨语言输入验证，找边界输入引发的崩溃与状态错误。

测试可以增加信心，但替代不了安全契约的设计与推理。

十七、把方法用于跨语言分析器

分析器遇到这样的跨语言调用时：

Rust
  │
  │ 传递 *mut Buffer
  ▼
C/C++
  │
  ├── 读取 Buffer
  ├── 可能保存指针
  ├── 可能修改内容
  └── 可能释放资源

不能仅看到 unsafe 就认定有漏洞，也不能仅看到 #[repr(C)] 就认为安全。应该回答：

维度关键问题
ABIRust 声明与实际 C 函数签名是否匹配？
布局传递的结构体是否采用兼容布局？
所有权哪一方负责释放内存？
生命周期外部函数是否保存了可能失效的指针？
别名是否存在违反 Rust 引用规则的读写访问？
线程安全是否存在跨线程数据竞争或非法共享？
错误路径创建失败、回调失败或提前退出时资源是否正确释放？

更系统的做法是把每个 FFI 函数抽象成一份契约：

Function Contract
├── ABI
├── Argument Constraints
├── Pointer Validity
├── Ownership Transfer
├── Lifetime / Retention
├── Mutability / Aliasing
├── Thread Safety
├── Callback Behavior
└── Error / Cleanup Behavior

这比扫描 unsafe 关键字更有价值：unsafe 是风险信号，不是漏洞结论，真正的漏洞取决于具体操作是否违反安全契约。

十八、设计检查清单

A. 设计阶段

  • 是否确实需要 unsafe？有没有现成的安全 API？
  • 所有权、生命周期、线程安全契约是否明确？
  • 外部函数的真实 ABI 是否明确？
  • 错误处理和资源释放规则是否明确？

B. 实现阶段

  • 是否尽量缩小了 unsafe 块？
  • 每个关键 unsafe 操作是否有具体的 SAFETY 注释？
  • 是否避免在没有充分证明时使用 transmute？
  • 是否避免为了方便而随意实现 Send / Sync？
  • 是否避免把外部资源误包装成 Rust 拥有的内存？
  • 是否考虑了 panic、回调、析构、重入等异常路径？

C. FFI 专项

  • C 类型与 Rust 类型是否匹配？
  • 结构体是否需要 #[repr(C)]？
  • 可空指针是否正确处理？
  • 字符串是否满足 NUL 终止约定？
  • 输入指针是否可能被外部代码保存？
  • 返回的指针由谁释放？
  • 外部函数是否可能修改 Rust 借用的数据？
  • C++ 异常与 Rust panic 是否可能跨越不允许展开的 ABI 边界？

D. 验证阶段

  • 是否覆盖正常路径与错误路径？
  • 是否测试空指针、零长度和边界长度？
  • 是否验证重复释放和生命周期错误？
  • 纯 Rust 的 unsafe 代码是否通过 Miri？
  • C/C++ 边界是否做了真实集成测试？
  • 是否考虑 Sanitizer 或 Fuzzing？

总结

把这一部分学扎实，最终要形成四种能力：

  1. 读懂 unsafe 代码：理解原始指针、型变、生命周期和别名规则。
  2. 设计 FFI：正确处理 ABI、内存布局、所有权与跨语言调用。
  3. 构建安全抽象：把底层操作包装成调用者不容易误用的 API。
  4. 审计与验证：明确安全契约，用测试工具与代码审查验证实现。

好的 unsafe 代码不是把 unsafe 写得更少就够了，而是让每一个无法由编译器证明的安全条件，都有明确的责任主体、清晰的契约和可审查的实现。

Rust 的所有权体系是理解 Drop、Drop Check、PhantomData 与资源管理的基础，也是把生命周期、型变、unsafe 与 FFI 串起来的那条主线。

二、Ownership：所有权究竟解决什么问题？

先看一个 C 语言中常见的问题：

int *p = malloc(sizeof(int));
*p = 42;
free(p);
printf("%d\n", *p); // Use After Free

p 保存着一个地址，但 free(p) 之后，原来的内存已经不再属于这个对象。如果继续解引用 p，就可能产生未定义行为。

问题的根源是什么？

指针本身并没有表达谁负责这块内存，也没有自动阻止内存释放之后继续使用指针。

Rust 的所有权机制就是为了解决这类问题：

fn main() {
    let value = Box::new(42);
    println!("{value}");
} // value 离开作用域，堆内存被释放

Box<i32> 拥有堆上的 i32。当 value 离开作用域时，Rust 会执行相应的析构过程，最终释放这块堆内存。

这里的关键并不是 Rust 具有自动析构功能，而是：

  1. value 是资源的所有者。
  2. 所有权不能被随意复制。
  3. 所有权转移之后，原来的变量不能再使用该值。
  4. 当拥有资源的值被正确析构时，资源会得到相应清理。

因此，Rust 能够在编译阶段阻止许多释放后使用和重复释放的问题。

2.1 为什么 Box 可以移动，却不会重复释放？

看下面的代码：

fn main() {
    let a = Box::new(42);
    let b = a;
    println!("{b}");
    // println!("{a}"); // 编译错误：borrow of moved value
}

执行 let b = a; 之后，所有权从 a 转移给 b。可以将其理解为：

移动之前：
a ──────> 堆上的 i32
b 不存在

移动之后：
a 已经不能再使用
b ──────> 堆上的 i32

需要注意，移动通常不意味着复制整个堆对象。

对于 Box<i32>，移动主要涉及所有权和指针值的转移；堆上的整数本身并不需要因此重新分配。

当 b 离开作用域时，Rust 才会执行这份资源的析构。

Rust 的移动语义保证同一份拥有型值不会被两个普通所有者同时析构。

当然，这个保证有适用范围。使用 unsafe、手动管理原始指针或违反外部 API 契约，仍然可能破坏内存安全。

三、Move、Copy、Clone：这三个概念必须分清

它们看起来相似，但语义完全不同。

3.1 Move：转移所有权

let a = Box::new(10);
let b = a;

Box 默认不是 Copy 类型，因此这里是移动。移动后，a 不再拥有原来的值。

3.2 Copy：复制值

let a = 10;
let b = a;
println!("{a}");
println!("{b}");

i32 实现了 Copy。因此赋值会复制整数值，a 仍然可以使用。

对于 Copy 类型，复制不需要通过析构来释放独占资源。

3.3 Clone：显式复制

let a = String::from("hello");
let b = a.clone();

这里调用了 String 的 Clone 实现。通常 b 会获得独立的字符串缓冲区，而不是与 a 共同拥有同一块缓冲区。

但要注意，Clone 的具体行为由类型决定。对于某些类型，clone() 可能只是复制一个引用计数句柄，而不是深拷贝全部底层数据。例如：

use std::sync::Arc;

let a = Arc::new(String::from("hello"));
let b = Arc::clone(&a);

这里的 Arc::clone 增加共享所有权的引用计数，不会深拷贝整个字符串。

操作是否转移原值所有权是否可能分配内存典型用途
Move是通常不需要因移动而重新分配转移资源所有权
Copy否，复制值不需要堆分配复制简单值
Clone原值仍然有效可能显式复制或共享句柄

这部分看似基础，但在 FFI 中非常关键。

例如，如果你把 Box<T> 转成原始指针交给 C 管理，就必须明确原有 Rust 所有权已经如何转移，否则可能发生双重释放。

四、Drop：Rust 到底什么时候释放资源？

现在进入重点。

Rust 提供了 Drop Trait：

pub trait Drop {
    fn drop(&mut self);
}

当一个实现了 Drop 的值被析构时，编译器会调用它的 drop 方法。例如：

struct Resource {
    name: String,
}

impl Drop for Resource {
    fn drop(&mut self) {
        println!("Dropping {}", self.name);
    }
}

fn main() {
    let resource = Resource {
        name: String::from("engine"),
    };
    println!("Using resource");
}

程序大致输出：

Using resource
Dropping engine

当 resource 离开作用域时，Rust 会执行它的析构过程。

但是，Drop::drop() 并不等于对象全部资源的最终释放过程。这点很重要。

4.1 结构体的析构顺序

考虑：

struct Engine {
    name: String,
    buffer: Vec<u8>,
}

impl Drop for Engine {
    fn drop(&mut self) {
        println!("Dropping Engine");
    }
}

当 Engine 被析构时，顺序是：

  1. 调用 Engine::drop()。
  2. 析构 name 字段。
  3. 析构 buffer 字段。

也就是说，执行 Engine::drop() 时，两个字段仍然有效，可以在满足借用规则的前提下访问它们。等自定义 drop() 返回后，字段才会继续析构。

4.2 字段的析构顺序

对于结构体字段，Rust 按照声明顺序析构：

struct Example {
    first: Resource,
    second: Resource,
    third: Resource,
}

当 Example 被析构时：

Example::drop()
    ↓
first.drop()
    ↓
second.drop()
    ↓
third.drop()

注意，这里是字段的析构顺序，而不是变量离开作用域的顺序。

对于局部变量，通常是按照定义的逆序析构：

fn main() {
    let first = Resource {
        name: "first".into(),
    };
    let second = Resource {
        name: "second".into(),
    };
}

通常会先析构 second，再析构 first。

这里和 C++ 有一个容易记混的差别：C++ 的成员按逆声明序析构，Rust 的字段按声明序析构。两者都是「先执行析构函数体、再析构成员/字段」，但成员顺序正好相反。

如果底层资源之间存在严格的释放依赖关系，应该明确设计所有权结构，不要依赖不必要的析构顺序假设。

五、为什么不能直接调用 Drop::drop()？

这是一个很值得理解的细节。

你可能会想：

let mut resource = Resource {
    name: String::from("engine"),
};
resource.drop();

但这不是正常的资源释放方式，编译器会直接拒绝：

error[E0040]: explicit use of destructor method

原因是：如果允许你随意调用 drop(&mut self)，那么之后变量离开作用域时，编译器还会再次执行析构过程。

对于拥有堆内存、文件句柄或 C 资源的类型，这可能造成重复释放。例如：

struct Resource {
    ptr: *mut u8,
}

如果 Drop::drop() 内部释放了 ptr 指向的内存，手动调用一次后，变量离开作用域又调用一次，就可能造成双重释放。

正确的做法是使用：

drop(resource);

这里调用的是标准库提供的 std::mem::drop，它的核心签名可以理解为：

pub fn drop<T>(_x: T)

它通过按值接收 resource，将值移动到函数参数中；当函数结束时，参数被正常析构。

因此：

let resource = Resource {
    name: String::from("engine"),
};
drop(resource);
// resource 已经被移动，不能再使用。

这会让资源在当前位置提前析构，而不是等待当前作用域结束。

记住：Drop::drop(&mut self) 是析构实现；std::mem::drop(value) 是通过所有权转移来提前结束一个值的生命周期。

六、为什么 Rust 允许内存泄漏？

这可能是所有权学习中最反直觉的地方。

Rust 保证安全代码不会轻易产生释放后使用等内存安全错误，但并不保证所有资源都一定会被及时释放。例如：

fn main() {
    let value = Box::new(42);
    std::mem::forget(value);
}

mem::forget 消耗这个值，却不执行其析构过程。结果就是：这个 Box 所拥有的内存不会通过正常析构路径释放——这是内存泄漏。

为什么 Rust 允许它？

因为内存泄漏通常是资源管理问题，而不一定是内存安全问题。

相比之下，如果 Rust 强制要求所有值都必须析构，就会让某些安全抽象难以实现。例如引用计数结构、循环引用或涉及资源所有权转移的底层实现，都可能需要容忍某些值没有按通常路径析构。

但这里要区分两个概念：

  • 内存泄漏：资源没有及时释放。
  • 释放后使用：程序继续访问已经失效的内存。

前者不必然导致 UB，后者则可能直接破坏内存安全。

另外，不能因为 mem::forget 是安全 API，就认为它对任何资源都没有后果。它可能泄漏文件句柄、锁、内存或其他资源，导致程序性能和正确性问题。

Rustonomicon 也专门讨论了这种情况（Leaking）：Rust 不保证析构函数一定执行，因此安全抽象不能把内存安全建立在「析构必定发生」这一假设上。

七、这对 FFI 有什么影响？

现在把所有权和 Drop 与 FFI 联系起来。

假设 C 库提供：

Engine *engine_create(void);
void engine_destroy(Engine *engine);

Rust 侧需要包装它。一个常见设计是：

use std::ptr::NonNull;

pub struct Engine {
    handle: NonNull<CEngine>,
}

Engine 拥有 C 库创建的资源，那么析构时应该释放它：

impl Drop for Engine {
    fn drop(&mut self) {
        unsafe {
            engine_destroy(self.handle.as_ptr());
        }
    }
}

这是示意代码，假定 CEngine、engine_destroy 等 FFI 声明已正确建立。

真正的实现必须确认：

  1. handle 来自正确的创建函数。
  2. 该句柄仍然有效。
  3. 当前 Engine 是唯一负责释放它的所有者。
  4. engine_destroy 可以在当前线程和当前状态下调用。
  5. 销毁操作不会引发不受支持的跨 ABI 异常传播。

如果这些条件没有得到保证，那么即使 Drop 写得很整齐，也仍然可能产生双重释放或释放后使用。

顺带一提：NonNull<T> 本身是 !Send + !Sync，所以这样的 Engine 默认也不能跨线程移动。真需要跨线程时，必须显式 unsafe impl Send，并对第 4 条负责。

7.1 典型错误：重复释放

例如：

let engine = Engine::new()?;
let ptr = engine.handle.as_ptr();

假设有人把 ptr 传给 C，并让 C 直接调用 engine_destroy(ptr)。但 Rust 侧的 engine 仍然认为自己拥有该资源。等 engine 离开作用域时，Drop 又会调用 engine_destroy——这就可能造成双重释放。

正确的设计必须明确选择一种所有权模型：

模型 A：Rust 拥有资源

Rust Engine
    │
    └── Drop 负责销毁 C 资源

外部代码只能在明确的借用契约下使用句柄，不能擅自释放。

模型 B：所有权转移给 C

Rust Engine
    │
    └── 将所有权转移给 C
              │
              └── C 负责销毁资源

转移之后，Rust 侧必须确保不再对该资源执行原有的析构操作。

这就是所有权系统在 FFI 中最重要的应用之一。

八、Drop Check 到底检查什么？

到这里，我们已经知道：

  • Rust 如何转移所有权；
  • Drop 如何执行析构；
  • 字段何时被析构；
  • 内存泄漏为什么可能是安全的；
  • FFI 资源应该由谁释放。

接下来会遇到一个更复杂的问题：

如果一个对象包含引用，那么它析构时，这些引用所指向的数据一定还活着吗？

普通生命周期检查已经能处理许多情况，但一旦引入自定义析构函数，问题就会变得更微妙。例如：

struct Inspector<'a>(&'a u8);

impl Drop for Inspector<'_> {
    fn drop(&mut self) {
        println!("value = {}", self.0);
    }
}

Inspector 持有一个引用，而且在析构时会读取它。因此，当 Inspector 被析构时，引用指向的数据必须仍然有效；否则，析构函数本身就可能访问无效内存。

这就引出了 Drop Check（析构检查）。

它是 Rust 所有权体系里比较容易学得似懂非懂的一部分：你已经理解了生命周期、Drop、协变与不变，但当这些机制组合在一起时，编译器为什么有时会拒绝一段看似安全的代码？PhantomData<T> 为什么会影响借用检查？Vec<T> 又为什么需要特殊的析构设计？

本篇后半部分主要依据 Rustonomicon 的 Drop Check 和 PhantomData 章节，按以下顺序展开：

  1. Drop Check 到底检查什么？
  2. 为什么实现 Drop 会改变生命周期检查？
  3. 为什么泛型析构函数可能造成内存安全问题？
  4. PhantomData<T> 如何影响 Drop Check？
  5. #[may_dangle] 为什么存在？
  6. Vec<T> 的底层设计如何使用这些知识？

8.1 一个最简单的例子

struct Inspector<'a> {
    value: &'a i32,
}

impl Drop for Inspector<'_> {
    fn drop(&mut self) {
        println!("value = {}", self.value);
    }
}

fn main() {
    let number = 42;
    let inspector = Inspector {
        value: &number,
    };
    println!("Inspector created");
}

这段代码是合法的。

当 main 结束时，局部变量按照逆序析构：

创建 number
    ↓
创建 inspector
    ↓
main 结束
    ↓
析构 inspector
    ↓
析构 number

所以，Inspector::drop() 运行时，number 仍然有效。

这里有一个关键点：

编译器不仅要检查引用在正常使用期间是否有效，还要考虑析构函数执行时，引用指向的数据是否仍然有效。

这就是 Drop Check 要解决的问题。

更具体地说，Drop Check 是借用检查器在考虑析构行为时采用的一组规则，用来避免对象在析构过程中访问已经失效的数据。

它与普通生命周期检查密切相关，但不是简单地把所有生命周期统一延长到 'static。

8.2 为什么不能只检查普通代码？

假设一个类型没有自定义析构函数：

struct Wrapper<'a> {
    value: &'a i32,
}

它只保存一个引用。编译器可以根据类型定义、所有权关系和实际使用情况判断引用的生命周期是否足够。

但现在我们为它添加一个 Drop：

struct Wrapper<'a> {
    value: &'a i32,
}

impl Drop for Wrapper<'_> {
    fn drop(&mut self) {
        println!("{}", self.value);
    }
}

这个类型在析构时会读取 value。因此，编译器需要考虑一个额外的事实：

即使调用者不再显式访问这个对象，析构函数仍然可能访问它内部的引用。

这就是析构行为对生命周期分析产生影响的原因。

这个差别可以直接观察。下面两段代码只差一个 Drop 实现：

struct NoDrop<'a>(&'a u8);

fn main() {
    let mut a = 0u8;
    let _inspector = NoDrop(&a);
    a = 1;              // ✅ 通过：NLL 认为借用在构造之后就结束了
}
struct HasDrop<'a>(&'a u8);

impl Drop for HasDrop<'_> {
    fn drop(&mut self) {
        let _ = self.0;
    }
}

fn main() {
    let mut a = 0u8;
    let _inspector = HasDrop(&a);
    a = 1;              // ❌ error[E0506]: cannot assign to `a` because it is borrowed
}

后者之所以被拒绝，是因为 HasDrop 有析构函数：a 的借用必须一直活到 _inspector 析构那一刻，而不是到「最后一次使用」就结束。

这就是「实现 Drop 后生命周期检查变严格」的具体含义。

不过，需要注意：实现 Drop 并不意味着所有内部引用都必须存活到程序结束，也不意味着所有带 Drop 的类型都会受到相同的限制。编译器会根据类型、生命周期约束和析构语义判断哪些条件必须成立。

九、为什么泛型析构函数会让问题复杂起来？

现在进入真正重要的部分。

先定义一个泛型类型：

struct Inspector<T> {
    value: T,
}

impl<T> Drop for Inspector<T> {
    fn drop(&mut self) {
        println!("Dropping Inspector");
    }
}

注意：这里的 T 可以是任何类型。例如：

Inspector<i32>
Inspector<String>
Inspector<&'a i32>
Inspector<Vec<u8>>

问题在于，编译器不能只根据当前的 Drop 函数表面上做了什么，就完全忽略泛型参数 T 的析构行为。

原因是 T 可能拥有自己的析构函数。例如：

struct Resource<'a> {
    reference: &'a i32,
}

impl Drop for Resource<'_> {
    fn drop(&mut self) {
        println!("Resource value = {}", self.reference);
    }
}

如果 Inspector<Resource<'a>> 被析构，那么析构过程可能是：

Inspector<Resource<'a>> 开始析构
          │
          ▼
Inspector::drop()
          │
          ▼
Inspector 的字段开始析构
          │
          ▼
Resource<'a>::drop()
          │
          ▼
访问 reference 指向的数据

即使 Inspector::drop() 自己没有读取 T，T 的析构函数仍然可能读取它所引用的数据。

因此，Rust 需要考虑的不只是外层类型的 Drop 实现，还包括字段及其相关析构行为。

这就是 Drop Check 对泛型类型特别重要的原因：泛型参数不仅携带数据，还可能携带析构行为。

十、为什么析构函数不能访问已经失效的引用？

我们先看一个安全的设计：

struct Inspector<'a> {
    value: &'a i32,
}

impl Drop for Inspector<'_> {
    fn drop(&mut self) {
        println!("{}", self.value);
    }
}

fn main() {
    let number = 10;
    let inspector = Inspector { value: &number };
    drop(inspector);
}

这里的 drop(inspector) 会提前析构 inspector。因为 number 仍然有效，所以访问是安全的。

现在考虑一个概念上的错误设计：

  1. 创建一个局部变量 number
  2. 创建 Inspector，并保存 &number
  3. 让 number 先失效
  4. 再析构 Inspector
  5. Inspector::drop() 解引用已经失效的引用

如果 Rust 允许这样的程序，就会产生悬垂引用访问。

但是在普通安全 Rust 中，借用检查器会阻止能够导致这种情况的合法代码路径。

因此，Drop Check 并不是一个运行时检测器。它不是等到 drop() 执行时才检查引用是否有效，而是通过编译期约束，避免某些不安全的生命周期安排。

所以应该这样理解 Drop Check：

它是编译器生命周期与析构安全分析的一部分，而不是一个运行时的析构函数检查器。

十一、PhantomData：为什么一个零大小字段会影响安全性？

现在进入本篇最重要的知识点之一。

PhantomData<T> 是 Rust 标准库提供的一个零大小类型。它本身不保存一个实际的 T 值，但可以向编译器表达：当前类型在类型系统层面，应当被视为与 T 存在某种关系。

例如：

use std::marker::PhantomData;

struct MyType<T> {
    marker: PhantomData<T>,
}

这里的 marker 不会在运行时存储一个实际的 T。但是，PhantomData<T> 会影响类型的静态属性，包括：

  • 型变（variance）；
  • 自动 Trait 推导，例如 Send 和 Sync；
  • Drop Check 对类型所表达的所有权关系的理解。

具体效果取决于 PhantomData 内部使用的类型形式。

因此，不能把所有 PhantomData 用法都简单归结为「告诉编译器我拥有 T」。

11.1 为什么需要 PhantomData？

假设我们在底层实现一个容器：

use std::marker::PhantomData;
use std::ptr::NonNull;

struct MyVec<T> {
    ptr: NonNull<T>,
    len: usize,
    capacity: usize,
    marker: PhantomData<T>,
}

它大致表达以下结构：

MyVec<T>
   │
   ├── ptr      ──────> 堆内存中的 T 元素
   ├── len      ──────> 当前初始化元素数量
   ├── capacity ──────> 已分配容量
   └── marker   ──────> 向类型系统表达与 T 的关系

ptr 是原始指针。它并不会像普通的 &T 那样，直接在类型系统中表达与目标数据之间的生命周期关系。

但 MyVec<T> 逻辑上拥有一组 T 元素。因此，如果我们希望编译器把 MyVec<T> 视为拥有 T，那么 PhantomData<T> 就是一个重要的工具。

它不仅是一个标记，还影响编译器如何理解这个类型的所有权和型变属性。

关键区别

struct A<T> {
    ptr: *const T,
}

与：

use std::marker::PhantomData;

struct B<T> {
    ptr: *const T,
    marker: PhantomData<T>,
}

这两个类型在类型系统中的含义并不完全相同。第二个类型明确表达了与 T 的额外关系。

不过，真实的指针容器应该根据自己的所有权语义选择正确的标记类型，而不是机械地为所有指针添加 PhantomData<T>。例如：

  • 拥有 T 的容器通常需要表达拥有型关系；
  • 仅仅借用 T 的包装类型，应当表达借用关系；
  • 如果类型只是保存一个不拥有目标对象的原始句柄，可能需要另一种标记策略。

PhantomData 的类型选择必须反映真实的语义，而不是仅仅为了让编译器接受代码。

十二、PhantomData 如何影响 Drop Check？

现在可以把前面的概念连起来了。

考虑：

use std::marker::PhantomData;

struct MyContainer<T> {
    marker: PhantomData<T>,
}

虽然 PhantomData<T> 不保存实际的 T 值，但它会让编译器把这个类型视为在类型系统中拥有与 T 相关的关系。

当 T 包含生命周期参数时，这种关系就可能影响借用检查和析构安全分析。例如：

struct Borrowed<'a> {
    value: &'a i32,
}

那么 MyContainer<Borrowed<'a>> 通过 PhantomData<T> 表达了与 Borrowed<'a> 的拥有型关系。

这意味着，类型系统需要考虑 MyContainer 与 'a 之间的关联，而不能只把它视为一个完全不相关的原始指针包装。

但要注意：

PhantomData<T> 不会自动保证 Drop 实现正确，也不会自动保证原始指针有效。它提供的是类型系统层面的关系信息。

如果你在实现 MyContainer<T> 时，仍然可能重复释放、访问已经失效的内存，或者在析构时违反类型不变量，那么仅仅增加 PhantomData<T> 并不能修复这些问题。

十三、为什么 Vec 是学习 Drop Check 的经典例子？

现在来看 Rust 标准库中最值得研究的类型之一：Vec<T>。

一个简化的 Vec<T> 可以理解为：

struct MyVec<T> {
    ptr: *mut T,
    len: usize,
    capacity: usize,
}

真实的标准库实现要复杂得多，而且会使用适合当前实现的内部类型和不变量。这里先用简化结构帮助理解。

它需要维护以下约束：

  1. ptr 必须符合分配器和布局要求。
  2. capacity 必须与实际分配的内存容量相符。
  3. [0, len) 中的元素已经初始化。
  4. [len, capacity) 中的空间不能被当成已经初始化的 T。
  5. 每个已初始化元素必须在适当时机被析构。
  6. 分配的内存必须由正确的分配器释放。

注意第五点。

假设：

struct Item {
    name: String,
}

当 Vec<Item> 被析构时，它不能仅仅释放存储元素的那块原始内存。它还需要正确析构其中已经初始化的 Item 元素，否则每个 Item 内部的 String 可能无法正常释放自己的缓冲区。

所以，容器的析构逻辑大致是：

Vec<T> 开始析构
       │
       ▼
析构所有已初始化的 T
       │
       ▼
释放容器的底层分配

这也是为什么 len 非常重要：它表示已经初始化、拥有的元素数量，而不是分配内存可以容纳的元素数量。capacity 与 len 不能混淆。

13.1 为什么不能析构整个 capacity？

假设：

let mut values: Vec<String> = Vec::with_capacity(10);
values.push(String::from("hello"));

这里的 capacity 至少为 10，但实际只初始化了一个元素。也就是说：

capacity >= 10
len = 1

如果底层实现尝试析构全部 capacity 个位置，就会把尚未初始化的内存当作 String 对象处理。这可能导致未定义行为。

正确的容器实现必须只析构已经初始化的元素，然后释放分配的内存。

这一点会在下一步学习 MaybeUninit<T> 时变得更加重要。

十四、Drop Check 与 PhantomData 的真正交汇点

现在我们已经知道：

  • Vec<T> 在逻辑上拥有 T；
  • T 可能包含生命周期参数；
  • T 也可能有自己的析构函数；
  • 原始指针不会自动表达完整的拥有型关系；
  • PhantomData<T> 可以帮助编译器理解这种关系。

于是就出现了一个问题：

如果我们正在实现自己的容器，如何告诉编译器这个容器拥有 T，同时又正确处理析构时的生命周期约束？

这就是 Drop Check 与 PhantomData 的交汇点。例如：

use std::marker::PhantomData;
use std::ptr::NonNull;

struct MyVec<T> {
    ptr: NonNull<T>,
    len: usize,
    capacity: usize,
    marker: PhantomData<T>,
}

这里的 PhantomData<T> 表达了拥有型关系。

对于安全设计来说，这意味着我们不能随意声称：MyVec<T> 只是保存一个不相关的地址，所以 T 的生命周期和析构行为与它无关。

它逻辑上拥有 T，因此必须认真考虑 T 的析构和生命周期约束。

但是，如果你只是在做一个不拥有目标对象的借用包装器，那么 PhantomData<T> 可能不是正确的选择。例如：

use std::marker::PhantomData;

struct BorrowedPtr<'a, T> {
    ptr: *const T,
    marker: PhantomData<&'a T>,
}

这个类型表达的是：

  • 它保存一个原始指针；
  • 它在类型系统中与一个生命周期为 'a 的共享借用相关联；
  • 它并不声称自己拥有 T。

这两个设计有着不同的语义：PhantomData<T> 与 PhantomData<&'a T> 不能随意互换。

前者表达与拥有型 T 的关系；后者表达与借用 T 的关系。这会影响型变、自动 Trait 推导，以及编译器如何理解该类型的生命周期与所有权关系。

十五、那么 #[may_dangle] 是什么？

这属于 Drop Check 中更高级的内容。

在某些底层泛型容器中，析构函数不一定需要访问 T 的内容。例如，一个容器的析构逻辑可能只需要：

  1. 释放某块内存；
  2. 不读取某个泛型参数的值；
  3. 不调用该泛型参数的析构函数。

这种情况下，如果编译器一律要求所有相关泛型参数在整个析构过程中保持可用，就可能限制某些原本可以安全实现的底层抽象。

#[may_dangle] 就与这种情况有关。

它允许某些受约束的 Drop 实现声明：析构期间，指定的泛型参数或生命周期可能已经不再有效。

但这不是一个普通的性能优化属性，而是涉及析构安全性的高级机制。

不能仅仅因为 Drop::drop() 没有直接读取 T，就认定可以使用 #[may_dangle]。因为还必须考虑字段析构和其他隐式析构行为。例如：

struct Container<T> {
    value: T,
}

即使 Container::drop() 不读取 self.value，在自定义 Drop 结束后，value 仍然会被析构。如果 T 的析构函数需要访问某个生命周期相关的数据，那么随意放宽该生命周期约束就可能破坏安全性。

这正是 Drop Check 必须谨慎处理的原因。

在当前稳定 Rust 中，#[may_dangle] 属于不稳定的内部机制（需要 nightly 的 dropck_eyepatch），不能把它当成普通稳定 Rust API 随意使用。学习时应以 Rustonomicon 的相关章节和当前编译器实现为准。

推荐阅读：Rustonomicon: Drop Check。

十六、把 Drop Check 应用到 FFI：一个实用设计

假设我们封装一个 C 引擎，它返回一块由 C 管理的缓冲区。

Rust 侧设计：

use std::ptr::NonNull;

pub struct Engine {
    handle: NonNull<CEngine>,
}

如果这个句柄由 Engine 独占拥有，那么 Drop 应该负责释放它。

但是，如果 Engine 还提供一个借用视图：

pub struct EngineData<'a> {
    ptr: *const u8,
    len: usize,
    marker: std::marker::PhantomData<&'a Engine>,
}

那么 EngineData<'a> 的类型就表达了：这个视图的有效期不能超过它所借用的 Engine。

这会帮助 Rust 的生命周期系统阻止调用者在引擎已经被销毁之后，继续通过安全接口使用该视图。

不过，这只有在 API 的实现确实维持该不变量时才成立。例如：

  • EngineData 不能在 Engine 销毁后继续访问内部缓冲区；
  • 引擎不能在视图仍然有效时释放该缓冲区；
  • 如果后续操作会使缓冲区失效，就必须通过借用规则或其他机制禁止冲突操作。

这里的 PhantomData<&'a Engine> 只负责表达类型关系，不会自动固定 C 缓冲区的内存，也不会阻止外部 C 代码偷偷释放它。

因此，FFI 封装必须同时具备：

  1. 正确的类型设计；
  2. 明确的外部 API 契约；
  3. 正确的资源管理；
  4. 必要的同步与生命周期控制。

十七、这一节你真正需要记住什么？

把最重要的结论压缩成六条。

第一，Drop Check 是编译期安全机制。

它关注析构过程中可能发生的引用访问，而不是在运行时检查内存。

第二，泛型参数可能带来隐式析构行为。

外层 Drop 函数不读取 T，不代表整个析构过程不需要考虑 T。

第三，PhantomData 会影响类型系统对所有权和生命周期关系的理解。

它不是一个简单的占位符，也不是用来欺骗编译器的工具。

第四，Vec<T> 必须区分已初始化元素与尚未初始化的容量空间。

只析构实际初始化的元素，然后释放底层分配。

第五，#[may_dangle] 是高级安全机制。

它不能作为随意绕过生命周期约束的手段。

第六，FFI 的安全性最终依赖正确的所有权与生命周期契约。

即使使用 NonNull<T>、PhantomData<T> 和 Drop，也不能自动保证外部资源有效或不会被重复释放。

一、什么是未初始化内存？

普通变量：

fn main() {
    let x: i32 = 42;
    println!("{x}");
}

状态很明确：分配了存储空间、空间里有一个合法的 i32、可以安全读取。

但如果先申请空间、之后再初始化：

// 伪代码：不是合法的 Rust
let x: i32;
println!("{x}");

Rust 会拒绝编译。这不只是编译器在限制你，背后有一个核心概念：

内存中存在一些字节，不代表这些字节已经构成一个合法的 Rust 值。

某些整数类型的任意位模式都是合法值，但并非所有类型如此：

let x: bool = true;

bool 只有两个合法表示（false = 0、true = 1），其他位模式不能作为合法 bool 使用。

let x: &i32 = &42;

引用更是如此：随便一组字节不能保证构成有效引用。

所以底层内存操作必须区分两种状态：

状态含义
已分配内存有一块可以存储数据的空间
已初始化的 T这块空间中存在一个合法的 T 值

1.1 一个底层场景

要分配能容纳 100 个 u64 的内存，逻辑上是两个阶段：

内存分配
    ↓
┌────┬────┬────┬────┬────┬────┐
│ ?? │ ?? │ ?? │ ?? │ ?? │ ?? │ ... 100 个槽位
└────┴────┴────┴────┴────┴────┘
    ↓
逐个初始化
    ↓
┌────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │ 60 │ ...
└────┴────┴────┴────┴────┴────┘

第一阶段只需要内存，不需要已经构造好的 u64。这在 C/C++/Rust 的底层容器里都很常见。

Rust 的额外要求是：一个位置在被初始化之前，不能当作有效的 T 来读取、传递或析构。

这就引出了 MaybeUninit<T>。

二、MaybeUninit<T> 是什么

MaybeUninit<T> 表示：

这里可能存在一个有效的 T，也可能还没有初始化。

use std::mem::MaybeUninit;

fn main() {
    let mut slot: MaybeUninit<u32> = MaybeUninit::uninit();
    slot.write(42);
    let value = unsafe { slot.assume_init() };
    println!("{value}");
}
MaybeUninit::uninit()
          │
          ▼
┌────────────────────┐
│ 未初始化的存储空间 │
└────────────────────┘
          │
          │ write(42)
          ▼
┌────────────────────┐
│ 有效的 u32 值：42  │
└────────────────────┘
          │
          │ assume_init()
          ▼
┌────────────────────┐
│ 普通的 u32：42     │
└────────────────────┘

注意 MaybeUninit::uninit() 本身是安全的：我们没有声称内存里已经存在有效的 u32。

需要 unsafe 的是 assume_init()：

use std::mem::MaybeUninit;

fn main() {
    let slot = MaybeUninit::<u32>::uninit();
    // 错误示范：不要这样做
    let value = unsafe { slot.assume_init() };
    println!("{value}");
}

因为编译器无法仅凭这次调用判断你是否真的完成了初始化。

unsafe 不会替你初始化内存，也不会检查内存里是否真的有合法 u32——它只是允许你执行一个需要由你证明安全的操作。

assume_init() 的含义不是「帮我初始化」，而是「我保证这里已经初始化好了」。

三、为什么不能直接用 T

需求：构造一个 4 元素数组，元素靠运行时计算得到。

fn calculate(index: usize) -> u64 {
    (index as u64 + 1) * 100
}

let values = [
    calculate(0),
    calculate(1),
    calculate(2),
    calculate(3),
];

这要求在构造数组时就能提供全部元素。如果数组很大、元素要逐个从外部接口取，或者想避免先造一批无用的默认值，就需要手动管理初始化过程。

典型场景：FFI 接口要求调用者提供缓冲区，由 C 函数填入数据——我们希望直接写进目标内存，而不是先造默认值再复制。

3.1 为什么不能用默认值

let mut values = [0u64; 100];

对 u64 通常没问题。但如果 T 是复杂对象：

struct ExpensiveObject {
    data: Vec<u8>,
}

为了创建 100 个对象，可能要先构造 100 个空 Vec 再逐个替换，产生额外的构造和析构开销。而且 T 甚至可能没有 Default 实现。

所以需要一种表示：有存储空间，但还没有构造出 T。这就是 MaybeUninit<T> 的核心用途。

优化是否值得取决于实际类型和场景，不能简单认为 MaybeUninit 一定更快。

四、ptr::write 与普通赋值的区别

普通赋值：

let mut x = String::from("hello");
x = String::from("world");

x 已经持有一个有效的 String，赋值时旧值需要被正确处理，否则它拥有的堆内存会泄漏。

但如果目标内存尚未初始化，就不能把它当成已有的 T 来赋值——普通赋值可能需要先处理目标位置上的旧值，而这对未初始化内存是不正确的。

std::ptr::write(dst, value) 会把 value 写入目标地址，不会先读取或析构目标地址原先的内容：

use std::mem::MaybeUninit;
use std::ptr;

fn main() {
    let mut slot = MaybeUninit::<String>::uninit();
    unsafe {
        ptr::write(
            slot.as_mut_ptr(),
            String::from("hello"),
        );
    }
    let value = unsafe { slot.assume_init() };
    println!("{value}");
}
  • slot.as_mut_ptr() 拿到用于存储 String 的原始指针；
  • ptr::write(...) 把一个新构造的 String 写入目标位置；
  • slot.assume_init() 在你能证明已初始化时，把它转成普通的 String。

4.1 为什么不会析构旧值

因为它面向的核心场景就是「向尚未初始化的内存写入新值」。如果写入前先尝试析构旧值，就等于要求调用者先提供一个有效的旧对象，与需求冲突。

但反过来说：如果目标位置原本已经持有有效值，ptr::write 也不会替你析构它。

let mut value = String::from("old");
unsafe {
    std::ptr::write(
        &mut value,
        String::from("new"),
    );
}

这会覆盖原来的 String，但不会析构 "old"——旧值拥有的资源泄漏了。

因此：

  • 目标位置未初始化：ptr::write 适合。
  • 目标位置已有有效值：必须先考虑旧值的生命周期与资源释放。
  • 不能确定目标状态：不要随意用原始指针写入。

一句话：ptr::write 负责写入，不负责管理旧对象的生命周期。

五、真正的难点：部分初始化

现在不是 1 个对象，而是 100 个：

第 0 个元素：初始化成功
第 1 个元素：初始化成功
第 2 个元素：初始化成功
第 3 个元素：初始化失败
...

这时怎么办？这才是 MaybeUninit<T> 真正困难的地方。

struct RawBuffer<T, const N: usize> {
    slots: [MaybeUninit<T>; N],
    initialized: usize,
}
  • slots 是存储空间；
  • initialized 表示前多少个元素已经成功初始化。

若 initialized = 3：

索引：     0        1        2        3        4
状态：   已初始化  已初始化  已初始化  未初始化  未初始化

这建立了一个关键不变量：

0 ≤ initialized ≤ N
∀ i ∈ [0, initialized): slots[i] 已初始化

前 initialized 个元素全部有效，后面的可能没有初始化。

这个计数不是简单的辅助字段——它决定了析构时哪些位置可以被当作有效的 T。

5.1 为什么不能析构全部元素

slots       = [有效 T, 有效 T, 有效 T, 未初始化, 未初始化]
initialized = 3

如果把 5 个槽位都当作 T 析构，后两个槽位并不包含有效 T，违反了 Rust 对有效值的要求。

正确清理逻辑：

析构 slots[2]
析构 slots[1]
析构 slots[0]

只清理已经初始化的元素。如果析构顺序有依赖，还要认真设计顺序；真实实现还要处理析构函数自身 panic 的情况。

六、一个可运行的部分初始化示例

先不实现完整 Vec<T>，而是观察如何保证初始化状态正确：

use std::mem::MaybeUninit;

fn build_array() -> [u64; 4] {
    let mut slots: [MaybeUninit<u64>; 4] =
        [const { MaybeUninit::uninit() }; 4];

    for i in 0..4 {
        slots[i].write((i as u64 + 1) * 10);
    }

    // SAFETY: 上面的循环已经初始化了全部 4 个元素，
    // 且 u64 是 Copy 类型，按位读出后源位置不会被再次析构。
    unsafe {
        (&slots as *const _ as *const [u64; 4]).read()
    }
}

fn main() {
    println!("{:?}", build_array());
}

输出：

[10, 20, 30, 40]

[const { MaybeUninit::uninit() }; 4] 是 inline const 语法（Rust 1.79 起稳定），用来给非 Copy 的 MaybeUninit<T> 批量初始化数组。

关于最后那次指针转换，有两点必须说清：

  1. 它只在 T: Copy 时安全。read() 是复制而非移动——对 String 这类拥有资源的类型，slots 里的值之后仍会被析构，导致双重释放。
  2. 这种手工转换容易出错，不是首选写法。如果元素是逐个算出来的，用安全 API 更简单：
fn build_array() -> [u64; 4] {
    std::array::from_fn(|i| (i as u64 + 1) * 10)
}

MaybeUninit::array_assume_init 能做到同样的事，但它至今仍是 nightly API（maybe_uninit_array_assume_init），不能用于稳定 Rust。

重点不是记住某种转换写法，而是理解：只有全部元素都有效时，才能把整个数组视为普通的 [T; N]。

七、初始化中途 panic 怎么办

for i in 0..100 {
    slots[i].write(create_object(i));
}

假设 create_object(57) 发生 panic：

索引 0~56：已初始化
索引 57~99：没有初始化

如果这些对象持有文件句柄、堆内存等资源，必须保证已初始化的对象得到清理，否则泄漏；但又不能析构整个数组，因为剩余元素没初始化。

所以底层实现必须维护初始化进度：

let mut initialized = 0;
for i in 0..N {
    let value = create_object(i);
    slots[i].write(value);
    initialized += 1;
}

顺序很重要：

  1. 先成功构造对象。
  2. 写入目标槽位。
  3. 确认写入成功。
  4. 更新已初始化数量。

如果第 57 个对象构造时 panic，计数仍是 57，清理代码就知道只有前 57 个元素可以被当作 T 处理。

但只有计数器还不够：还需要一个清理机制，例如一个持有 slots 与 initialized 的 guard，在栈展开时析构已初始化的元素。如果清理本身再次 panic，行为会更复杂。

这就是 Vec<T> 底层实现不是「分配内存、逐个写入」这么简单的原因——它必须处理部分初始化、资源释放、所有权转移和异常路径。

八、与 Vec<T> 的关系

概念上的结构：

struct VecLike<T> {
    ptr: *mut T,
    len: usize,
    capacity: usize,
}

（简化模型，不是标准库真实定义。）

字段含义
ptr指向元素存储空间
len已经初始化、且属于本容器的元素数量
capacity当前分配空间能容纳的元素数量

设 capacity = 8、len = 3：

内存分配空间
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ T0 │ T1 │ T2 │ ?? │ ?? │ ?? │ ?? │ ?? │
└────┴────┴────┴────┴────┴────┴────┴────┘
  └─────────┘
     len = 3
  └───────────────────────────────────┘
                capacity = 8
  • len 以内是已经初始化的有效值；
  • len 到 capacity 之间属于分配区域，但不一定包含有效的 T。

所以 len() 不是「分配了多少内存」，而是「当前拥有多少个有效元素」；capacity() 才是「不重新分配还能再放几个」。

8.1 push 的核心过程

从 len = 3、capacity = 8 开始，容量足够时：

1. 找到第 3 个元素的位置
             ↓
2. 将 value 写入该位置
             ↓
3. 确认新元素已初始化
             ↓
4. 将 len 从 3 更新为 4

必须先写入、再增加 len。 因为 len 是容器对外承诺的有效元素数量，先加 len 会让容器声称存在一个尚未初始化的元素，直接破坏不变量。

8.2 pop 的核心过程

1. 检查 len 是否为 0
             ↓
2. 确定最后一个有效元素的位置
             ↓
3. 将该元素的所有权转移给调用者
             ↓
4. 将 len 从 4 更新为 3

关键在于：最后一个元素不能既由 Vec<T> 拥有、又由返回的 value 拥有。

struct Resource {
    data: String,
}

所有权转移正确时，pop() 返回的 Resource 由调用者负责析构，Vec<T> 不会再析构那个已移出的对象。

这也是 ptr::read、ptr::write 和 MaybeUninit<T> 必须放在所有权语义里一起理解的原因。

九、Drop 与 MaybeUninit 的结合

持有原始分配内存的容器，析构逻辑不能写成：

// 错误示意：不能这样实现真实容器
unsafe {
    drop_all_elements_in_allocation();
}

因为整个分配区域里可能只有一部分元素已初始化。

正确的清理过程：

读取 len
   ↓
析构已初始化的元素
   ↓
释放底层分配

最关键的一条：析构的元素数量应等于实际初始化且由容器拥有的元素数量，而不是容量。

这也说明了 MaybeUninit<T> 与 Drop Check 的关系：

  • MaybeUninit<T> 用来表达某个位置尚未构造出 T；
  • 初始化状态记录哪些位置已经拥有有效的 T；
  • Drop 只能处理真正有效且由当前容器拥有的对象；
  • PhantomData<T> 可以进一步表达容器与 T 在类型系统层面的关系。

十、应用到 FFI：C 分配的内存能直接当 Rust 对象吗

void fill_buffer(uint32_t *buffer, size_t len);
unsafe extern "C" {
    fn fill_buffer(buffer: *mut u32, len: usize);
}

分配一段缓冲区交给 C 写入时，必须区分三个问题。

问题一：内存是否已经分配？

有存储空间，不代表其中有有效的 u32 值。

问题二：C 函数是否真的初始化了所有元素？

如果 C 只写了前 10 个，其余位置不能自动视为已初始化。

问题三：C 函数的行为是否符合约定？

  • 是否会写出缓冲区边界？
  • 是否真的初始化了约定数量的元素？
  • 是否会保留指针、在函数返回后继续使用？
  • 是否会在其他线程访问缓冲区？

这些都属于 FFI 安全契约。Rust 编译器不能自动证明外部 C 函数遵守了约定。

因此，安全的 FFI 封装必须先明确约束 C 函数的行为，再根据它实际完成的初始化范围，把内存转成 Rust 可以安全使用的值。

不能仅因为 C 函数返回成功，就假定所有内存都已正确初始化——这一点必须由具体接口的契约保证。

十一、可用于跨语言分析的维度

从内存安全分析器的角度看，MaybeUninit<T> 涉及的问题可以归纳为几个可分析维度：

分析维度需要判断的问题
初始化状态某个内存位置是否已被写入有效值？
初始化范围数组或缓冲区中究竟哪些元素有效？
所有权当前代码是否拥有这些对象的析构责任？
所有权转移对象被移出后，旧容器是否还会析构它？
析构正确性是否可能析构未初始化的内存？
异常安全部分初始化失败后，已构造对象是否得到清理？
FFI 契约外部函数是否初始化了约定的内存区域？

要区分两种能力：

  • 静态分析能直接验证的事实：某条控制流路径上，初始化计数是否可能小于 len；某分支是否可能在初始化之前读取目标位置。
  • 需要建模的外部契约：C 函数是否真的写入了全部元素。仅凭 Rust 调用点的类型信息通常无法证明，需要分析外部实现、可信注解或接口契约。

这也与 Ownership Tracking、Memory Graph 和 FFI 边界分析直接相关。

但要注意：不能把所有初始化问题都归结为「变量有没有赋值」。对 Rust 来说，有效值、对象所有权、初始化范围、析构责任是相互关联但不同的概念。

十二、必须记住的六条

  1. 分配内存不等于初始化对象。 一段内存可以存在，但尚未构造出有效的 T。
  2. MaybeUninit<T> 表达可能尚未初始化的存储空间。 它允许延迟构造对象，但不会自动管理初始化进度。
  3. assume_init() 是一条安全边界。 调用者必须保证目标位置已包含有效 T。
  4. ptr::write() 不析构目标位置的旧值。 它适合向未初始化内存写入；若覆盖已有对象，调用者必须自行处理旧值。
  5. len 与 capacity 语义不同。 len 是有效元素数量，capacity 是可容纳元素数量。
  6. 部分初始化必须有明确的清理策略。 构造中途失败时，必须知道哪些对象已构造完成、哪些需要析构。

Rust panic 展开、异常安全与原始内存

2026-10-25
:: tags:  #Memory  #Panic  #Rust  #Unsafe

我最初读 Rustonomicon 的 Exception Safety 那一章，觉得没什么难的：panic 就 panic，Rust 会自动清理。直到自己动手写一个简化版 Vec，才发现 push 里一个赋值顺序就能把整个容器搞成未定义行为。

这篇就围绕一个问题展开：

程序执行到一半突然 panic，已经申请的内存、已经构造的对象、还没初始化的空间，分别该怎么处理？

参考：Rustonomicon: Exception Safety、Uninitialized Memory。

先把两条 panic 策略的差别摆出来，后面所有讨论都建立在这个前提上：

panic = "unwind"（默认）panic = "abort"
发生 panic 时栈展开，逐层执行 Drop直接 abort 进程
资源清理离开作用域的局部变量会被析构不保证任何析构执行
能否 catch_unwind可以捕获能编译，但捕获不到（进程直接终止）
编译产物大小略大（需要展开信息）更小
性能正常路径几乎无差异正常路径几乎无差异，异常路径更快（不展开）
典型场景需要 catch_unwind 隔离故障嵌入式、CLI、追求最小产物
展开期间再次 panic进程 abort不适用

我在下面的分析默认按 unwind 走——因为只有它会触发「析构顺序」「部分初始化清理」这些问题。切到 abort 之后，panic 就是进程终结，容器是否处于一致状态已经不重要了。

一、Unwinding 到底是什么

先看一段很普通的代码：

struct Resource {
    name: &'static str,
}

impl Drop for Resource {
    fn drop(&mut self) {
        println!("drop {}", self.name);
    }
}

fn main() {
    let a = Resource { name: "A" };
    let b = Resource { name: "B" };
    println!("before panic");
    panic!("something went wrong");
}

用默认的 panic = "unwind" 配置时，panic 会触发栈展开：

main()
  │
  ├── 创建 a
  │
  ├── 创建 b
  │
  ├── println!
  │
  └── panic!
         │
         ▼
     开始栈展开
         │
         ▼
     离开当前作用域
         │
         ├── drop b
         │
         └── drop a

我在本机跑出来的输出是：

before panic
thread 'main' panicked at src/main.rs:9:5:
something went wrong
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
drop B
drop A

这里有个容易记错的顺序：drop B / drop A 出现在 panic 消息之后。因为 panic 消息是 panic hook 先打印的，打印完才开始栈展开、逐个执行 drop。同一个线程里这两件事是顺序发生的。

关键在于：栈展开过程中，Rust 会清理离开作用域时需要析构的局部变量，而且是逆序（先 b 后 a）。

这让资源管理变得可靠。比如：

use std::fs::File;

fn process() {
    let file = File::open("data.txt").unwrap();
    // 后续代码即使 panic，
    // 在正常的栈展开路径上，file 也会被清理
}

文件句柄由拥有它的对象管理，不用在每个错误分支手动关闭。这就是 RAII 在 Rust 里的价值。

但有三个限制必须记住：

  • panic = "abort" 时直接终止进程，没有常规栈展开。
  • 进程被强杀、崩溃，或遇到无法正常展开的情况，不能指望所有 Drop 都执行。
  • Drop 实现本身再次 panic，行为会变得复杂，甚至直接终止进程。

所以「析构一定会执行」不能当成无条件前提。

二、panic 为什么让底层容器变复杂

先看普通的 String：

let value = String::from("hello");
栈
┌─────────────────┐
│ String          │
│ ptr ────────────────┐
│ len = 5         │   │
│ capacity = 5    │   │
└─────────────────┘   │
                      ▼
堆              ┌───────────────┐
                │ hello         │
                └───────────────┘

它被正确析构时会释放自己拥有的堆内存。

但我自己实现容器时：

struct MyVec<T> {
    ptr: *mut T,
    len: usize,
    capacity: usize,
}

所有权关系得自己维护：

  • ptr 指向一段分配空间；
  • len 是已经初始化的元素数量；
  • capacity 是总容量。

如果 push() 中途 panic，我必须保证容器没有进入一个「无法正确析构」的状态。这就是异常安全的核心。

2.1 一个错误的实现思路

假设容器当前 len = 3、capacity = 8，准备加第 4 个元素。一种想当然的写法：

// 仅为错误示意，不能用于真实容器
self.len += 1;
let value = create_value(); // 这里可能 panic
unsafe {
    self.ptr.add(3).write(value);
}

问题在哪？

self.len += 1 之后，容器已经声称自己拥有 4 个有效元素。但如果 create_value() panic，第 4 个元素根本没写进去：

实际状态：[有效 T, 有效 T, 有效 T, 未初始化]
容器记录：len = 4

容器析构时按 len 去析构前 4 个元素，就会去析构一块没初始化的内存。

正确顺序只有一种：

let value = create_value(); // 如果 panic，len 仍为 3
unsafe {
    self.ptr.add(self.len).write(value);
}
self.len += 1;

这个例子还是伪代码，完整的容器还要处理容量检查、指针有效性、对齐等。但它揭示了一条原则：

容器的内部状态必须准确反映已经完成的初始化和所有权转移，不能提前承诺尚未完成的操作。

三、异常安全的三个层次

这套分类来自 C++，但用来分析 Rust 的 panic 一样好用。

3.1 第一层：不产生未定义行为

最基本的要求。无论操作成功与否，都不能因为异常路径破坏内存安全。

let mut values = Vec::<String>::new();

假设某个操作中途失败，容器仍然不能：

  • 读取未初始化的 String；
  • 对同一个对象重复析构；
  • 使用已经释放的内存；
  • 通过悬垂指针访问对象。

这里要强调一句：内存泄漏不一定构成未定义行为。程序可能因为错误路径没释放某个分配，这是资源管理问题，和对无效内存执行操作不是一回事。

3.2 第二层：基本保证

操作失败后，对象仍处于一个有效、可安全析构的状态，但逻辑状态可能已经变了。

操作前：[A, B, C]
操作后：[A, B, C]

这是比较理想的结果。但基本保证实际只要求：对象仍然满足自己的不变量，能安全继续使用或析构——不要求业务状态完全回到原样。

3.3 第三层：强保证

强保证的意思是：操作失败就像从没发生过。

操作前：[A, B, C]
尝试追加 D
发生失败
操作后：[A, B, C]

如果一次操作要重新分配内存、构造多个元素、或执行多个相互依赖的步骤，做到强保证就很困难。常见策略是：

  1. 在临时空间完成可能失败的工作；
  2. 确认成功；
  3. 最后再提交状态变更。

这类似事务里的 commit。

不过不是所有操作都值得追求强保证。对底层容器来说，先保住内存安全和内部状态有效，再按 API 需求决定要不要更强的保证，通常更实际。

四、Guard：处理部分初始化的关键机制

这是底层编程里我用了最多的一种模式。

Guard 本身是个普通 Rust 对象，只是它的 Drop 负责在操作失败时清理资源。先看一个不碰指针的版本：

struct Guard {
    committed: bool,
}

impl Drop for Guard {
    fn drop(&mut self) {
        if !self.committed {
            println!("operation did not commit");
        }
    }
}

fn operation() {
    let mut guard = Guard { committed: false };
    println!("working");
    // 所有工作成功，提交状态
    guard.committed = true;
}

如果 operation() 在提交前 panic，栈展开会让 guard 析构，它发现 committed == false，就执行清理。

真实实现当然不能让 guard 只打印一句话——它得真的持有待清理的资源或初始化状态。

4.1 把 Guard 用在部分初始化上

概念上的结构是这样：

InitGuard<T>
├── ptr         → 目标存储空间
├── initialized → 已成功构造的元素数量
└── capacity    → 可用槽位数量

正常初始化时：

initialized = 0
写入第 0 个元素 → initialized = 1
写入第 1 个元素 → initialized = 2
写入第 2 个元素 → initialized = 3

如果第 3 个元素构造失败，guard 记录的仍是 3，它就只清理前 3 个。

写成代码（capacity 这一段暂用不到，先省掉）：

use std::ptr;

struct InitGuard<T> {
    ptr: *mut T,
    initialized: usize,
}

impl<T> Drop for InitGuard<T> {
    fn drop(&mut self) {
        unsafe {
            for i in (0..self.initialized).rev() {
                ptr::drop_in_place(self.ptr.add(i));
            }
        }
    }
}

这段只展示清理逻辑，离生产可用还差得远。调用它之前必须保证：

  1. ptr 指向足够大、正确对齐的存储空间；
  2. [0, initialized) 内元素全部已初始化；
  3. 这些元素确实由 guard 负责析构；
  4. 每个元素只被析构一次；
  5. 对应分配在清理完成前仍然有效；
  6. 没有其他所有者同时析构同一批元素。

它也没处理 Drop 期间再次 panic 的情况，也没负责释放底层分配。

4.2 为什么要倒序析构

for i in (0..self.initialized).rev()

从最后一个已初始化元素开始往前清。

对于按顺序构造的元素，逆序析构是自然的选择——后构造的对象可能依赖先构造的对象。不过具体容器该不该采用某种顺序，要看它自己的语义和契约，不能一概而论。

五、Guard 与所有权转移：最容易出错的地方

上面那个 guard 会在 Drop 里析构已初始化的对象。但如果元素已经全部构造成功，现在要把它们交给另一个容器呢？

Guard 持有清理责任
          │
          ▼
   [A, B, C, D]

我们把这批对象交给目标容器：

目标容器拥有清理责任
          │
          ▼
   [A, B, C, D]

如果 guard 仍然认为自己拥有这些元素，那就变成两个所有者 → 重复析构。

所以成功提交后，必须让 guard 停止清理已经转移出去的对象。常见设计是在刚才的结构上再加一个 armed: bool：

  • 提交前 armed = true，表示 guard 负责清理；
  • 成功转移所有权后 armed = false，表示 guard 放手。
impl<T> Drop for InitGuard<T> {
    fn drop(&mut self) {
        if self.armed {
            // 清理 guard 仍然拥有的对象
        }
    }
}

这仍是概念设计。实际实现还要保证转移操作本身的失败语义正确，并且目标容器只有在确实拿到所有权之后才把自己标记为所有者。

armed 这个字段叫什么不重要，重要的是：任何时刻都必须明确到底由谁负责析构。

六、三个底层操作：ptr::read、ptr::write、set_len

这三个经常一起出现，但职责完全不同。

6.1 ptr::write：在指定位置写入值

let mut slot = std::mem::MaybeUninit::<String>::uninit();
unsafe {
    slot.as_mut_ptr().write(String::from("hello"));
}

它把一个值写入目标内存，不会先析构目标位置原来的内容，也不会维护 len，不会记录所有权转移。写入条件得你自己保证。

6.2 ptr::read：按值读取

let value = String::from("hello");
let ptr = &value as *const String;
let moved_value = unsafe { ptr.read() };

这段要格外小心。

ptr::read() 从指针位置读出一个 T 并按值返回。对 String 这种拥有资源的类型，这意味着现在有两份描述同一块资源的句柄——但原来的 value 还在。

如果之后让 value 正常析构，就是重复释放。

所以上面这段是刻意展示的危险操作，不能当作正确的所有权转移来用。

对 Copy 类型没这个问题；对拥有资源的非 Copy 类型，必须明确处理源位置的所有权状态。

更符合转移语义的写法是让源槽位变成 MaybeUninit：

use std::mem::MaybeUninit;

fn main() {
    let mut slot = MaybeUninit::new(String::from("hello"));
    let value = unsafe { slot.assume_init_read() };
    println!("{value}");
}

assume_init_read() 从已初始化的槽位读出值，不会析构源槽位里的对象。因为 slot 是 MaybeUninit<String>，它析构时本来也不会去析构内部的 String——清理责任就交给了返回的 value。

这也说明 MaybeUninit<T> 不只用于延迟初始化，还能精确控制对象生命周期。

6.3 set_len：修改「有效元素数量」的记录

unsafe {
    vec.set_len(new_len);
}

它不初始化元素，不移动数据，只是改容器记录的长度。

调用者要保证：

  • 新长度不超过容量；
  • 新长度范围内每个元素都已初始化；
  • 容器能合法拥有这些元素并在以后正确处理。

所以这是错误示范：

let mut vec: Vec<String> = Vec::with_capacity(10);
unsafe {
    vec.set_len(10);
}

分配了够放 10 个 String 的空间，但这些位置没有被初始化。set_len(10) 不会凭空构造 10 个 String，它只是告诉 Vec「你现在拥有 10 个有效元素」——而这个声明是假的。

后面容器一访问或析构，就是未定义行为。

记住：set_len() 改的是记录，不是内存。

七、用这三个操作拼出 push

假设 len = 3、capacity = 8，要加一个 String：

创建新 String
      │
      ▼
ptr::write 写入第 3 个槽位
      │
      ▼
确认元素已初始化
      │
      ▼
更新 len = 4

用原始指针写大概是：

// 仅为解释核心机制的伪代码，不是完整 Vec 实现
let value = String::from("new");
unsafe {
    ptr.add(len).write(value);
    // 只有在写入成功、且新元素确实有效后，
    // 才能更新容器记录的长度
    len += 1;
}

真实的 Vec 还要处理：容量不足时重新分配、内存布局与对齐、分配失败、指针有效性、与借用检查的配合、初始化中途失败的清理、零大小类型等特殊情况。

但原理上它已经解释了为什么 Vec 必须区分「分配空间」和「已初始化元素」。

八、set_len 最典型的使用场景：FFI 缓冲区

假设 C 函数负责把数据写进 Rust 提供的缓冲区：

int read_data(uint8_t *buffer, size_t capacity, size_t *written);
  • buffer 是目标缓冲区；
  • capacity 是容量；
  • written 返回实际写入的字节数。

Vec::with_capacity(capacity) 只保证容量，不意味着 Vec 已经有 capacity 个初始化元素。所以不能直接把 len 设成 capacity 然后让 C 去写。

一种简单且安全的做法是先造出有效长度：

fn read_from_c(capacity: usize) -> Vec<u8> {
    let mut buffer = vec![0u8; capacity];
    // 调用 FFI，让 C 在 buffer 的有效元素范围内写入
    // 实际调用要根据接口契约处理错误和 written
    buffer
}

代价是先把缓冲区清零。

如果确实要省掉这一步，就得用 MaybeUninit<u8> 或原始分配空间，并且严格按这个顺序：

分配足够容量
      │
      ▼
外部函数写入数据
      │
      ▼
验证外部函数实际初始化的字节数
      │
      ▼
确认 written <= capacity
      │
      ▼
最后才把 len 设为 written

这里有个关键细节：written <= capacity 只证明长度没越界，不能证明 C 真的初始化了这些字节。如果 C 的契约不保证它初始化前 written 个字节，Rust 侧就不能仅凭这个数字设置长度。

这就是 FFI 里「类型信息」和「外部契约」的区别。

九、如果析构函数自己 panic 呢

struct Item {
    id: usize,
}

impl Drop for Item {
    fn drop(&mut self) {
        if self.id == 2 {
            panic!("drop failed");
        }
    }
}

假设容器逆序清理：

Item 4
Item 3
Item 2  ← panic
Item 1
Item 0

Item 2 的析构 panic 后，后续清理流程就被打断了。

更糟的是，如果此时程序本来就在另一次 panic 的栈展开过程中，再次 panic 会导致进程直接 abort。所以「double panic」不是能被 catch 住的普通错误。

要点：

  • Drop 接口本身没承诺析构函数绝不 panic；
  • panic = "abort" 下程序直接终止；
  • 栈展开期间再次 panic，进程会终止；
  • 复杂的清理逻辑必须明确自己的异常行为。

实践上，析构函数应该尽量简单可靠，别在里面做容易失败的复杂业务。自定义容器如果要考虑「析构一个元素就中断后续清理」这种情况，就得明确设计是否接受、要不要额外的恢复策略。

十、把机制串成一张图

            MaybeUninit<T>
                  │
                  │ 表达存储空间可能未初始化
                  ▼
              初始化元素
                  │
                  │ ptr::write()
                  ▼
              有效的 T 对象
                  │
                  │ 记录初始化状态
                  ▼
               len / guard
                  │
                  │ 正确转移所有权
                  ▼
              容器接管对象
                  │
                  │ 正常析构或栈展开
                  ▼
                Drop<T>
                  │
                  ▼
                释放资源

ptr::read() 是另一条与所有权转移有关的路径：

已初始化的 T
     │
     │ ptr::read()
     ▼
返回一个按值读取的 T

它不会改变源位置的状态，也不会更新 len。所以调用者必须保证不会出现两个所有者都认为自己拥有同一个非 Copy 对象。

set_len() 则是：

已有初始化事实
       │
       ▼
更新容器对有效元素数量的记录

它不构造对象，也不验证外部函数是否守约。

十一、我从这节里提炼的四个不变量

写到这里，我把这一节的内容压成四类可以拿去做代码审查的不变量。

1. 初始化不变量

任何控制流路径上，容器声明为有效的元素都必须真的初始化了。

0 ≤ len ≤ capacity
并且 [0, len) 中的元素都有效

只检查 len <= capacity 不够，它证明不了元素确实初始化过。

2. 所有权不变量

每个需要析构的对象，都必须有明确的析构责任归属。重点看：

  • ptr::read() 之后源位置的状态；
  • 对象移出容器之后的清理责任；
  • guard 提交之后是否仍会析构对象；
  • FFI 返回的对象到底由谁释放。

3. 分配不变量

容器必须知道：哪个指针对应哪次分配、布局是什么、分配是否仍有效、释放时用的布局是否匹配、有没有重复释放。

4. 异常路径不变量

除了正常控制流，还要看：初始化中途 panic、重新分配失败、guard 在栈展开期间执行、析构函数自身 panic、外部 FFI 函数返回错误或违约。

这也是原始内存分析和普通语法级检查的分界：不能只看每条指令「看起来安不安全」，还得看不同控制流路径怎么改变对象的初始化状态和所有权状态。

十二、小结

五句话说完这节：

  1. Unwinding 是 panic 时的栈展开机制，正常情况下会清理离开作用域的局部变量。
  2. 异常安全要求失败路径也不能破坏内存安全和内部不变量。
  3. Guard 能把部分初始化的清理责任绑定到对象生命周期上。
  4. ptr::read() 和 ptr::write() 只做底层内存操作，不管理容器状态。
  5. set_len() 只改长度记录，调用者必须保证范围内元素已初始化。

Rust Vec 的真实内存布局、扩容与 ZST

2026-10-25
:: tags:  #Memory  #Rust  #Vec  #ZST

前面几节攒下的 MaybeUninit<T>、Drop、ptr::read、ptr::write、set_len()，最后都会在 Vec 的实现里汇合。这篇就把它们对起来看。

还有一个我最初没想明白的问题：

如果一个类型占 0 字节，Vec<T> 还需要分配内存吗？如果不需要，它怎么表示自己拥有 100 个这样的元素？

参考：Vec<T>、Rustonomicon: Exotic Sizes。

一、先建立 Vec 的内存模型

let mut values: Vec<u32> = Vec::with_capacity(8);
values.push(10);
values.push(20);
values.push(30);
values.len()      // 3
values.capacity() // 至少 8

概念上的布局：

Vec<u32> 这个对象
┌─────────────────────┐
│ ptr                 │ ─────────────┐
│ len = 3             │              │
│ capacity >= 8       │              │
└─────────────────────┘              │
                                     ▼
堆内存
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ ?? │ ?? │ ?? │ ?? │ ?? │
└────┴────┴────┴────┴────┴────┴────┴────┘
  └─────────┘
    len = 3
  └───────────────────────────────────┘
               capacity >= 8

注意那些 ??。

这些位置属于分配出来的存储空间，但不一定包含已经初始化的 u32。这就是前几节反复强调的区别：

  • 容量描述可用存储空间；
  • 长度描述已经初始化、由容器拥有的元素。

Vec<T> 必须维护这个不变量：

0 ≤ len ≤ capacity

并且对普通的非零大小类型，[0, len) 中每个元素都必须是有效的 T。

这不是可有可无的约定，而是 Vec 能正确访问和析构元素的基础。

1.1 Vec 对象本身不等于元素数组

let values = vec![10u32, 20, 30];

values 这个变量保存的是容器的管理信息，元素通常在另一块单独分配的内存里。

Vec<T> 的管理对象
        ≠
Vec<T> 所拥有的元素存储空间

所以移动一个 Vec<T>，通常不需要把所有元素逐个复制到新地址——搬的只是那三个字的头。

二、RawVec：只管理内存，不负责元素生命周期

理解 Vec 的实现，可以从职责划分入手。概念上它分两层：

┌────────────────────────────┐
│ Vec<T>                     │
│                            │
│ len                        │
│ 元素初始化状态             │
│ 元素所有权与析构           │
└─────────────┬──────────────┘
              │
              ▼
┌────────────────────────────┐
│ RawVec<T>                  │
│                            │
│ 原始内存指针               │
│ 容量管理                   │
│ 分配与重新分配             │
│ 释放存储空间               │
└────────────────────────────┘

这是概念模型。具体字段和内部辅助类型会随 Rust 版本变化，别把这张图当成当前源码的逐字结构。

两层关心的东西不一样：

RawVec 只管：内存在哪、分配了多少容量、要不要扩容、怎么重新分配、怎么释放。

Vec 还要管：哪些位置已初始化、当前拥有几个元素、哪些要析构、怎么安全地增删和移动元素。

为什么要拆开？因为分配了一段内存，不代表里面已经存在对应数量的 T 对象。

let mut values: Vec<String> = Vec::with_capacity(100);

这行不会创建 100 个 String。它创建的是一个 len = 0、capacity >= 100 的容器。底层空间是有了，但没有 100 个 String 等着被析构。

这就是内存分配层和元素生命周期管理层必须协同工作的原因。

三、扩容时究竟发生了什么

let mut values = Vec::with_capacity(4);
values.push(10);
values.push(20);
values.push(30);
values.push(40);

此时 capacity = 4、len = 4。再 push(50)，容器得腾出第 5 个位置：

原有内存
┌────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │
└────┴────┴────┴────┘
       capacity = 4
       len = 4
             │
             ▼
       申请更大空间
新内存
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ ?? │ ?? │ ?? │ ?? │
└────┴────┴────┴────┴────┴────┴────┴────┘
              capacity >= 5

这是逻辑结果，不意味着分配器一定会把数据搬到另一个地址。重新分配可能原地扩展，也可能整个搬走，取决于分配器、布局和实现策略。

如果要搬，原来的元素必须在新位置继续保持有效，并且不能在搬运过程中被重复析构。

3.1 Rust 的「移动」不一定逐字节复制

let a = String::from("hello");
let b = a;

执行后 a 不再拥有这个 String，所有权给了 b。

从语义上说这是一次移动。但对 String 这种类型，Rust 通常只要搬指针、长度、容量这几个字，不需要复制全部字符。

Vec 扩容时的情形又不一样：如果底层分配要移动，容器得保证原有元素被正确搬到新地址，而且对带析构函数的类型，不能留下两份都被认为有效的所有者。

旧地址：元素原本所在的位置
                │
                │ 受控地转移元素
                ▼
新地址：元素后续所在的位置

原来的位置不能再被当作仍然拥有该对象的有效元素。

真实的实现会按具体操作选不同策略，不能假定所有扩容都走同一套逐元素复制或移动算法。

四、为什么扩容用几何增长

如果每次加元素只把容量加 1，插 1000 个元素会怎样？

容量 0 → 1
容量 1 → 2
容量 2 → 3
...
容量 999 → 1000

每次扩容都要重新分配并搬移现有元素，总搬移量是：

1 + 2 + 3 + ... + (n-1) = n(n-1)/2

也就是 O(n²)。这对大量插入来说完全不能接受。

几何增长（比如按大于 1 的比例翻倍）就不同：

4 → 8 → 16 → 32 → 64 → ...

所有扩容中搬移的元素总数可以控制在 O(n)。于是连续 n 次 push() 的总成本是 O(n)，单次 push() 的摊销复杂度是 O(1)。

要注意两点：

  • 摊销不等于每次都常数时间。触发扩容那一次仍然要搬一大批元素。
  • 具体倍率不是稳定 API 保证，会随标准库版本和实现变化。

真正该记住的是：几何增长在额外空间和重新分配成本之间取了不错的平衡。

五、重新分配失败怎么办

len = 4
capacity = 4

要给第 5 个元素腾地方，但新分配失败了，合理的容器行为是：

  • 原来的 4 个元素仍然有效；
  • 原来的所有权关系不能被破坏；
  • 不得析构未初始化的内存；
  • 不得释放仍由容器拥有的有效元素；
  • 失败不能让容器进入不一致状态。

这正好对应上一节的异常安全原则。

原有容器
    │
    ▼
申请新的存储空间
    │
    ├── 失败
    │     │
    │     ▼
    │  保留原有状态
    │
    └── 成功
          │
          ▼
      转移已有元素
          │
          ▼
      更新指针与容量
          │
          ▼
      释放旧存储空间

这是逻辑流程，不代表所有路径都严格这么分步。

还有个现实细节：某些分配器接口在失败时会直接触发分配错误处理，而不是返回 Result。所以别指望所有 Vec 扩容失败都像普通业务错误一样被 catch 住。

自己设计容器或 FFI 缓冲区时，就得明确回答：

  • 分配失败返回错误还是 panic？
  • 保留原有数据吗？
  • 允许部分完成吗？
  • 需不需要强异常保证？

这些都属于 API 设计的一部分。

六、最特殊的情况：零大小类型

前面聊的 u32、String 都占空间，但 Rust 允许定义零大小类型：

struct Marker;

struct Nothing {
    marker: (),
}

它们的大小都是 0：

use std::mem::size_of;

fn main() {
    println!("size_of::<()>() = {}", size_of::<()>());
    println!("size_of::<Marker>() = {}", size_of::<Marker>());
    println!("size_of::<Nothing>() = {}", size_of::<Nothing>());
}
size_of::<()>() = 0
size_of::<Marker>() = 0
size_of::<Nothing>() = 0

编译器不需要为每个值保留独立的有效载荷字节。

于是问题来了：

let mut values: Vec<Marker> = Vec::new();
values.push(Marker);
values.push(Marker);
values.push(Marker);
len = 3

三个 Marker 不占三个独立的元素存储区域，那容器怎么表示自己拥有三个元素？

答案：靠长度这类元数据表达元素数量，而不是靠元素占了多少字节。

len 表示元素数量，不是有效载荷字节数。这和前面建立的内存模型完全一致。

七、ZST 的 Vec 为什么不需要元素分配

use std::mem::size_of;

struct Marker;

fn main() {
    println!("Marker size = {}", size_of::<Marker>());

    let mut values = Vec::new();
    values.push(Marker);
    values.push(Marker);
    values.push(Marker);

    println!("len = {}", values.len());
    println!("capacity = {}", values.capacity());
}

注意这里的类型推导：因为后面插入了 Marker，编译器推出 Vec<Marker>。

标准库对 ZST 用了特殊路径。我在本机实测（rustc 1.99）：

Marker size = 0
len = 3
capacity = 18446744073709551615

capacity 是 usize::MAX。这很合理：零大小元素不需要实际存储空间，容量上限就只剩 usize 能表示多少的问题。

不过 ZST 的具体内部表示属于实现细节，写代码时应该依赖 Vec 的公开 API，而不是去推断内部指针值。

7.1 ZST 不等于没有生命周期

这点特别容易误解。

use std::sync::atomic::{AtomicUsize, Ordering};

static DROPS: AtomicUsize = AtomicUsize::new(0);

struct Marker;

impl Drop for Marker {
    fn drop(&mut self) {
        DROPS.fetch_add(1, Ordering::SeqCst);
    }
}

Marker 不占有效载荷字节，但它有 Drop 行为：

let mut values = Vec::new();
values.push(Marker);
values.push(Marker);
values.push(Marker);
drop(values);

三个元素仍然要按容器的生命周期语义逐个析构。我实测打印了 3 次 drop Marker。

所以 ZST 的特殊性只在于：

  • 每个元素不需要独立的有效载荷存储；
  • 容器仍然要维护元素数量；
  • 元素仍然可能有析构行为；
  • 所有权与生命周期规则仍然生效。

零大小 ≠ 零生命周期，也不等于零析构成本。

八、ZST 为什么让指针运算变特殊

struct Marker;

因为 size_of::<Marker>() == 0，如果按普通数组的字节布局算地址：

第 0 个元素的偏移量 = 0 × 0 = 0
第 1 个元素的偏移量 = 1 × 0 = 0
第 2 个元素的偏移量 = 2 × 0 = 0

所有偏移量都是 0。

ptr.add(0)
ptr.add(1)
ptr.add(2)

对 ZST，不能期待这几个指针像普通数组那样对应不同字节地址。

但这不影响 Vec<Marker> 表示多个元素——Rust 的元素数量语义本来就不要求每个零大小值占据不同的字节。

同时要注意：不能把「元素大小为 0」理解成「指针运算可以随便做」。原始指针操作仍然必须满足 API 的安全契约。

8.1 一个常见的错误设计

假设自己写容器：

struct MyVec<T> {
    ptr: *mut T,
    len: usize,
    capacity: usize,
}

push 里用：

let destination = self.ptr.add(self.len);

对普通类型这符合直觉：索引对应不同字节偏移。但对 ZST：

size_of::<T>() == 0

按字节算的偏移量不随索引增长，这套逻辑就失效了。

容量管理也有问题：如果每个元素大小为 0，用「总分配字节数 ÷ 元素大小」来算容量会直接除零。

这就是标准库必须给 ZST 走特殊路径，而不能套用普通分配公式的原因。

九、ZST 与 Drop Check

把这一节和之前的 PhantomData<T> 接上：

use std::marker::PhantomData;

struct MyHandle<T> {
    raw: *mut u8,
    marker: PhantomData<T>,
}

PhantomData<T> 本身不占空间：

size_of::<PhantomData<String>>() == 0

但它仍然表达类型系统中的关系。即使不占内存，它也会影响型变和 auto trait 推导。

这里要分清两件事：

  • PhantomData<T> 能告诉编译器类型之间存在什么关系；
  • 它不能凭空证明原始指针有效，也不能保证外部资源还在。

如果 raw 指向 C 分配的对象，那么何时释放、谁负责释放、能否跨线程使用，仍然得由实现和安全契约保证。

这和 ZST 的核心思想一致：类型的内存大小，与它在类型系统中表达的语义，不是一个概念。

十、把 ZST、容量与 Drop 放一起

struct Marker;

impl Drop for Marker {
    fn drop(&mut self) {
        println!("drop Marker");
    }
}

fn main() {
    let mut values = Vec::new();
    for _ in 0..3 {
        values.push(Marker);
    }
    drop(values);
}

即使 Marker 大小为 0，容器仍然必须知道「我拥有三个元素」，否则没法正确析构。

所以 Vec 的核心不变量不能简化成：

len = 已经分配的字节数        ❌

正确的是：

len = 已初始化、由容器拥有的元素数量

普通类型下，元素存储空间大约是：

capacity × size_of::<T>()

但 ZST 时 size_of::<T>() = 0，这个乘法结果是 0，而不能据此推断容器没有任何逻辑元素。

长度、所有权、析构语义一样都不能少。

Rust Pin：地址稳定性到底在保证什么

2026-10-25
:: tags:  #Async  #Pin  #Rust  #Unsafe

我一开始对 Pin 的理解是错的。我以为它会把内存锁住，后来发现它连「禁止移动」都不完全成立——Pin<Box<T>> 这个变量本身照样可以搬来搬去。

真正的结论只有一句：

Pin 不是锁内存，也不是禁止所有移动。它是一套类型系统约定，用来保证某些值在被固定期间不会被移动出原来的内存位置。

为什么需要这种保证？得从 Rust 的普通移动语义说起。

一、Rust 的「移动」到底做了什么

struct User {
    name: String,
    age: u32,
}

fn main() {
    let a = User {
        name: String::from("Alice"),
        age: 18,
    };
    let b = a;
    println!("{}", b.name);
}

执行 let b = a; 之后，a 的所有权转移给 b，a 不能再用了。

但这里有个关键问题：

移动一个 Rust 值，是不是意味着它拥有的堆内存也被搬走了？

不是。String 大致长这样：

String 对象
┌─────────────────┐
│ ptr             │ ────────┐
│ len             │         │
│ capacity        │         │
└─────────────────┘         │
                            ▼
                       堆内存
                    ┌─────────────┐
                    │ Alice       │
                    └─────────────┘

移动时 Rust 只需搬走那三个字的头，字符本身原地不动。

但如果结构体里有个指针指向自己，事情就不一样了。

1.1 自引用结构体的问题

struct SelfRef {
    data: String,
    ptr: *const String,
}

我想让 ptr 指向结构体自己的 data 字段：

SelfRef 位于地址 A
┌──────────────────────────┐
│ data: String             │
│                          │
│ ptr ─────────────────────┼──┐
└──────────────────────────┘  │
                              │
                              ▼
                         data 字段

如果结构体被移到地址 B，而 ptr 还指着地址 A：

原地址 A                   新地址 B
┌───────────────┐          ┌───────────────┐
│ 旧对象的内存  │          │ 新对象        │
│               │          │ data          │
│ ptr ──────────┼──────┐   │               │
└───────────────┘      │   └───────────────┘
                       │
                       ▼
                  原地址 A

原地址上的对象一旦失效，ptr 就变成悬垂指针。

注意这里有两个细节：

  • 不是所有自引用结构体都会因为移动出错——关键在于内部引用是否依赖外层对象的固定地址。
  • 上面这个 SelfRef 只是展示问题的骨架，它并没有真的建立自引用关系（ptr 还是空指针）。

二、为什么 &mut T 不够

既然有借用检查器，为什么还非要 Pin？

因为借用检查器管的是生命周期和别名，它并不会阻止值被搬到新地址。let b = a; 这种移动完全合法。

而自引用对象需要的是另一层保证：

对象被固定之后，在特定期间内，不能通过安全操作把它移动到别的内存位置。

这叫地址稳定性。

有些类型不在乎自己住哪：u64、String、Vec<u8> 都可以随便搬。另一些类型则依赖地址：

  • 包含指向自身字段的原始指针的结构体；
  • 某些底层异步状态机；
  • 依赖固定地址的 FFI 对象；
  • 侵入式链表节点；
  • 保存指向自身内部数据的回调注册信息。

具体的冲突点在这里：

struct Data {
    value: String,
}

let mut data = Data { value: String::from("hello") };
let r: &mut Data = &mut data;

r.value.push_str(" world");   // 改字段，没问题
*r = Data { value: String::from("new") };  // 替换整个对象

两种操作都合法。但一旦 Data 内部有指向自身的指针，第二种操作就可能让内部指针失效。

所以需要一种更强的引用：Pin<&mut Data>。它的意思不是「我有一个可变引用」，而是：

我有一个指向已固定对象的可变引用，并且在固定约定生效期间，不能通过安全操作把这个对象移出它的固定位置。

关键字是「移出对象」，不是「禁止修改对象」。固定住的对象照样可以有可变状态。

顺带说一句：Pin 不是实现地址稳定的唯一办法。你也可以把对象放在永不移动的堆分配里，并且不暴露会破坏不变量的接口。Pin 的价值在于能把这类约定写进类型系统。

三、Pin 到底是什么

use std::pin::Pin;

泛型参数 P 通常是指针类型：

Pin<Box<T>>
Pin<&mut T>
Pin<Arc<T>>
类型含义
Box<T>拥有堆上 T 的所有权
Pin<Box<T>>通过 Box 拥有一个被固定的 T
&mut T对 T 的独占可变借用
Pin<&mut T>对一个被固定的 T 的独占可变借用

最重要的一句话：

Pin 固定的是指针所指向的值，不是指针对象自身的地址。

let value = Box::pin(42);
栈
┌─────────────────┐
│ Pin<Box<i32>>   │
└────────┬────────┘
         │
         ▼
堆
┌─────────────────┐
│ i32 = 42        │
└─────────────────┘

Pin<Box<i32>> 通过 Box 指向堆上的整数。栈上那个 Pin<Box<i32>> 变量随便搬，堆上的 i32 不动。

但这里还有个坑：i32 是 Unpin 的，所以 Pin<Box<i32>> 并不会真的阻止你通过合法途径把它取出来。这就引出了 Unpin。

四、Unpin：什么时候不需要固定

pub auto trait Unpin {}

Unpin 是个 auto trait，含义很简单：

T: Unpin 表示这个类型不依赖 Pin 提供的固定地址保证。

绝大多数普通类型都是 Unpin：

fn assert_unpin<T: Unpin>() {}

fn main() {
    assert_unpin::<u32>();
    assert_unpin::<String>();
    assert_unpin::<Vec<u8>>();
}

这些类型随便移动都没问题，Pin 对它们而言形同虚设。

反过来，需要地址稳定的类型可以用 PhantomPinned 阻止自动实现 Unpin：

use std::marker::PhantomPinned;

struct SelfRef {
    data: String,
    ptr: *const String,
    _pin: PhantomPinned,
}

PhantomPinned 是零大小标记类型，但作用和 PhantomData<T> 完全不同：

  • PhantomData<T> 表达所有权、生命周期、型变这些类型系统关系；
  • PhantomPinned 只做一件事——阻止类型自动实现 Unpin。

PhantomPinned 本身不会把对象固定在任何地址。 它只改变类型的 Unpin 属性。

let value = SelfRef {
    data: String::from("hello"),
    ptr: std::ptr::null(),
    _pin: PhantomPinned,
};

这个对象仍然可以自由移动，因为还没有任何 Pin 参与。

两个机制要分清：

PhantomPinned
    │
    └── 阻止类型自动实现 Unpin

Pin<P>
    │
    └── 在安全约定成立时，固定指针指向的值

五、Pin<Box<T>> 与 Pin<&mut T>

5.1 Pin::new 与 Box::pin

这两个 API 经常被搞混。

use std::pin::Pin;

let mut value = 42;
let pinned = Pin::new(&mut value);   // Pin<&mut i32>

Pin::new 不分配内存，它只是把现有引用包一层。标准库要求传入的指针目标必须 Unpin——因为只有这样，包装才不需要额外的保证。

let value = Box::pin(42);            // Pin<Box<i32>>

Box::pin 会把值放到堆上再固定。对 !Unpin 类型，这是最常见的固定方式。

但固定不是单纯由「在堆上」决定的。普通 Box<T> 也能搬所有权、也能在满足规则时把 T 取出来；Pin<Box<T>> 对 !Unpin 类型施加的约束要强得多。

区别不只是堆分配，而是类型系统表达的契约。

5.2 移动的是指针所有者

let future1 = Box::pin(some_future());
let future2 = future1;
栈上的指针对象
┌──────────────────┐
│ Pin<Box<Future>> │
└────────┬─────────┘
         │
         ▼
堆上的 Future
┌──────────────────┐
│ Future 状态机    │
└──────────────────┘

移动 Pin<Box<Future>> 只是换了个变量持有这个指针，堆上的 Future 一动没动。

这也解释了为什么堆分配总跟 Pin 一起出现：搬指针所有者，不等于搬被指向的对象。

六、get_mut 与 get_unchecked_mut

6.1 get_mut 为什么要求 Unpin

pub fn get_mut(self) -> &mut T
where
    T: Unpin,

为什么有这个约束？因为普通 &mut T 允许你替换整个对象：

*value = another_value;

如果 T 依赖固定地址，这个操作就可能毁掉内部自引用。

我实测过：给一个含 PhantomPinned 的类型调 get_mut()，编译器直接拒绝。

error[E0277]: `PhantomPinned` cannot be unpinned

所以标准库用 Unpin 把情况分成两类：

  • T: Unpin：可以安全地拿普通可变引用；
  • T: !Unpin：安全 API 不给你这个引用。

这是编译期约束，不是运行时检查。

6.2 get_unchecked_mut 为什么是 unsafe

pub unsafe fn get_unchecked_mut(self) -> &mut T

它不要求 Unpin，代价是你得自己保证后续操作不会破坏固定地址约定。

危险在哪？拿到 &mut T 之后，这两件事都可能发生：

*value = another_value;
let moved = std::mem::replace(value, another_value);

都可能把对象整体换掉或搬走。

正确用法只有四步：

  1. 通过 unsafe 拿到普通可变引用；
  2. 只修改不会破坏固定约定的字段；
  3. 不把整个对象移走；
  4. 不通过其他路径绕过约定。

这和 ptr::write() 有点像：都能做底层操作，但调用者必须证明操作符合契约。区别是职责不同——ptr::write 管写入不管旧值析构，get_unchecked_mut 管绕过固定限制不管后续移动。

七、完整构造一个自引用类型

前面都是骨架，现在来一个能跑起来的。

use std::marker::PhantomPinned;
use std::pin::Pin;
use std::ptr;

struct SelfRef {
    data: String,
    ptr: *const String,
    _pin: PhantomPinned,
}

impl SelfRef {
    fn new(data: String) -> Pin<Box<Self>> {
        let mut value = Box::pin(Self {
            data,
            ptr: ptr::null(),
            _pin: PhantomPinned,
        });

        let self_ptr: *const String = &value.data;

        // SAFETY: value 已经被 Box::pin 固定，
        // 这里只修改 ptr 字段，不移动 SelfRef 本身。
        unsafe {
            value.as_mut().get_unchecked_mut().ptr = self_ptr;
        }

        value
    }

    fn data(self: Pin<&Self>) -> &str {
        &self.get_ref().data
    }

    fn pointer_is_valid(self: Pin<&Self>) -> bool {
        self.ptr == &self.data as *const String
    }
}

fn main() {
    let value = SelfRef::new(String::from("hello"));
    assert_eq!(value.as_ref().data(), "hello");
    assert!(value.as_ref().pointer_is_valid());
}

拆开看三步。

第一步：先分配，再固定

let mut value = Box::pin(Self {
    data,
    ptr: ptr::null(),
    _pin: PhantomPinned,
});

Box::pin 把对象放到堆上并返回 Pin<Box<Self>>。因为 Self 含 PhantomPinned，它不会自动实现 Unpin，后续安全代码不能把它从固定位置取出来。

第二步：建立内部指针

let self_ptr: *const String = &value.data;
unsafe {
    value.as_mut().get_unchecked_mut().ptr = self_ptr;
}

这里必须 unsafe。get_unchecked_mut() 不会替你保证后续操作遵守固定约定——我们只改 ptr 字段、不动 SelfRef 本身，所以安全。

第三步：只通过固定引用访问

fn data(self: Pin<&Self>) -> &str

方法用 Pin<&Self> 接收，表达「调用者访问的是一个已经被固定的对象」。

不过这个例子依然依赖实现者守规矩。Pin 不是运行时的内存保护，它不会检查你的裸指针是否还有效。

八、字段修改 vs 字段替换

这段我以前混淆过，值得单独说。

struct Data {
    value: String,
}

对象已经固定，现在只想改 value。两种写法的语义不一样：

value.push_str("hello");        // A
self.value = String::from("new");  // B
  • A 改的是 String 管的堆缓冲区，可能触发扩容重新分配，但外层 Data 对象没动。
  • B 替换了 String 字段的值，外层 Data 也不必然移动，但会影响那些指向旧字段值或旧缓冲区的指针。

所以对自引用类型，不能只问「外层对象动没动」，还得问：

  • 内部指针指向的是外层对象的字段地址，还是字段拥有的堆缓冲区？
  • 被替换字段的地址稳定吗？
  • 被指向的数据还有效吗？
  • 这次修改会不会破坏别的字段维护的不变量？

举例：如果内部指针指向 String 对象本身，那么替换该字段就断了关系；如果指向字符缓冲区，那么 String 扩容时缓冲区换地址，指针同样失效。

Pin 固定的是外层对象的地址，不会自动固定它拥有的所有间接分配。 这点在 FFI 和自引用设计里特别关键。

九、Pin 与 Drop

对象最终总要销毁。被 Pin 住的对象当然也能 Drop。

use std::marker::PhantomPinned;

struct Resource {
    value: String,
    _pin: PhantomPinned,
}

impl Drop for Resource {
    fn drop(&mut self) {
        println!("Dropping: {}", self.value);
    }
}

但 Drop::drop 收到的是 &mut self，不是 Pin<&mut Self>。这不是漏洞。

Pin 的契约要求是：如果类型依赖固定地址，它的安全实现不能在对象还处于 Pin 保证范围内时把对象整体移出原位置。

正常析构当然可以释放内部资源，析构结束后存储空间也可以被回收。但不能在析构过程中偷偷把整个 !Unpin 对象搬到别处，然后假装 Pin 保证还成立。

所以如果你写了一个依赖地址稳定的 !Unpin 类型，下面这些都得想清楚：

  • 构造函数怎么建立自引用；
  • 公共方法怎么避免移动对象；
  • 内部修改怎么维护指针关系；
  • Drop 怎么清理依赖固定地址的资源；
  • 有没有 mem::replace、ptr::read 这类绕过路径。

这跟上几节 Vec、MaybeUninit、Drop Check 是同一类问题：你必须清楚对象在每个生命周期阶段归谁所有，哪些不变量必须成立。

十、安全性为什么依赖类型实现者

这是 Pin 最容易被忽略的一层。

struct MyType {
    data: String,
}

就算你把它装进 Pin<Box<MyType>>，也不代表所有代码都遵守了固定约定。

假设这个类型提供了这样一个安全方法：

impl MyType {
    fn dangerous(self: Pin<&mut Self>) {
        // 如果这里内部通过 unsafe 移动整个对象，
        // 就会破坏 Pin 的安全约定
    }
}

调用者完全按安全 API 的规则用，也可能踩到内存安全问题。

所以 Pin 的安全性不只是调用方的事。类型实现者必须保证自己暴露的安全接口不会破坏 pinning 约定。

这和设计安全的 FFI wrapper 是同一个道理：不能要求调用者先理解一堆隐藏的 unsafe 不变量，才能正确使用一个声称安全的 API。

十一、Pin Projection

这是 Pin 进阶里最重要的一块。

11.1 为什么不能直接取字段

use std::marker::PhantomPinned;

struct Inner {
    value: String,
    _pin: PhantomPinned,
}

struct Outer {
    inner: Inner,
    name: String,
    _pin: PhantomPinned,
}

把 Outer 固定住，得到 Pin<Box<Outer>>。现在我想取 Pin<&mut Inner>，也就是把：

Pin<&mut Outer>  →  Pin<&mut Inner>

问题是：父对象被 Pin 住，不代表它的所有字段都必须遵守 Pin 约束。

struct Outer {
    movable: String,
    _pin: PhantomPinned,
}

Outer 是 !Unpin，但 movable 字段仍然是 Unpin，它可以在不移动父对象的前提下被单独替换。

所以不能想当然地认为「父对象固定了，字段就都固定了」。这不是 Pin 的语义。

要做投影，必须先回答：Outer::inner 这个字段是否也必须遵守固定地址契约？

  • 是 → 安全 API 就不能允许它被移出原位置；
  • 否 → 它可以移动，但你不能假装它也拿到了 Pin 保证。

11.2 map_unchecked_mut

impl Outer {
    fn project_inner(self: Pin<&mut Self>) -> Pin<&mut Inner> {
        unsafe { self.map_unchecked_mut(|outer| &mut outer.inner) }
    }
}

Pin::map_unchecked_mut 是 unsafe 的。原因：调用者必须保证投影出来的字段在被 Pin 期间不会被移出原位置。

它本身不会阻止任何事，只是把维护不变量的责任交给你。

所以手写投影不只是写一个转换函数。你得把整个 API 过一遍：

  • 有没有安全方法能移动这个字段？
  • 能不能通过 &mut Self 替换字段？
  • 能不能用 mem::replace 移出字段？
  • Drop 会不会破坏不变量？
  • 还有没有别的路径能绕过投影约束？

漏一个，单独正确的投影函数也救不了整个类型。

11.3 工程上怎么写

生产代码一般用现成的投影工具，比如 pin-project：

use pin_project::pin_project;
use std::marker::PhantomPinned;

#[pin_project]
struct Outer {
    #[pin]
    inner: Inner,
    name: String,
    _pin: PhantomPinned,
}
  • #[pin] 标记的是 pinned 字段；
  • 没标记的 name 是普通字段；
  • 宏根据声明生成投影接口。

概念上，使用者会拿到类似这样的东西：

struct OuterProjection<'a> {
    inner: Pin<&'a mut Inner>,
    name: &'a mut String,
}

这是解释语义的伪代码，不是宏真实生成的完整形式。实际使用请照宏的文档来，别自己猜接口。

重点只有一个：pinned 字段和普通字段的访问方式不同。 对 pinned 字段不能随手给出一个能把它移走的普通可变引用。

十二、Future：为什么 poll 收 Pin<&mut Self>

pub trait Future {
    type Output;
    fn poll(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>,
    ) -> Poll<Self::Output>;
}

为什么不是 &mut self？

因为某些 Future 在第一次被 poll 之后，可能建立依赖自身地址的内部状态。如果调用者之后随意移动它，内部关系就断了。

Pin<&mut Self> 给这些 Future 提供了固定地址语义。

但别因此认为所有 Future 都要固定地址。很多 Future 是 Unpin 的，根本不依赖地址稳定。poll 收 Pin<&mut Self> 是为了让整个接口能容纳那些确实需要固定的实现。

也就是说，Pin 不是为了让异步任务动不了，而是为了让可能自引用的 Future 也能被纳入统一接口。

12.1 .await 做了什么

async fn fetch_data() -> String {
    String::from("hello")
}

let future = fetch_data();

调用 fetch_data() 不会立刻执行函数体并返回 String。它生成一个实现 Future 的状态机对象：

Future 状态机
┌──────────────────────┐
│ 当前执行状态         │
│ 局部变量             │
│ 等待中的子 Future    │
│ 恢复执行所需的数据   │
└──────────────────────┘

当它在某个 .await 处暂停时，必须把恢复执行所需的全部状态保存下来。如果这些状态之间存在自引用关系，那它在被 poll 期间就不能随便移动。

这就是 Pin 在异步里的核心价值。

12.2 跨越 await 的局部变量

同步函数：

fn example() {
    let value = String::from("hello");
    do_something();
    println!("{}", value);
}

value 通常就是当前栈帧的一部分。

异步函数：

async fn example() {
    let value = String::from("hello");
    some_async_operation().await;
    println!("{}", value);
}

执行停在 .await 时，后面还要用 value，编译器就必须把它存进 Future 的状态里，将来恢复执行时再用。

所以异步函数里的局部变量，有时会变成 Future 对象的一部分。如果 Future 内部还要保存指向这些局部状态的引用，地址稳定性就变得重要了。

但也不要反推成「只要有 .await，Future 就一定是自引用结构体」。编译器会按实际代码生成不同的状态结构，很多 Future 完全不需要自引用。

Pin 提供的是一个通用保证：即使某个 Future 需要依赖地址稳定，也能在这个统一接口下安全运行。

12.3 手写一个最小 Future

先来个不需要地址稳定的：

use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct ReadyFuture {
    value: i32,
}

impl Future for ReadyFuture {
    type Output = i32;

    fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<i32> {
        let this = self.get_mut();
        Poll::Ready(this.value)
    }
}

ReadyFuture 会自动实现 Unpin，所以这里可以直接 get_mut() 拿普通可变引用。

如果类型是 !Unpin，这个安全接口就用不了了。

那能不能直接写 unsafe { self.get_unchecked_mut() }？技术上可以，但你必须自己保证：

  • 不把依赖固定地址的整个对象移走；
  • 不把 pinned 字段移出原位置；
  • 不通过其他安全接口破坏已建立的地址关系。

别因为函数收了 Pin<&mut Self>，就以为函数内部可以随便移动 Self。unsafe 不消除约束，它只是把责任交给你。

12.4 Waker 解决的是另一个问题

Future 没完成时返回 Poll::Pending。那执行器怎么知道什么时候该再 poll 一次？

靠 Context 里的 Waker。Future 暂时无法推进时，通过 Context 拿到 Waker，将来有进展时唤醒执行器。

Executor
   │
   ▼
Future::poll(Pin<&mut Future>, Context)
   │
   ├── Poll::Ready(value)
   │       └── Future 完成
   │
   └── Poll::Pending
           │
           ▼
      等待外部事件
           │
           ▼
      Waker 唤醒执行器
           │
           ▼
      再次 poll

Waker 不负责固定 Future 的地址。它和 Pin 是两件事：

机制解决的问题
Pin对象是否需要保持在原来的内存位置
WakerFuture 有进展时怎么通知执行器重新轮询

十三、Pin 与 FFI

void register_callback(void *context);

C 库会保存传入的 context，之后在回调里继续用它。

struct CallbackContext {
    state: i32,
}

let context = Box::pin(CallbackContext { state: 42 });

Box::pin 把对象放到堆上并固定住地址，C 保存的指针就不会因为 Rust 侧搬移而失效。

但 Pin 单独搞不定 FFI 安全。C 代码还可能：

  • 在 Rust 对象销毁后继续访问旧指针；
  • 把指针传给另一个线程；
  • 重复调用回调；
  • 回调还没结束就释放资源；
  • 保存未经授权的别名；
  • 违反 Rust 侧规定的调用顺序。

一个可靠的 FFI 设计还得明确：

  1. 谁拥有对象？
  2. 对象何时销毁？
  3. C 可以保存指针多久？
  4. 回调会不会并发？
  5. 允许重入吗？
  6. 允许从其他线程调用吗？
  7. 谁负责注销？
  8. 注销后怎么保证不再访问旧指针？

关键是要先弄清 C 端到底保存了什么：

情况 A：C 保存的是独立的稳定句柄（比如句柄 ID）。这种根本不需要 Pin，用句柄表加引用计数就够了。

情况 B：C 保存的是 Rust 对象本身的地址。如果对象注册后不能移动、C 又会长期访问，那固定地址才成为必要条件，才需要 Pin<Box<Context>>。

用 Pin 之前可以先问自己：能不能用一个独立稳定的句柄把 Rust 对象的移动隔离开？很多问题这样一绕就简单了。

不是所有涉及指针的问题都要上 Pin。先弄清要维护的不变量，再挑复杂度最低的方案。

十四、Pin 不能保证什么

这部分我特意写清楚，因为它比「Pin 能做什么」更容易出错。

14.1 不等于内存不释放

let pinned = Box::pin(42);

Box 被销毁时，指向的对象照样正常销毁。Pin 约束的是「在契约期内不被随意移动」，不是「永远存在」。

14.2 不等于线程安全

Pin<Box<T>> 不会让 T 自动变成 Send 或 Sync。这两个 trait 的含义一点没变。

14.3 不等于内部数据都固定

struct Example {
    text: String,
}

即使 Example 被 Pin 住，String 内部的字符缓冲区也不由 Pin 保证永远在同一个地址。如果你保存了指向该缓冲区的裸指针，那缓冲区扩容导致的失效得你自己分析。

14.4 不等于借用检查器的替代品

Pin 不会帮你解决：生命周期错误、数据竞争、悬垂指针、重复释放、无效的 FFI 所有权、裸指针别名、错误的线程同步。

它只解决一类很具体的问题：对象地址稳定性，以及由此产生的移动约束。

十五、五个常见误解

误解一：Pin 会锁住内存。

不是。它不是操作系统级的内存锁，也不会阻止别的代码访问那个地址。它只是类型系统层面的约定。

误解二：Box::pin(T) 之后什么都不能动。

不是。Pin<Box<T>> 这个指针所有者本身可以移动；如果 T: Unpin，连 T 都能安全取出。

误解三：PhantomPinned 会自动固定对象。

不是。它只阻止类型自动实现 Unpin。真正的固定要靠 Pin 加上正确的构造与访问接口。

误解四：Pin 能替代 FFI 的生命周期管理。

不能。它拦不住 C 端提前释放，也保证不了跨线程访问安全。

误解五：!Unpin 就已经固定了。

不是。!Unpin 只是「可能依赖地址稳定」的类型标记。没有 Pin 参与时，它照样能被 let b = a; 搬走。

十六、总结

整条链路是这样的：

Rust 普通移动语义
        │
        ▼
值可以在满足所有权规则时移动
        │
        ▼
某些对象依赖自身地址
        │
        ▼
需要地址稳定性保证
        │
        ├── PhantomPinned
        │      阻止自动实现 Unpin
        │
        └── Pin<P>
               提供固定地址约定
                    │
                    ├── 自引用结构体
                    ├── 某些异步 Future
                    ├── 侵入式数据结构
                    └── 部分 FFI 对象

三个定义：

  • Pin<P>：对指针指向的值提供固定地址语义，前提是相关安全约定得到遵守。
  • Unpin：表示类型不依赖 Pin 提供的固定地址保证。
  • PhantomPinned：阻止类型自动实现 Unpin，但自身不固定任何地址。

最后一句总结：

Pin 的核心不是「对象永远不能移动」，而是对于依赖固定地址的 !Unpin 类型，Pin 通过类型系统与安全 API 约束，保证对象在固定期间不会被安全地移出原位置。

要用对它，得同时理解：Unpin 决定约束是否必要，PhantomPinned 负责关掉自动实现，Pin<P> 表达约定，unsafe 操作维护不变量，Drop 也得守约——而 FFI 的所有权、生命周期、线程安全，仍然要单独管。
